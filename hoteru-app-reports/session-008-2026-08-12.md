# Session 8 — Second per-hotel tenant instance: `bwalk.hoteru.co.id`

**Date:** 2026-08-12

Production onboarding of **Bwalk Hotel Malang** as the second live per-hotel tenant, same
dedicated-clone-per-hotel model as session-002's Technopark Malang. This closes the follow-up
flagged in session-007: the app code (`apps/web/bwalk`, seed data) landed on `main` in that
session's 25-commit pull but was deliberately left staging-only (`dev`, `154.26.130.96`).
Production onboarding was scoped as a separate task there — this session is that task.

## What drove the design

- App code was already on `main` (no special branch needed, unlike Technopark's
  `feat/integration-area-a-b`) — confirmed the `~/hoteru-technopark` clone itself now tracks
  `main` too (multi-tenant backend merged in via PR #2, per session-004).
- A full staging runbook already existed at `docs/deployment-bwalk.md` (dev box, `*.dev.hoteru.uk`)
  documenting hotel id, ports, and tenant identity — used as the source for content facts, but
  **not** followed literally for two reasons specific to prod:
  1. Staging uses one shared monorepo checkout with multiple `.env.<tenant>` files; production
     uses Technopark's dedicated-clone-per-tenant model for consistency with the existing fleet.
  2. Staging's step 3 runs the generic `pnpm db:seed` — but that script now wipes all tables and
     creates **three** hotels (demo Jakarta + Technopark + Bwalk) in one DB. Production has never
     done that: a direct query of `hoteru_tpm` confirmed it holds only the Technopark hotel, not
     all three. Ran a dedicated `prisma/seed.bwalk.ts` instead (standing rule since session-002).

## Issue hit and resolved

**Technopark's documented admin login (`admin@technopark.com` / `tnpadmin123`) returned
`401 Invalid email or password`** when used as the second identity for the cross-tenant isolation
check. Not a blocker for this session — swapped to central's `admin@hoteru.com` credential to
complete the isolation proof (still valid: different JWT secret per tenant instance is the actual
mechanism being tested, any two tenants prove it). Left as an open follow-up below; not
investigated further here since it's pre-existing Technopark state, unrelated to this deploy.

**Cert issuance first attempt failed** — default `--dns-cloudflare-propagation-seconds` (10s) was
too short for the two new DNS records to propagate to Let's Encrypt's validators (NXDOMAIN on
`app.bwalk` and the apex). Retried with `45s` — succeeded. Worth using `45` by default for any
future tenant's first cert request, since two new records (this session) propagate slower than
Technopark's original one-shot request.
