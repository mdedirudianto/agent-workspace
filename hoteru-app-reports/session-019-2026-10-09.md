**Date:** 2026-10-09

Two pieces of work in one session. **(A)** Redeployed all three instances (central + Technopark +
Bwalk) from `f56d178` to `origin/main` `fb56685` (16 commits). **(B)** Onboarded **Syariah Radho

## Findings that shaped the work

- **Repo deploy docs don't apply to us.** `deploy.sh`, `docs/deployment-prod*.md` and
  `deployment-prod-avilia.md` describe the unrelated `103.253.244.195` single-VPS box (`db push`,
  tar-pipe). The real runbook is these reports (sessions 008/018). `docs/deployment-radho-syariah.md`
  is a **staging** (`dev`) record only.
- **Management refresh-token bug was live on `main` for all hotels.** `POST /auth/refresh` returns only
  `{ accessToken }`; the SPA interceptor destructured a non-existent `refreshToken` and stored the
  string `"undefined"`, so the **second** access-token expiry logged staff out. The fix existed only on
  the Radho staging release. Fixed in PR #26 (`c29f001`, regression test red→green, 7/7 management
  tests) and rebuilt into all four management SPAs.
- **Backend does not enforce capacity.** `BookingService.create` assigns a free room if one exists and
  otherwise creates the booking with `roomId = null`. The guest UI is the only gate
  (`availableCount >= rooms`). See the incident below.

### Incident during the smoke test (own goal, cleaned up)

The first smoke run assumed an empty-inventory booking would be refused and POSTed one to the
public booking route. It returned **201**: booking `RDH-OY2UZONO` (PENDING, `roomId` null, Rp 1.000.000)
plus Guest `smoke@example.invalid` were written to production `hoteru_radho`. Impact: none external
(Avilia unwired, no notifications, no payment rows; DB had no real customers). Cleaned up in one
transaction with `DELETE … WHERE id = <exact captured id> AND <guard columns>`, residue and all
table counts verified back to baseline (bookings 0, guests 0; hotel 1, types 3, users 2, rooms 0).
The script was changed to assert the UI gate (`availableCount` 0/0/0) and zero new rows instead of
posting a booking.
