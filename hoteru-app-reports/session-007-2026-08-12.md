## Actions taken — upload storage bridge (new infra, not in the original plan)

The design (`docs/superpowers/plans/2026-08-03-image-uploads.md`) assumes nginx and the app share
a box and can `alias` the upload directory directly. Our topology splits them: files live in
`/var/lib/hoteru/uploads` on `app` (`10.0.0.5`); the public-facing nginx is on `proxy`
(`10.0.0.2`). Resolved by standing up a private static file server on `app` and reverse-proxying
to it from `proxy`.

| # | Step | Result |
| --- | --- | --- |
| 1 | Backed up both proxy nginx vhosts before editing | snapshot on `proxy` under `/root/backups/hoteru-nginx-*` |
| 2 | On `app`: found nginx installed but inactive, with legacy unrelated vhosts in `sites-available` (biji, wagrab, ytgrab, etc. — pre-existing, untouched) and only `default` enabled | `default` listens on `80 default_server` across **all interfaces** — starting nginx as-is would have exposed a public "Welcome to nginx" page on this host for the first time (port 80 is open in `ufw`, nothing was listening there before) |
| 3 | Disabled `default` (`rm /etc/nginx/sites-enabled/default`); added a new `hoteru-uploads.conf` site, bound **only** to `10.0.0.5:8931` (matches the private-bound convention every other service on this host already follows, e.g. `meetgrab-api` on `:8930`), serving `/var/lib/hoteru/uploads` with `X-Content-Type-Options: nosniff`, `autoindex off` | `nginx -t` clean |
| 4 | `systemctl enable --now nginx` on `app` | running, confirmed listening only on `10.0.0.5:8931` via `ss -tlnp`, no public exposure |
| 5 | Added `location /uploads/ { proxy_pass http://10.0.0.5:8931/; ... }` (prefix-stripping form) to both `hoteru.uk.conf` and `technoparkmalang.hoteru.co.id.conf` on `proxy`, ahead of the catch-all `location /` | `nginx -t` clean, `systemctl reload nginx` |
