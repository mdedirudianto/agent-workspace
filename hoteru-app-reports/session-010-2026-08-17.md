Brought all three production checkouts on `app` up to `origin/main` (`ce49b0b` → `a57b217`, 15
commits): central `~/hoteru`, Technopark `~/hoteru-technopark`, Bwalk `~/hoteru-bwalk`. One real
schema migration in this range (`20260815000000_add_day_of_week_rates`) plus an idempotency fix to

## What drove this

15 commits had landed on `origin/main`: two feature PRs (day-of-week seasonal pricing +
server-authoritative booking totals; full room CRUD) and a 9-commit documentation overhaul
(`FEATURES.md`, rewritten `BUSINESS_RULES.md`/`PRODUCT_REQUIREMENTS.md`, a new
`docs/agents/baseline-prod-tenant-dbs.md` runbook — see finding below). No dependency or env
changes.

**Pricing (`4bb215a`):** `SeasonalRate` gains `daysOfWeek` (`0`–`6`, `0`=Sunday, empty = every day),
`priority` (highest wins when several rates match one night), and a nullable `endDate` (`null` =
open-ended standing rule, e.g. "every weekend"). `Hotel` gains `taxRate` (fraction; central
backfilled to `0.11`, tenants stay `0`). Booking totals are now computed server-side from
seasonal/day-of-week rates + re-validated promo + hotel tax — public booking routes **ignore any
client-sent `totalAmount`**. New `POST /bookings/staff` honors an explicit staff override; new
public `GET /rates/quote` lets front-ends preview the same math before submit.

**Rooms (`e1fc842`):** Full inventory CRUD (`POST/PATCH/DELETE /rooms/:id`) — add, edit
number/floor/type/notes, soft-delete (reactivates on room-number reuse), guarded against deleting
or retyping a room with a CONFIRMED/CHECKED_IN booking. Status stays on the existing
`PATCH /rooms/:id/status` route.

## Pre-deploy finding: tenant DBs needed baselining first

`docs/agents/baseline-prod-tenant-dbs.md` (new in this range) turned out to describe a **different,
unrelated deployment** — box `103.253.244.195`, `/opt/hoteru`, tar-pipe deploys, no git remote —
not our infra (same trap the README already flags for `docs/deployment-technopark.md`). But the
underlying problem it describes is real for us too: direct read-only queries against our actual
prod DBs (`hoteru_tpm`, `hoteru_bwalk` on `db` `10.0.0.1`) confirmed **neither has a
`_prisma_migrations` table** — both are db-push-managed, with no day-of-week columns present.
Running `prisma migrate deploy` unbaselined would have tried to replay all 13 migrations against
tables that mostly already exist and failed partway through.

Fixed by baselining both tenant DBs before touching code: `prisma migrate resolve --applied` for
the 12 pre-day-of-week migrations (ledger-only, no SQL executed), confirmed absent columns
immediately before, confirmed `migrate status` clean after — then let the real
`prisma migrate deploy` apply only the 13th (real) migration for both DBs and central. Central's
own ledger already carried a resolved failure from `2026-07-25` for the old
`20260414_update_payments_table` (unrelated to this session, already fixed then) — the new
idempotency fix to that file is a no-op for us since `migrate deploy`/`migrate status` ignore
checksum drift on already-applied migrations (confirmed by the upstream commit's own testing, and
by our clean `migrate deploy` run).

## Verification

Standard health checks passed on all three (API `/health` 200, guest sites 200, management SPA 200,
central `hoteru.uk` 307 locale redirect as expected).

**`GET /api/rates/quote`** confirmed live and correct: central returns `taxRate: 0.11` with subtotal
from the active seasonal rate; Bwalk returns `taxRate: 0`.

**Server-authoritative totals — verified by a real booking round-trip, not status code**, on both
central and a tenant, deliberately sending a wrong client `totalAmount` to prove it's ignored:

| Instance | Client sent `totalAmount` | Server computed | Correct? |
| --- | --- | --- | --- |
| Central | `1` | `849150` (subtotal `765000` × 1.11 tax) | ✓ matches quote math exactly |
| Bwalk | `999999999` | `580000` (subtotal, 0% tax) | ✓ matches quote math exactly |

**Day-of-week priority — verified end-to-end** on central: created an open-ended (`endDate: null`)
weekend rate (`daysOfWeek: [5,6]`, i.e. Fri+Sat under the `0`=Sunday convention, `priority: 5`).
Quoted Fri–Mon: Fri and Sat both returned the new rate's price; Sunday correctly fell back to the
pre-existing "Low Season" rate (not in `[5,6]`) — confirms the day-of-week filter and priority
ordering both work against real data.

**Room CRUD — verified end-to-end** on central: created a room, `PATCH`'d its floor/notes, deleted
it (confirmed soft-delete: `isActive` flips to `false`, row otherwise intact) — matches the
documented behavior.

All test artifacts (2 bookings + their auto-created guests, 1 room, 1 seasonal rate) deleted after
verification, scoped to the exact IDs returned by each API call. Verified `count(*) = 0` for every
row across both DBs after cleanup — no residue.

PM2 logs on all 7 processes checked post-restart — no error spam, no restart loops, restart counts
unchanged since the deploy restart.
