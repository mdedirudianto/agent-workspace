## What drove this

24 commits had landed on `origin/main`: a real production bug fix for referral/affiliate
commission attribution, a Guest-record backfill for historical bookings, and a batch of
management-app UX fixes (pagination, notification bell, dialog scrolling, occupancy calendar).

**The attribution bug:** `bwalk.hoteru.co.id` and `technoparkmalang.hoteru.co.id` post
booking-create straight to a different host (`api.<tenant>.hoteru.co.id`). The `hoteru_ref`
referral cookie is host-only on the site's own origin, so it never reached the API cross-host —
every referred booking in production was silently losing its commission. Fix: each tenant site
now mounts a same-origin `/api/bookings` proxy route (`packages/hotel-ui/src/booking-proxy.ts` +
per-site route handlers) that forwards the cookie server-side; `createHotelClient.createBooking`
now posts there instead of straight to `apiBase`. Central's `demo.hoteru.uk` (`apps/public`) does
**not** use this shared client — it has its own `lib/api.ts` — so it's unaffected by both the bug
and the fix.

**The guest backfill:** until this range, `Booking.guestId` was only ever set via guest-portal
login — bookings taken from a tenant site or the management app left it null, so the management
Guests page under-reported. `pnpm --filter hoteru-backend db:backfill-guests` (idempotent, has
`--dry-run`) creates the missing `Guest` rows and recomputes stats from booking history.

## DB access note (new for this fleet)

Backups in prior sessions apparently SSH'd directly to `db`; that path isn't available from here —
`db.biji.uk:22` is unreachable from this network, and an `app`→`10.0.0.1:22` SSH hop has no
authorized key for any user tried. **Not needed anyway**: `app`'s own `apps/backend/.env` already
holds a working `DATABASE_URL` for each instance (that's how the live backend connects), so
`pg_dump` runs directly from `app` against `10.0.0.1:5432` over the existing connection, no SSH hop
to `db` required. Used this for all three backups below.
