### PaymentGateway migration conflict (confirmed, not hypothetical)

Migration `20260414_update_payments_table` does `CREATE TYPE "PaymentGateway"`, but that enum
and the `gateway`/`snapToken`/`expiresAt` columns on `payments` already existed on prod —
applied by an earlier out-of-band migration `20260101000000_add_payment_gateway`. Confirmed by
direct query before touching anything. `migrate deploy` hard-fails on this step; the fix is
`prisma migrate resolve --applied 20260414_update_payments_table` (bookkeeping only — the
columns were already correct, verified first). Dry-ran the exact sequence on a scratch DB
(`hoteru_migtest`) before doing it for real on prod; both runs behaved identically.

### Finding: the tenant DB has no migration history at all

`hoteru_tpm` has **no `_prisma_migrations` table** — its schema has only ever been synced with
`prisma db push`, never `prisma migrate`. Running `migrate status` reported all migrations as
"not applied," which was misleading: direct inspection showed `payments`, `hotels`,
`bookings`, and `commissions` already had most of this PR's columns (`gateway`/`snapToken`/
`expiresAt`, `slug`/`brandColor`/`logoUrl`, `promoCode`/`discountAmount`, nullable
`paymentId`) and an `affiliate_commission_rates` table already existed. Only `gallery_images`
and `room_types.beds`/`category`/`popular`/`size` were genuinely missing. `migrate deploy`
would have failed immediately trying to replay `CREATE TABLE`/`CREATE TYPE` for things that
already exist. Used `prisma migrate diff` to get the exact SQL first (confirmed additive-only:
one `ALTER TABLE room_types ADD COLUMN`, one `CREATE TABLE gallery_images` with an FK to
`hotels`), then applied with `prisma db push` — consistent with how this tenant has always been
schema-managed.

## Operational gotchas hit this session (worth knowing next time)

- **`hoteru` DB role lacks `CREATEDB`.** Creating the scratch DB for the central dry-run
  (`hoteru_migtest`) failed as the app role; had to create it as the `postgres` superuser via
  `root@db` (`sudo -u postgres createdb -O hoteru hoteru_migtest`), then drop it the same way
  after the dry-run.
- **`pm2 reload app1 app2 app3` only reloads the first name.** Confirmed empirically on both
  Part A and Part B — passing multiple app names to one `pm2 reload` call silently no-ops on
  everything after the first. Reload each process individually.
- **`devops@app` has no SSH trust to `proxy`** (neither `devops@proxy` nor direct key auth
  worked). Both management-SPA deploys (central and tenant) went **app → local machine →
  proxy** via `root@proxy`, same relay pattern session-001 used — this is evidently the
  standing mechanism, not a one-off. Fixed ownership to `www-data:www-data` after each push;
  excluded `mockServiceWorker.js` from the sync (dev-only MSW artifact, dropped per the
  precedent set in session-002's TPM deploy).

### Bug found and fixed during the booking-flow test: stale standalone static assets

Loading `demo.hoteru.uk` in a real browser (not just `curl -I`) surfaced 4 console 404s on
`_next/static/chunks/*.js`/`.css`. Root cause: Next.js standalone output does **not**
auto-copy `.next/static`/`public` into `.next/standalone/apps/<app>/` on build — this has to
be done manually after every build. The PR's migration guide only mentions this step for
Technopark, but it applies to **every** standalone app. I'd done it for the tenant's
Technopark build in Part B but missed it for central `apps/public` and `apps/marketing` in
Part A — their standalone dirs were still serving a single stale chunk from a much older
build while the fresh build sat unused. Checked `docs/deployment-prod.md`'s own redeploy
runbook — it never mentioned this step either, so anyone following it exactly would hit the
same bug.

**Fixed at the source, not just patched on the server.** Manually copied the assets and
reloaded `hoteru-public`/`hoteru-marketing` to unblock this session's smoke test, then went
back and added a `postbuild` script (`mkdir -p .../.next && cp -r .next/static .../.next/static
&& cp -r public .../public`, skipped for `marketing` which has no `public/` dir) to
`apps/public`, `apps/marketing`, and `apps/web/technopark`'s `package.json` so the copy
happens automatically on every `next build` from now on — no more relying on deploy docs or
memory. Committed and pushed to `biji-dev/hoteru` main (`124d070` → `d94e768`,
`fix(build): auto-copy static assets into Next standalone output`). Verified for real: pulled
the fix onto `app`, deleted the existing standalone static dir for `public`, rebuilt, confirmed
`postbuild` fired automatically and re-populated all 37 chunks + `public/` with zero manual
steps, reloaded PM2, and re-checked `demo.hoteru.uk` in browser — 0 console errors. This would
have shipped as a broken guest site (missing JS/CSS on every page) on the very next deploy if
the booking flow hadn't been tested in an actual browser first.
