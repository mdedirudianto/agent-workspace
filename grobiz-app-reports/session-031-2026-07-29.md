## Why this session

Three feature branches had landed on `main` since session-030 (which shipped zero-DDL QA fixes): a
self-service WhatsApp "Lupa PIN" reset (closing the only account-recovery gap in the app), a hard fix for
merchants stranding themselves mid-registration (the `8731f6bc` "ES TELER" incident from 2026-07-28), and
an admin customer-support surface (PIN reset, unlock, purge, audit trail) to give ops/support tools that
didn't exist before. All three shipped with their own deploy runbooks
(`docs/runbooks/2026-07-28-pin-reset-deploy.md`, `docs/runbooks/2026-07-29-stuck-registration-deploy.md`,
`docs/runbooks/2026-07-29-admin-cs-tooling-deploy.md`) — this session followed them, then ran a full
functional smoke pass rather than stopping at structural checks.

## 1. Pre-flight

- **`WEB_APP_URL` confirmed unset in prod `.env`.** The PIN-reset runbook's "the one that bites" — an
  unset value fails *silently* (merchants get an unopenable `localhost` reset link, zero errors anywhere).
  Added `WEB_APP_URL=https://app.gro.biz.id` before any reload.
- **Verified the new `core/security/config-guard.ts` FATAL gate was pre-existing, not new risk.** The diff
  only added one field (`webAppUrl`) to an already-live `checkProductionSecurityConfig()` call; the
  `ADMIN_ENFORCE_2FA` FATAL check it contains has been running successfully on `1a849bf7` since
  session-027. `ADMIN_ENFORCE_2FA` is unset in prod → resolves `true` → no boot risk. (Standing lesson from
  session-027's 7.5-min outage: a boot gate can live outside the zod schema — checked the whole path this
  time, not just `env.ts`.)
- **Ran migration 0028's own duplicate pre-check live:** 0 tenants with concurrent live `provision_new`
  jobs — the index will build clean.
- **Ran the stuck-registration runbook's own purge-preview query live:** exactly one row, `8731f6bc` (ES
  TELER), age ~27h (past the sweep's 24h purge cutoff). Per the runbook's explicit call, bumped its
  `updated_at` to `now()` **before** the reload, buying it a window instead of an instant, silent delete on
  the sweep's first run.

## 2. Deploy — the one ordering deviation

The stuck-registration runbook reverses the usual schema→code→data rule for migration `0028` specifically:
reload the API **first**, then apply the migration. Old code's `set-pin` inserts with no `ON CONFLICT`
guard, so building the unique index while old code still runs risks a bare constraint violation 500ing a
merchant mid-registration; the new code's `ensureProvisioningJob` tolerates the index landing after it.

Skipped `drizzle-kit push` entirely (standing risk: hangs non-interactively on a stale `feature_flags`
snapshot per session-004/028) — applied both migrations by hand instead, matching every prior release:

| Step | Result |
| --- | --- |
| `git pull` (49 commits) | `1a849bf7 → 3674b2a3` |
| `pnpm install --frozen-lockfile` | clean, lockfile unchanged |
| `pnpm build` | clean; shared+api+web+admin+landing (landing rebuilt for parity even though unchanged, per the guide's "don't skip static apps" rule) |
| `pm2 reload grobiz-api --update-env` | clean boot, api `0.14.0`, all 15 schedulers started incl. the new hourly sweep, **no `WEB_APP_URL` warning** |
| `pm2 startOrRestart … --only grobiz-admin,grobiz-landing --update-env` | both online |
| `psql -f apps/api/drizzle/0029_pin_reset_requests.sql` | table + 3 indexes created |
| `pnpm db:backfill` | 6 idempotent migrations replayed (incl. older ones); `0028`'s dedupe UPDATE affected 0 rows as predicted, unique index created |

Zero errors in the API log since reload. `/api/health` → `{postgres, redis, erpnext} = ok`.
`health-check.sh` FAILs on its local Postgres/Redis probes — the known pre-existing false-positive for this
split cluster (session-030), not new.

### 3.3 Admin CS tooling — via Playwright, incl. a temp `ops_admin` account

Logged in as `super_admin` (password provided by the user; TOTP entered live). Verified:

- `/provisioning` "Stranded registrations (1)" card shows **exactly** ES TELER and nothing else.
- Users tab on a tenant shows the **Reset PIN** button (not clicked — would have changed a canary's live PIN).
- **RBAC narrowing, both directions, both layers:**
  - Created a temporary `ops_admin` account via `POST /api/admin/users`, completed its forced first-login
    2FA enrollment entirely via API (the setup endpoint returns the raw TOTP secret; computed a valid code
    locally with a standard RFC 6238 implementation — no external device needed).
  - **API level:** `POST /api/admin/tenants/:id/purge` → **403** for `ops_admin`. `POST
    /api/admin/provisioning/:jobId/purge` → **403** (permission check fires before even a not-found lookup).
    `POST /api/admin/provisioning/:jobId/retry` → **404** (permission check *passes*, confirming retry
    stayed broader than purge, per the runbook's intent).
  - **UI level:** opened a second tab, injected the `ops_admin` session token — the entire **Danger zone**
    card is absent from Overview. Restored the `super_admin` token in the same tab — Danger zone reappears.
  - Deactivated the temp account afterward (`PUT /api/admin/users/:id {isActive:false}` — no delete
    endpoint exists by design).
- **Purge itself, exercised for real** against `05110a77` (now `active` after finishing provisioning):
  - First attempt → **409 `PURGE_STATUS_FORBIDDEN`** — active tenants can't be purged directly
    (`PURGEABLE_STATUSES = {failed, provisioning, pending_deletion, deleted}`). Correct, working guard, not
    a bug — see the ops note filed in the grobiz repo (§5).
  - Used **Actions → Mark for Deletion** (an audited, reversible transition) to move it to
    `pending_deletion`, then purged.
  - Confirm dialog matched the runbook exactly: type-to-confirm business name, **masked** phone
    (`62 8 ** *** **99` — the new `phone-mask.ts`), required reason.
  - Verified after: `tenants` and `provisioning_jobs` both 0 rows for `05110a77`; `audit_log` has both
    `tenant.purge_requested` and `tenant.purged`, correct actor/reason/target_id, exactly matching the
    documented two-row-with-`tenant_id`-NULL design.
