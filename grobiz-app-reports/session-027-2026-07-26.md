## Pre-flight — what the analysis found (and what it got wrong)

Four parallel research agents covered migrations, ERPNext backfills, live server state, and the order app.
The findings that changed the plan:

### 1. Prod's documented deploy mechanism would have silently skipped three migrations

`deployment-prod.md` §9/§14 prescribes `drizzle-kit push`. That diffs `schema.ts` against the live DB and
emits **DDL only** — it never reads the numbered `.sql` files, so the hand-written `UPDATE`s in `0014`,
`0015` and `0023` would never have run. Worse, `push` independently builds the same unique indexes from
`schema.ts`, so for `0015`/`0023` it would have hit the un-deduplicated data and **failed mid-run**.

Used manual `psql -1 -f` per file instead (the standing hard rule from session-022), never `push`.

Also confirmed: **no migration-tracking table exists on prod at all**, and `drizzle/meta/_journal.json` is
gitignored and frozen at `0005`. The numbered files are the only source of truth, applied by hand.

### 2. The three data-carrying migrations were pre-checked against real prod data

Rather than apply and hope, each was dry-queried first. Every prediction matched the actual result exactly:

| Migration | Predicted | Actual |
| --- | --- | --- |
| `0014` void→failed | 0 rows (none exist) | `UPDATE 0` |
| `0015` dedup unpaid | 1 row: `25726cc4` (Dipra Pastry, `max` Rp149k, Jul 13), superseded by their `starter` Rp49k of Jul 23; **no** `payment_transactions` attached | `UPDATE 1` |
| `0023` canonicalize phone | 7 rows `08…`→`62…`, **0 collisions** | `UPDATE 7` |

`0023` carries an in-file warning that its `CREATE UNIQUE INDEX` **fails outright** on collisions — and it
exists precisely because duplicate tenants from phone-format mismatches were a real bug. Prod was clean, but
that was verified, not assumed.

## ⚠️ Incident — 7.5 minute prod outage on the restart

`grobiz-api` crash-looped on boot:

> `Refusing to start: ADMIN_ENFORCE_2FA is disabled in production — mandatory admin 2FA enrollment is OFF,
> so a never-enrolled admin can sign in with a password alone.`

Prod had `ADMIN_ENFORCE_2FA=false`, set deliberately in session-003. A **new fail-closed boot gate** in
`apps/api/src/app.ts:75` refuses to start with it in production.

**Why the pre-flight missed it.** The env audit checked `apps/api/src/env.ts` — the zod schema — and
correctly found no newly-*required* vars, plus verified the new SEC-006 JWT-distinctness `superRefine` would
pass. **But this gate lives in `app.ts`'s `securityConfig`, not in the zod schema.** The check was scoped to
one file and reported "no boot-blocking env changes" with more confidence than the evidence supported.

**Resolution:** commented out `ADMIN_ENFORCE_2FA` (leaving an audit trail rather than deleting the line),
restarted. Service restored. Total outage **11:31:29 → 11:38:54 ≈ 7.5 min** — longer than the predicted
30–60s single-fork blip because of the loop while diagnosing and confirming the security decision with the
user. No merchants were active (confirmed with the user before proceeding).

**Consequence, accepted by the user:** mandatory admin TOTP enrollment is now **ON**. `admin@gro.biz.id` will
be prompted through enrollment on next admin-dashboard login — a supported flow, not a lockout. Merchant POS
was never affected by the setting itself.

**The generalisable lesson: a boot-time env contract is not only what the schema validates.** Grep the whole
boot path for `NODE_ENV === 'production'` guards, not just the env module.

## New surface: `order.gro.biz.id` is live

The diner PWA had **never existed on prod** — no DNS, no vhost, no cert entry, nothing on disk. 796 commits
brought `apps/order` from nothing to 0.2.1.

- **DNS** added by the user (Cloudflare-proxied, resolves identically to `app.gro.biz.id`).
- **Before this session `order.gro.biz.id` fell through the `*.gro.biz.id` wildcard to ERPNext**, which
  answered Frappe's *"order.gro.biz.id does not exist"*. An explicit `server_name` block now wins over it.
- **Served statically from `proxy`** (`/var/www/grobiz/order`), *not* `pm2 serve`. grobiz's own admin/landing
  use `pm2 serve` on `0.0.0.0:7016/7017` — publicly exposed on app's IP. Static-on-proxy matches the repo's
  own `order.conf` intent, the newer cluster convention (hoteru, meetgrab, eventopia-checkin), and avoids
  opening another public port for a **JWT-less** diner surface.
- Reuses the existing LE `*.gro.biz.id` cert (valid to 2026-09-22) — no new cert needed.
- `app→proxy` SSH is closed (good hygiene), so the build was relayed via the local machine.

**The bundle-host gate did its job.** `deployment/scripts/verify-bundle-host.sh` (added session-026 after the
wrong-host bug shipped to dev three times) passed: expected host present, forbidden dev host absent. It was
then re-checked twice more — once locally before pushing to proxy, and finally **against the bytes actually
served over HTTPS** (`app.gro.biz.id`: 1, `app.dev.gro.biz.id`: 0). Verifying the served artifact, not the
build output, is the whole point of that lesson.

Note: this build emits **no `sw.js`/`registerSW.js`** — the service-worker location blocks are present for
forward-compat but currently never match.

## Env changes

Only two vars added, both reasoned from the new `.env.example` audit (`619946bd`):

| Var | Why |
| --- | --- |
| `API_BASE_URL=https://api.gro.biz.id` | Builds the absolute Midtrans webhook notification URL. Prod sits behind the proxy, so the inbound host is internal (`10.0.0.5`) and the derive-from-request fallback would produce a wrong URL. Inert until Midtrans creds exist, but set now so it isn't a forgotten landmine. |
| `VITE_ORDER_BASE_URL=https://order.gro.biz.id` | Baked into printed dine-in QR codes at web build time. |

**`VITE_ORDER_BASE_URL` turned out not to be load-bearing** — `apps/web/src/lib/order-url.ts:19-21` derives
`order.<apex>` from the current host, which yields exactly the right value from `app.gro.biz.id`. Set it
explicitly anyway to remove the reliance. Verified in the compiled bundle: the minifier constant-folded it to
`function wse(){return"https://order.gro.biz.id".replace(/\/+$/,"")}`, with **zero** `localhost:4715` residue.

**`VITE_API_URL` deliberately left unset** in the root `.env` — setting it there would break the web SPA's
same-origin build. The order app receives it inline at build time only.

## Two deliberate deferrals

**Midtrans stays off** (user's call — production keys not yet available). Verified this degrades safely
rather than breaking: `isMidtransMockEnabled()` and `shouldMockQrisCharge()` both hard-return `false` when
`NODE_ENV === 'production'`, so the mock is structurally unreachable; and `isDynamicQrisAvailable()` gates on
a server key being present, so with none set the diner is simply never offered the QRIS button. The order app
ships with **pay-at-cashier + static-QRIS-hint** only. No real-money path exists on prod.

**`CORS_ORIGINS` stays unset** — and this **reverses the deployment guide's instruction**. The guide says to
set it for the order app, but reading `app.ts:100`, unset means `origin: true` (reflect any), so the order
app works either way. Setting it would *tighten* CORS and risk two silent breakages:

1. The landing page at `gro.biz.id` fetches `https://api.gro.biz.id/api/public/plans` — **genuinely
   cross-origin**. The guide's suggested value (`app` + `order` only) would have silently dropped live
   pricing to the hardcoded fallback.
2. The Chrome extension sends a `chrome-extension://<id>` origin whose ID can't be determined from here.

This is a pre-existing condition, not something this deploy introduced. **Verified post-deploy** that the
landing fetch still works: `Origin: https://gro.biz.id` → `access-control-allow-origin: https://gro.biz.id`,
real plan JSON returned. Left as a follow-up to harden properly with every origin enumerated.

## SEC-013/015 cleanup

| Item | Scope | Result |
| --- | --- | --- |
| SEC-013 plaintext owner PINs | 7 exact `provisioning_jobs` IDs, all `completed` | `UPDATE 7`, residue **0** |
| SEC-015 pool superuser creds | 6 exact **claimed** `site_name`s | `UPDATE 6` |

`UPDATE`s only, never `DELETE`. Row counts verified unchanged (7 and 9).

**The load-bearing exclusion: the 3 `available` pool rows kept their credentials.** They're unclaimed and
`claimPoolSite` returns `null` without them — nulling those would silently break signup by forcing every new
tenant down the slow on-demand build path. The `IN (...)` list excluded them explicitly rather than trusting
the `status` filter, and a post-check asserted all 3 still hold creds.

The scrub also encodes the code's own safety invariant in SQL (`AND EXISTS (… provisioning_jobs … 'completed')`)
rather than assuming it: `provision-tenant.ts:452` documents that a *pre*-completion retry re-reads these
creds, so scrubbing early would force a retry to drop and recreate the live site.

### 🐛 A real bug found by the smoke test: PIN login is phone-format sensitive

Chasing a `401 Nomor telepon atau PIN salah` seen in the post-deploy logs, I checked whether `0023` had
broken login. **It had not** — `0023` only rewrote `tenants.owner_phone`; login reads `users.phone`, which it
never touched. But the two columns have now permanently diverged:

| Column | Format | Used by |
| --- | --- | --- |
| `tenants.owner_phone` | `6285748524448` (canonical, UNIQUE) | WhatsApp routing |
| `users.phone` | `085748524448` (**raw as typed**) | **PIN login**, exact match, no canonicalization |

**Confirmed empirically** on the canary (an account we own — deliberately not probed against a real
merchant, since `PIN_LOGIN_PHONE_LOCK_THRESHOLD` is 10 failures / 15 min and the gate's `normalizePhone`
only trims whitespace, so `08…` and `62…` burn separate budgets):

| Same account, same correct PIN | Result |
| --- | --- |
| `081999900001` | **200 login OK** |
| `6281999900001` | **401** |
| `+6281999900001` | **401** |

`registerStartSchema` explicitly accepts all three formats, so a merchant can register one way and be unable
to log in another — and the error blames the PIN. This is the exact SEC-014 bug class `0023` was raised to
fix; it fixed tenant/WhatsApp routing and left the login path. Filed for the dev agent.

### Three gotchas worth recording

1. **Provisioning is enqueued by `set-pin`, not `register/complete`** — the latter returns
   `status:"provisioning"` but creates no job row (deliberate, so the user sees live progress). Polling before
   set-pin waits forever.
2. **On F&B, `POST /api/products` does not create a menu item** — it creates an ingredient with
   `is_sales_item: 0`, which the diner menu deliberately excludes. F&B menu items go via `POST /api/menu`.
3. **An invalid `item_group` returns a bare `{"message":"Data tidak valid"}`** naming no field, while genuine
