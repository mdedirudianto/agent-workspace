## ⚠️ Incident — `drizzle-kit push` hung for 10 minutes on a known standing footgun

`bash deployment/pm2/scripts/deploy.sh` (the now-recommended full deploy path) got through pull → install →
build (all 6 apps, ~90s) cleanly, then hung at step 4 (`drizzle-kit push`) until my Bash tool's 10-minute
timeout killed the *local* SSH client — the *remote* `deploy.sh` + `drizzle-kit push` chain kept running on
the server, orphaned.

**Root cause:** this is the exact footgun the grobiz-app-reports README has flagged as an open follow-up
since session-004 — `drizzle-kit push` interactively prompts to truncate `feature_flags` before adding
`feature_flags_unique_idx`. Checked live: **that constraint already exists** on the table, byte-identical to
`schema.ts`. `push` diffs against its own local migration-journal snapshot (`drizzle/meta/_journal.json`),
which has been stale at `0005` for a long time — so it keeps re-proposing an already-applied change forever,
regardless of actual DB state. Confirmed **zero `schema.ts` changes ship in this entire release**, so `push`
had nothing legitimate to do here at all.

**Recovery:** confirmed nothing had been applied (PM2 still old version, health still fine, the constraint
already present) — safe to kill the hung process chain. Completed the remaining deploy.sh steps by hand,
since the builds had already succeeded and nothing was lost: `pm2 reload grobiz-api` → reconcile
admin/landing from the ecosystem file with `--update-env` → `pm2 save` → `pnpm db:backfill`. The last step is
what actually applies data migrations (`sql.unsafe()` directly via postgres.js, never touching drizzle-kit),
which is why it's immune to this whole class of problem.

**A second, unrelated finding surfaced by the dry-run:** `0007_feature_flags_nulls_not_distinct.sql` —
`db:backfill`'s `DATA_MIGRATIONS` list — had apparently **never been applied to prod**, despite predating
this release by months. It landed cleanly in the same `db:backfill` run alongside `0027`.

**Standing follow-up flagged in the runbook, not blocking:** `deploy.sh` should skip `drizzle-kit push`
outright when a diff check shows no `schema/` changes between the previous and new commit, since a
schema-unchanged release has no reason to invoke a tool with a known-hung interactive path.

## Two more script bugs found running the smoke test for the first time against real production

The smoke test had never been run before — it was written against an *assumed* API response shape rather
than one confirmed live. Running it surfaced two more defects (beyond the `item_group` one from pre-flight),
both fixed and pushed the same session:

- **Invoice extraction** (`6213f2e8`'s partner, actually caught running the test): `POST /api/sales` returns
  `{"sale":{"id":..., "invoice_name":...}, "receipt":{...}}` — no top-level `data`. The script's
  `.data.invoice_number // .data.name // .invoice_number` matched nothing, so a **successfully booked sale**
  (confirmed independently — stock correctly went 50→48) reported as `FAIL: Sales Invoice booked — empty`.
- **Three F&B jq paths** made the same `{data:...}` assumption against endpoints that don't use it:
  `GET /public/order/menu` returns `{"items":[...]}`, `GET /api/orders?status=incoming` returns
  `{"orders":[...]}`, and `GET /api/tables` returns a **bare array** with no wrapper at all — the last of
  which threw a hard jq error (`Cannot index array with string "data"`) rather than a clean assertion
  failure.

Fixed both, each time by hitting the real endpoint directly first to confirm the actual shape before touching
the script — same discipline as the `item_group` fix. Both `--profile retail` and `--profile fnb` then passed
clean, 15/15 and equivalent assertions, against the two canary tenants (`d6f28680`, `f4c91773`) — reactivated
before each run, re-suspended after (tenant count unchanged, 9, before and after).
