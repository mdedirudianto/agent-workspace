## 2. Pre-flight the owner's decision required — closed before touching anything

The owner asked explicitly for `PAYMENT_GATEWAY=xendit`, reversing the prior plan's
recommendation to hold it at `midtrans`. Before executing that, the one real correctness
question — CR-013 M5's standing precondition — was checked rather than assumed:

**Is any tenant's configured QRIS fee at or below Xendit's 0.777% MDR?** A fee at or below the
MDR books a loss per transaction. Queried directly:

```sql
SELECT tenant_id FROM tenants WHERE settings ? 'qrisFeeSettings';   -- 0 rows
```

**Zero tenants carry a per-tenant override.** All 23 run the global default —
`{"type":"percent","value":0.8}` — verified in `platform_config`, which is 0.023% above the
Xendit MDR (~Rp 23 margin on a Rp 100.000 sale). Thin, previously flagged, and the owner's
explicit call to proceed regardless. With the audit clean, there was no correctness reason to
withhold the cutover.

## 4. Verification — proven with a real Xendit charge, not just structure

**All four surfaces + boot log clean.** `/health` → postgres/redis/erpnext all `ok`; app/admin/
order/landing all `200`. The boot log's `"QRIS refund confirmation sweep started (every 2 min)"`
line confirms the new job registered; there is no `PAYMENT_GATEWAY=xendit` warning anywhere in
the log, meaning the guard was satisfied silently rather than degraded.

**Existing anchors provably untouched.** All 15 pre-existing `dine_in_order_payments` rows still
read `gateway_provider: midtrans`, `refund_status: NULL` — exactly as before the cutover. This is
D2's design (the provider is captured on the anchor at creation and never re-read from env)
proven on real data rather than assumed.

**A real charge was minted on the retail canary (`d6f28680`) and it worked end to end:**

| | |
|---|---|
| Invoice | `ACC-SINV-2026-00040` |
| Item | a real product, Rp 23.456 |
| Xendit charge | `qr_dd54a83a-0be2-4399-b988-fd044c33dd9e` — a genuine QRIS code, encoded to PT BIJI INOVASI GRUP, Malang |
| **Anchor `gateway_provider`** | **`xendit`** — captured at creation, confirmed in Postgres |
| Provider mix after | **15 midtrans / 1 xendit** |

**Then the draft was cancelled to leave nothing dangling — which also exercised the
Xendit-specific cancel-on-pending path** (`POST /api/orders/:id/cancel`, owner role required for
a pending QRIS cancel):

```
"orderId":"pos-f56650af...","provider":"xendit","msg":"QRIS charge voided locally —
provider has no cancel verb; the QR expires"
```

That log line is a byte-for-byte match for the documented design (§9 of CR-013's engineering
note): Xendit has no void verb, so the route never calls one — it closes the ledger door locally
(`markFailed('void')`) and lets the QR expire on its own. Final anchor state: `payment_status:
void`. **Zero flags raised.** The API response was `{"cancelled":true}`.

**What was deliberately NOT tested with real money:** a paid-then-refunded round trip. That would
require either scanning a live QR with real funds or Xendit's sandbox-only `/payments/simulate`
endpoint, which does not exist against the production API. The refund code path is live
(`XENDIT_REFUND_IMPLEMENTED: true`, the sweep job registered, the async refund flow documented
and unit/integration-tested pre-merge) but has not yet processed a real refund in production.
Recorded as the honest boundary of this pass rather than silently assumed.

## 6. Follow-ups carried from this session

- [ ] **A real paid-then-refunded Xendit QRIS cycle has not been proven in production.** The
  code path, the sweep, and the async confirmation are all live and pre-tested, but the first
  live refund will be the first real exercise of `jobs/qris-refund-sweep.ts` against production
  traffic. Worth a deliberate, small, real test the next time a genuine refund is needed — or a
  small owner-initiated one if that is preferred sooner.
- [ ] **The 0.023% fee margin (0.8% platform fee vs 0.777% Xendit MDR) is thin and was flagged,
  not fixed** — the owner's stated intent is to revisit the platform fee separately. Nothing
  blocks on this; it is a live economic fact from the moment of this cutover.
- [ ] **`PAYOUT_GATEWAY=xendit` remains configured and unexercised.** The Rp 2.775 flat
  disbursement fee (measured in CR-013 at 6 real disbursements) means a payout only breaks even
  around Rp 383.800 — worth a minimum-payout-threshold decision before the first real batch runs.
  Carried forward from session-039; still open.
- [ ] **The transient 502 immediately after the P5 restart is unexplained beyond "proxy caught
  the brief window"** — it self-resolved within seconds and left no trace, but if it recurs on a
  future `grobiz-api` restart it is worth checking whether nginx's health-check interval or
  keepalive timeout is too aggressive for this app's restart time.
- [ ] **`backfill:payment-channels` was only dry-run** (1 row, xendit, readable). Running it for
  real is a one-line, low-risk write whenever convenient — not done here because the approved
  plan scoped it to dry-run only.
