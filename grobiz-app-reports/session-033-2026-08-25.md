## Why this session

A change request (CR-008) proposed a loyalty **tier ladder** — Member → Silver → Gold, climbed by spend,
carrying an earn-rate bonus, an automatic discount and merchant-defined perks. Before building it, the CR
named a gate: measure how many customers could actually stand on such a ladder. This session took that
measurement, first on dev and then on production.

The answer stopped the feature. It also turned up one genuine ERPNext defect and one live configuration
gap that are worth keeping regardless.

## 1. What was measured

Two multipliers decide the addressable population, and the CR's first draft named only the first:

- **attach rate** — share of submitted invoices carrying a real customer rather than the `Pelanggan Umum`
  walk-in placeholder.
- **enrolment** — of customers who have actually bought, the share enrolled in the tenant's loyalty
  programme.

Method on production: read-only SQL against MariaDB on `db` (one query per per-tenant ERPNext database)
plus the tenant registry from Postgres. **The purpose-built script was deliberately not used** — prod runs
`2aafd740` and the script imports `DEFAULT_CUSTOMER_NAME`, which did not exist on that SHA, so running it
would have meant deploying code in order to take a measurement.

## 3. Findings — dev, for contrast

Dev suggested 10–15 enrolled customers per tenant (`demofnb002` 10 of 47, `demoret002` 15 of 60), attach
rate 22–75 %. That looked thin. Production is roughly twenty times thinner again, and the dev figures are
seeded data describing the demo seeder rather than any merchant.

## 4. Two things worth keeping regardless of the feature

**ERPNext's own tier metric is unusable, and it was measured, not assumed.** `Loyalty Program` assigns a
tier from `SUM(Loyalty Point Entry.purchase_amount)`, which is (a) lifetime, (b) recomputed only on invoice
submit so a tier can never fall, and (c) **inflated by redemption** — `apply_loyalty_points` writes each
redemption row with `purchase_amount = grand_total`, positive. Measured on dev: two Rp 100 000 invoices with
one 50-point redemption report `total_spent` **250 000** against 200 000 of real sales. Redeeming advances
your tier. Anything that ever reads that field inherits this.

**`auto_opt_in` is off everywhere, and it is a one-switch fix.** ERPNext enrols customers inside
`Customer.validate()` → `set_loyalty_program()`, so with the switch on every new customer joins with no code
from us. It is provisioned `0` and the settings page exposed it as an unexplained toggle. It fires only on
**save**, so existing customers are never enrolled without a backfill.

`Cafe Bahagia` is that gap in isolation, live: both switches on, three customers, zero enrolled, because all
three predate the setting.

## 5. Side finding — production is 14 days behind `main`, and the recorded SHA was wrong

**The recorded SHA was wrong by 127 commits.** The Operations README had prod at `2aafd740` (session-032,
2026-08-04); `ssh devops@app 'cd ~/grobiz && git log -1'` says **`b277abb6`, 2026-08-11**, api `0.26.2`. A
deploy happened and no session was filed, so the gap is 409 commits rather than the 536 the record implied.
Session-032 made this same point about repo docs; it applies to our own notes. Ground truth is the host.

`main` is at `46a644c5` and the gap includes CR-007 (merchant promotions, shipped and live-verified), the
CR-006 order-queue and storefront work, the kitchen board and tables redesigns, and the
loyalty-redemption-at-checkout branch — including a **money defect fix** where redeeming against a prepaid
order produced cash change that was never handed over.

**Not deployed this session** (read-only scope), but the ordered plan is now written and committed to the
repo: `docs/runbooks/2026-08-25-prod-catchup-deploy.md` (branch `docs/prod-catchup-deploy`, commit
`56cb60b0`). What it establishes that was not obvious:

- **`pnpm backfill:shop-fields` is not in `deploy.sh` and its ordering is load-bearing.** It creates the
  ERPNext Custom Fields the new API both filters and selects, and v16 hard-fails a `getList` naming an
  unknown field — so an un-backfilled tenant gets a Pesanan queue that 400s and, if F&B, a kitchen board
  that 400s on `custom_service_mode`. It must run from the newly built code BEFORE the API reload, and
  zero failures is a gate. (`deploy.sh` step 5c runs a different thing — `db:backfill`, the SQL
  `DATA_MIGRATIONS` replay — and correctly runs it after.)
- **Nine new migrations (`0031`, `0033`–`0040`), all verified DDL-only**, so none belongs in
  `DATA_MIGRATIONS` and none is listed there. `0032`'s absence is a deliberate renumber off a `0031`
  collision (`9747e079`), not a lost file. All seven new tables are registered in **both**
  `drizzle.config.ts` and the schema barrel — worth re-checking every deploy, since a missing config entry
  is silently absent in production.
- **Ten env vars are absent.** Two of them stop the new `grobiz-wa-gateway` process booting, deliberately.
  `SHOP_BASE_DOMAIN` fails **closed and silently** — CORS emits no wildcard and the storefront renders its
  shell with an empty catalogue and no error anywhere.
- **`WA_SESSION_PATH` must be a persistent, backed-up volume before the first merchant pairs.** Baileys
  credentials have no re-issue and no reset link; losing them means every paired merchant re-scans a QR.
- **Risk posture:** with 161 lifetime invoices (§2), downtime is cheap and data loss is not. The runbook
  names the three things that can actually destroy data — a `drizzle-kit push` proposing a DROP, that
  session volume, and the fact that `deployment/scripts/backup.sh` is still broken for this split-cluster
  topology (session-032) — and recommends shipping both new public surfaces dark.

## 7. Repo work (branch `docs/cr-008-loyalty-tiering`, not merged)

Shipped as M0, useful whether or not tiering is ever built:

- `pnpm measure:loyalty-base` — read-only measurement script, safe against production once prod catches up
  to a SHA that has `DEFAULT_CUSTOMER_NAME`.
- `pnpm backfill:loyalty-enrolment` — enrols existing customers, gated on **both** `auto_opt_in = 1` and
  `loyaltyEnabled = true`. The second gate is load-bearing: `Sales Invoice.loyalty_program` carries
  `fetch_from: customer.loyalty_program`, so enrolling a customer starts real point accrual whether or not
  GroBiz's own switch is on. Proven on dev `demofnb002` (10 → 22 enrolled, `Pelanggan Umum` excluded,
  `loyalty_program_tier` untouched, re-run a no-op).
- The `auto_opt_in` control moved above the point rules with copy that says what it does and that it reaches
  **new** customers only.
