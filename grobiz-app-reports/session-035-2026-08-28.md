## 1. The `drizzle-kit push` hang — diagnosed, not worked around (open since session-004)

Three session reports (032, 033, 034) recorded this as a false positive on `feature_flags_unique_idx`
and left it there. The actual cause was found this session by reproducing it against a copy of
production's own schema:

**drizzle-kit cannot round-trip `unique().nullsNotDistinct()`.** It re-proposes that constraint on
*every* run, on 0.31.9 **and** 0.31.10 (tested; no upstream fix in the 0.31.x line). Proof: deleting
`.nullsNotDistinct()` from the schema makes push a clean no-op against the identical database — and
that is emphatically **not** the fix, because the flag is the entire point of migration `0007`.

The reason nobody saw it in dev or CI: **drizzle only offers to truncate a table that has ROWS.** An
empty database is silently re-issued the same DDL with no prompt. A restored prod schema with zero
rows reproduced nothing; inserting five `feature_flags` rows reproduced it exactly.

Prod's constraint was also confirmed byte-identical to what push itself builds
(`UNIQUE NULLS NOT DISTINCT (key, scope, scope_value)`), so there was never any real drift to fix.

**Fix:** deploy step 4 now runs `pnpm db:apply-sql` — the numbered SQL, which is what every real
deploy already did by hand with `psql -1 -f` — with `< /dev/null` and a `timeout`, gated by
`db:check-drift` before and after. The `< /dev/null` is the load-bearing part: it makes any *future*
prompt fail fast rather than hang a deploy forever.

### The correction that stopped this becoming an outage

The obvious next step — "prod applies the numbered SQL, so drop push" — is **wrong**, and measuring
it is what caught it: **28 of the 47 live tables are created by no numbered migration at all**
(`subscriptions`, `invoices`, `plans`, `whatsapp_*`, …). They exist only because push built them
incrementally over a year. A from-empty rebuild from `drizzle/` fails on `0001` with
`relation "subscriptions" does not exist`.

So push remains the **constructor** (dev + all four CI jobs, which build from an empty service
container and cannot hit the prompt) and the numbered SQL is the **evolution** (prod only). The new
seam is guarded by `pnpm db:check-migration-coverage`, in CI: a table in `schema.ts` with no
numbered `.sql` would otherwise be silently absent in production, with no build error, no deploy
error, and a 500 from one route as the first symptom.

A second correction, found by reading the files rather than grepping them: only **`0014` and
`0027`** may be deferred past the code reload, not three. A grep for a leading `UPDATE` misses
`0007`/`0027` (statements inside `DO $$`) and wrongly flags `0023`, which really does create
`tenants_owner_phone_idx` — and cannot be split, since its `CREATE UNIQUE INDEX` is only correct
after its own UPDATE. Deferring any of the four DDL-carrying files would have failed the post-apply
drift gate on a perfectly healthy database.

## 4. The health gate meant nothing, and now does

`HEALTH_URL` was unset on prod, so `deploy.sh` passed its `http://localhost` default on **every**
deploy — the four false FAILs were the normal outcome, and `HEALTH_OK=false` had become noise on the
one gate meant to catch a bad deploy. It has been re-diagnosed from scratch in four separate
sessions (028, 030, 032, 034).

It now defaults from `WEB_APP_URL`, and `health-check.sh` **refuses** a bare localhost / bind-IP
origin with one clear message (exit 2) rather than emitting four confident wrong failures.

This deploy's own health check: **14 of 16 OK**, including API, web app, bundle and PWA — all four of
which used to fail. The two remaining FAILs are the standing local-`localhost` Postgres/Redis probe
false positive (documented since session-028); the API's own `/health` reports both `ok`.

## 5. CORS closed — session-027's own follow-up, finally enumerated

Production had been reflecting **any** origin since forever:

```
$ curl -I -H "Origin: https://evil.example.com" https://app.gro.biz.id/api/health
access-control-allow-origin: https://evil.example.com
```

This was **deliberate** in session-027, not an oversight — it named the two origins a naive
allowlist breaks and closed with *"left as a follow-up to harden properly with every origin
enumerated."* That enumeration was done this session, from the code rather than from memory:

- `order.gro.biz.id` → `app.gro.biz.id` — genuinely cross-origin, baked into `apps/order/.env.production`
- `gro.biz.id` / `www.gro.biz.id` → `api.gro.biz.id` — the landing page's plans fetch
- `app.` and `admin.` are **same-origin** (no absolute API URL configured in either) — listed anyway as defence
- **The Chrome extension is deliberately NOT listed.** Its `dist/manifest.json` has no `key`, so it
  has no stable extension id and cannot be allowlisted at all; no CI job builds or publishes it, and
  its `host_permissions` still name `http://localhost:4000/*`. It is an unpacked dev build.

Verified after the deploy — hostile origin gets **no** `access-control-allow-origin` header, all five
first-party origins are echoed, the landing plans fetch returns **4 real plans** (free/starter/growth/max,
not the hardcoded fallback), and `order.gro.biz.id` still loads at 200 with its CORS header intact.

Note for whoever picks up the shop: **with `CORS_ORIGINS` unset, `SHOP_BASE_DOMAIN` had no effect on
CORS at all**, because the matcher is never installed. That is now unblocked.

## 6. Geocoding — the documented fix would not have worked

Session-034 left `MAP_GEOCODE_URL` on public Nominatim because "the code only parses a Nominatim-shaped
(`display_name`) or Geoapify-shaped (`formatted`) response". **Measured against the live APIs, no
provider returns a top-level `formatted` at all:**

| Provider | Where the label actually is |
| --- | --- |
| Nominatim | `display_name` (top level) |
| Geoapify `format=json` | `results[0].formatted` |
| Geoapify geojson | `features[0].properties.formatted` |
| Mapbox v5 / MapTiler | `features[0].place_name` |
| Mapbox v6 | `features[0].properties.full_address` |

So switching to Geoapify — the fix named in the follow-up doc, the CR **and** the runbook — would
have produced a 200 parsing to nothing, on every request, forever, and been **invisible**: "no label"
renders as bare coordinates, exactly like a pin in the middle of a field. Nothing logs, nothing errors.

`reverse-geocode.ts` now carries the measured path list, warns once on a 200 with no recognised
label, and has one test per shape. Verified end to end through `reverseGeocode` itself against all
three live providers, then again **from prod's own egress** after the deploy: the URL survives
dotenv intact (`&` and both placeholders) and returns
`"Zodiak Sutami Bandung, Bandung 40111, JR, Indonesia"`.

## 7. Online-shop routing → CR-009

Session-034's finding was confirmed exactly (`randomslugtest123.gro.biz.id` returns Frappe's own
*"site does not exist"*). Four things it did not have:

- **`shop.conf` was never deployable anyway** — still says `yourdomain.com`, and names
  `cloudflare-origin.key`, a path no other vhost uses (all three others are `cloudflare-origin-key.pem`),
  so `nginx -t` would fail on a missing key regardless.
- **The `map`/njs option is narrower than it looked.** The proxy is stock nginx 1.24 with only
  `--with-http_perl_module`, and it is **shared with ~30 unrelated apps** — adding a module has a
  blast radius far past this feature.
- **The nested-zone option is not free.** `foo.shop.gro.biz.id` fails TLS handshake **at Cloudflare's
  edge** today; the origin cert covers `*.gro.biz.id` and `gro.biz.id` only. It needs Advanced
  Certificate Manager plus a new origin cert.
- **A collision hazard neither option addressed.** `tenantId` is `randomUUID().slice(0, 8)` and
  `site_name` is `<tenantId>.<domain>`, so prod rows are `f4c91773.gro.biz.id` — and `shopSlugSchema`
  **accepts `f4c91773` today**. Under any exact-`server_name` scheme that slug beats the wildcard and
  steals another tenant's ERPNext desk. It runs in reverse too: signup mints a random tenantId and
  never consults `shop_slug`. **0 of 18 tenants have claimed a slug**, so this is still a clean slate.

Written up with three costed options in `docs/change-requests/CR-009-shop-storefront-routing.md`.
The gate is a certificate cost/security decision, not an engineering one. A third option is now on
the table that neither follow-up doc had: **nest ERPNext at `*.erp.gro.biz.id`**, freeing
`*.gro.biz.id` for shops — it deletes the sync machinery entirely and kills the collision class by
separating namespaces. `ERPNEXT_BASE_DOMAIN` is already a single env var and `renameSite` is already
exercised on every pool-claimed provision, but it needs a cert, 18 site renames, and a fix to
`site-teardown.ts:42` (which protects `erp.${baseDomain}` and would silently compute
`erp.erp.gro.biz.id`).

`shop.conf` is marked non-functional; the guide's DNS/nginx sections now warn instead of instructing.
