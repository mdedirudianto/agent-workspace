## Pre-flight analysis (drove the plan)

- **DB migrations: 2 new, both additive/idempotent, no data backfill.**
  - `0025_broadcast_recipient_claim.sql` — nullable `broadcast_recipients.claimed_at`. Fixes a real bug: the WhatsApp broadcast worker claimed pending recipients with a plain `SELECT`, so two concurrent workers (or an overlapping rolling deploy) could both dispatch the same recipient — every recipient got the WhatsApp message twice. Now atomically claims via `pending → sending` + `FOR UPDATE SKIP LOCKED`, with a stale-claim reaper (`sending` → `failed` if a worker dies mid-batch, deliberately not retried — a duplicate WA send is unrecoverable, an under-delivery is human-fixable).
  - `0026_users_email.sql` — nullable `users.email`, backing a new self-service `/settings/profile` email field. `phone` stays the immutable auth identity (the new `PUT /api/auth/profile` explicitly rejects a `phone` field rather than silently stripping it).
- **No ERPNext doctype changes at all** — zero diff under `apps/api/src/core/erpnext/`.
- **Env: no new required vars** — `.env.example` diff is empty.
- **Deps:** trivial — `@playwright/test` added as an `apps/order` devDep (e2e-only), root `package.json` gains a `db:backfill` script.
