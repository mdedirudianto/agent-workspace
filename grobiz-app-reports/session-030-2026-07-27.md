## 1. `ERPNEXT_CRED_ENC_KEY` — the pre-flight that changed a decision

The plan originally made a missing key a **boot FATAL**, arguing that a silently-off security control is
the exact failure shape this whole QA pass was about. That reasoning rested on "if the key were unset we
would already know, because its consumers throw." **That premise is false**: `core/auth/owner-pin.ts:29-40`
catches the missing-key throw and falls back to storing the owner's PIN in plaintext, by design and with a
comment saying so. So the third consumer degrades with **zero signal**, and there was no evidence either
way about production — a boot refusal would have bet the API's availability on a guess.

Checked before deploying, and the answer settles it:

```
ERPNEXT_CRED_ENC_KEY: SET       (decodes to exactly 32 bytes)
```

Set in **session-011** on both prod and dev, and still correct. Two consequences: W3's encryption really
encrypts, and owner PINs were **never** plaintext on this deployment. The guard shipped as a WARN anyway —
correct for the general case, and it can be promoted to FATAL now that the key is confirmed. It did not
fire at boot, which is itself the confirmation.

## 2. No migration, and `drizzle-kit push` deliberately skipped

`deploy.sh` step 4 runs `drizzle-kit push`, which has hung on the stale `feature_flags_unique_idx`
snapshot since session-004 and cost session-028 ten minutes. This release ships **zero DDL**:

- The only `db/schema/` change is `subscriptions.ts`, and it is **type-only** — `fromPlan`/`toPlan` added to
  the `PlanOverrideRecord` TypeScript interface. `planOverride` is already `jsonb`, so there is nothing to
  migrate.
- No files added under `apps/api/drizzle/`.

So the deploy was run **by hand** — pull → install → build → reload → ecosystem reconcile → `pm2 save` →
health check — skipping step 4 entirely rather than starting it and killing it. Note the fix proposed in
session-028 (skip push when `git diff --quiet -- apps/api/src/db/schema/` is empty) **would not have helped
here**: that directory did change, just not in a way that produces DDL.

## 4. Verified on production, per defect

Every check below ran against the live system. The two canaries were the only tenants touched, and both
are back to `suspended`/`free`.

### W1 — the headline fix

A **failed** first attempt produced a better reproduction than the one I planned. Calling
`changeTenantStatus` with a placeholder admin UUID hit the `tenant_lifecycle_events` FK **after** the status
write and **before** the invalidation — leaving Postgres saying `active` while the cache still said
`suspended`. That is precisely the defect:

| Step                                                        | Result                                             |
| ----------------------------------------------------------- | -------------------------------------------------- |
| DB `active`, cache stale at TTL **783**                     | `GET /api/products` → **403 TENANT_SUSPENDED**      |
| `DEL tenant:d6f28680:config` (the key the fixed code drops) | redis → `1`                                        |
| same request, immediately, **same TTL window**              | → **200**                                          |

Then the real path, end to end, with a real admin id:

```
before : key TTL = 877
change : {"ok":true,"fromStatus":"active","toStatus":"suspended"}
after  : key TTL = -2        <- the function itself dropped it. This is the fix.
GET /api/products -> 403     <- enforcement immediate, was up to 15 min
```

Pre-fix that TTL would have read ~875, unchanged, because the code deleted `tenant:<id>` and
`tenant:<id>:subscription`. Live Redis confirms only `tenant:d6f28680:config` has ever existed.

**The measurement trap was avoided deliberately.** Session-029's first attempt at this A/B was inconclusive
because ~15 min elapsed and the entry aged out on its own TTL, giving a 200 that looks like a pass and
proves nothing. Every step above ran inside one window with the TTL read out at each stage.

### W2 — suspension

```
login  -> suspended: True   user.tenantStatus: suspended
403    -> {"code":"TENANT_SUSPENDED","message":"Akun ditangguhkan. …"}
```

All three are new. `suspended` has been sent by the API since COR-031 and **nothing ever read it**;
`tenantStatus` is the field every client now locks on; and the `code` is what lets a client branch on
something other than an Indonesian sentence. The served web bundle contains `tenantStatus` and
`TENANT_SUSPENDED`, so this is the artifact, not just the build.

The retail canary is parked `tenants.status=suspended` + `subscriptions.status=trialing` — i.e. exactly the
divergent state where the API 403s everything while the old lock never rendered.

### W3 — TOTP at rest

```
stored looksEncrypted : true          (86 chars, envelope format, was base32)
decrypts to base32    : true - len 32
verifyTotp(decrypted) : true          <- exactly routes/admin/auth.ts:225. Admin login works.
verifyTotp(RAW blob)  : threw TypeError <- a DB read alone is no longer a second factor
```

The last line is the security goal, demonstrated rather than asserted. The first three are the safety
property: this is the one change that could have locked the single super-admin out of the dashboard.

### W4 — plan-override expiry

Production has exactly one override, and it belongs to a **real merchant**:

```
d132982a | Telaga Shanaya Restaurant | growth | {"reason":"client bu yulia", …, "expiresAt": null}
```

`expiresAt` is null — a permanent comp. The new job's predicate selects **0 rows**, so the 02:00 UTC run
will not touch it. Verified the predicate actually works rather than trusting the zero: a past date matches,
a null is ignored. Had NULL been treated as expired, that merchant would have been silently downgraded to
`free` overnight. The record also has no `fromPlan`, so even a match would have been skipped and logged
rather than guessed.

### W6 — P&L parity

Row order, visibility and the render guard now come from one shared function. The served bundle contains
`grossProfitBasisNote` (the new caption explaining why gross profit can be negative while net profit is
positive) and `operatingExpenses`. No API change — every field the UI needs already shipped.

W5 is **test-only** and changes no production behaviour. Its two premises were checked against production:

it looked before opening the payment sheet), and the QRIS settings endpoint correctly 403s on the suspended
canary. Running the specs themselves needs a browser, and that is blocked — see follow-ups.

## 5. One pre-existing defect found, not caused by this deploy

`health-check.sh` reports **PostgreSQL FAIL / Redis FAIL** on `app`. Confirmed a false alarm and a script
defect for this topology:

- nothing listens on `:5432`/`:6379` on `app` — both live on `db` (`10.0.0.1`), which is reachable
- the script's own header says these two probes are **local** `pg_isready`/`redis-cli`, meaningful only on
  a single-host box
- the API's `/health`, which uses the real connections, is green

So the script's HTTP checks follow `BASE_URL` while its last two checks silently probe the wrong host. On a
split cluster they can only ever fail. Worth fixing, because two permanent FAILs train an operator to
ignore the summary line — which is how the session-027 landing incident stayed invisible.

I also briefly reported two landing assets as 404 before checking: `/img/logo.svg` and `/og-cover.png` do
not exist under those names. The real ones (`/img/og-cover.png`, `/img/qr.svg`, `/img/food-*.svg`) all
serve 200, and a nonsense path still 404s (non-SPA, correct).

## Follow-ups
