## 2. Backup — found the mechanism broken, used a different one already working

`deployment/scripts/backup.sh` failed twice: first on `mkdir /var/backups/grobiz` (root-owned, 755 — fixed by
`chown devops:devops`), then on `pg_dump -h localhost` — **the script hardcodes `localhost` and reads a
`deployment/.env.production` file that doesn't exist on this server.** It was written for a single-server
layout; this is a split cluster (Postgres on `db` = `10.0.0.1`). Same unfixed-tooling shape as the already-
documented `health-check.sh` localhost issue (session-030), not previously known to affect backups too.

Confirmed the **actual** production backup path is healthy instead: `backup` host (`194.233.81.93`) pulls
grobiz Postgres + all 11 ERPNext tenant sites + `.env` every 6h independently of this script (per the
session-006 mechanism). Latest snapshot at deploy time was 3.5h old (`grobiz-2026-08-04-0600.dump`, 150KB;
all 11 site dirs; `env-2026-08-04-0604`) — used that as the pre-deploy safety net instead of fighting the
broken local script. **Follow-up filed below** — `backup.sh` needs multi-host awareness or should be retired
in favour of documenting the `backup`-host pull job as canonical.
