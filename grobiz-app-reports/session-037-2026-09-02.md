## 1. What the pre-flight measured — and why the deploy was far less risky than its size

The headline number (1,271 commits, more than twice session-034's 619) predicted a dangerous deploy.
Measurement said otherwise, and the measurements are the reason this ran clean.

| Checked | Result | Consequence |
|---|---|---|
| `NODE_ENV` on the running process (`/proc/<pid>/environ`) | **`development`** | The fail-closed `ADMIN_ENFORCE_2FA` gate that cost prod 7.5 min in session-027 **structurally cannot arm here**. Dev has `ADMIN_ENFORCE_2FA=false` and that is fine. |
| Newly-required env vars (schema diff vs `2bc46d9f`) | **zero** — 54→69 keys, all `.optional()` or `.default()` | No boot-blocking env work. |
| The 11 new tables + `tenants.shop_slug` | **all absent** | Every `CREATE TABLE IF NOT EXISTS` genuinely creates, so the inline `UNIQUE`/`REFERENCES` clauses actually land. The "IF NOT EXISTS silently skips a constraint on a pre-existing table" hazard was dead before we started. |
| `0027` collision pre-check (its own `DO $$` predicate, run read-only) | **0 collisions**, 18 rows to rewrite | The one migration that can abort outright was proven safe first. |
| `0028` duplicate live provisioning jobs | **0** | Self-dedupe UPDATE is a no-op; partial UNIQUE builds clean. |
| dev ERPNext version | **v16.5.0 / frappe 16.6.0** | Matches prod. No version gap behind the shop code's v16 field requirements. |
| Toolchain | Node 22.22.0, pnpm 9.15.4, `engines` unchanged | No toolchain migration. |

**The deploy's real risk was the host, not the code.** `dev` runs ~46 PM2 processes across a dozen
products on 5.8 GB RAM; at start it had **~1.0 GB free with 3.9 GB of swap already in use**. A
parallel `pnpm -r build` could OOM, and the kernel's victim might have been another product. With
the user's approval 15 processes were stopped (eventopia, seenow, the two hoteru tenant instances,
pasarbesar), taking available memory **1.1 GB → 2.3 GB**. Builds then ran sequentially under
`--max-old-space-size=1536` and never came close: peak available stayed ≥ 2.2 GB.
**Per the user's instruction those processes were left stopped** — they start when needed.

## 2. The one landmine, caught before it shipped

The deployed order bundle baked `https://app.dev.gro.biz.id`, but dev's `.env` had
**`VITE_API_URL=` empty**. `apps/order` has no same-origin `/api` proxy, so that value is inlined at
build time — and `apps/order/.env.production` supplies the **production** host as the fallback. A
plain `pnpm build` would have shipped a diner app pointing at production (or at nothing) while every
health check stayed green. That exact bug has shipped twice on this box (2026-06-17, 2026-07-26).

It was defused the way the repo's own tooling intends:

```
VITE_API_URL=https://app.dev.gro.biz.id pnpm --filter @grobiz/order build
bash deployment/scripts/verify-bundle-host.sh apps/order/dist app.dev.gro.biz.id app.gro.biz.id
  ok  expected host present: https://app.dev.gro.biz.id
  ok  forbidden host absent: https://app.gro.biz.id
```

…and then re-verified **against the bytes actually served over HTTPS**, which is the only check that
proves what a browser receives: the served bundle contains exactly one host, the dev one.

## 3. Deploy order — two deliberate departures from the written runbook

`docs/guides/deployment-dev.md` **has zero changes in this entire 1,271-commit range**. The dev
runbook is exactly as stale as the dev server was, and three of its five commands are now wrong. Two
departures mattered:

**(a) The frontends were built AFTER the API restart, not before.**
`docs/runbooks/2026-09-01-inventory-improvements-deploy.md` states plainly that *deploying
`apps/web` before `apps/api` **wipes merchants' product descriptions** — no error, no log line*. On
dev this is sharper than on prod, because the API serves the seller SPA from `apps/web/dist`
**in-tree** (confirmed: served bundle hash == in-tree hash, and there is no `/var/www/grobiz/web`).
So the new bundle goes live the instant the build writes it. Building the frontends after the
restart removes that window entirely rather than merely shortening it.

**(b) `pm2 restart --update-env`, never `pm2 start ecosystem.config.cjs`.**
That file injects `NODE_ENV: 'production'` with no dev override *and* declares `grobiz-wa-gateway`.
Running it would have armed the 2FA boot-refusal gate against dev's `ADMIN_ENFORCE_2FA=false` **and**
started a gateway that hard-throws without two ≥24-char secrets — two failure modes in one command.
`NODE_ENV=development` was re-verified from `/proc` after the restart.

Schema went **before** the reload, data **after** it. `0027`'s own header documents that order as
measured, not stylistic: applied before the code, it flips `08…` login from 200 to **401** for every
user typing the form the login placeholder itself asks for.

## 4. Three findings

### 4a. `pnpm db:backfill` is unusable on dev — dev runs PostgreSQL 14

The sanctioned dev data-migration path **failed at its first file**:

```
[db-backfill] applying 0007_feature_flags_nulls_not_distinct.sql…
[db-backfill] failed: syntax error at or near "NULLS"
```

`NULLS NOT DISTINCT` requires **PostgreSQL 15+**. Dev's server is **14.20**; prod's `db` host is
PostgreSQL 16. `db-backfill.ts` always replays the whole `DATA_MIGRATIONS` list from `0007` and has
**no `--from`**, so it aborts there and never reaches `0027`/`0028` — the two files this deploy
actually needed.

Dev's `feature_flags_unique_idx` already exists in the PG14-compatible plain form
(`UNIQUE (key, scope, scope_value)`), so `0007` is not merely unapplied, it is **unappliable** here.

Worked around at deploy time within sanctioned tooling, using documented flags, without touching
`0007`:

```
pnpm db:apply-sql -- --include-data --from 0027    # 19 applied, 1 skipped
```

Verified: **18/18 user phones canonical `62…`, 18 rows before and after** — no row lost, exactly the
count the pre-check predicted.

**Then fixed properly, same session — see §8.**

### 4b. `backfill:fnb-cogs-account` fails 4/6 on dev — a shared-site artifact, not a defect

`updated=0, skipped=2, failed=4`. All six F&B tenants enumerate the **same 14 global Item docs**,
because dev is one shared ERPNext site. `dev00001` and `e2efnb001` report all 14 `unchanged`
(already correct); the other four fail every item with `Data tidak valid` trying to point those same
Items at their own company's account. Unlike `backfill:shop-fields`, this script has **no
shared-mode guard** and loops tenants regardless. The script's own message confirms it is harmless:
*"The P&L still reports their COGS correctly."*

This **falsifies a claim made during this session's own pre-flight analysis** — that company-keyed
accounts made the tenant loop safe on a shared site. It is not safe; it is merely harmless. Recorded
so the next session does not re-derive it.

`backfill:selling-settings` shows the same shared-site shape benignly: `updated=1, skipped=15`
(the first write converges the single shared doc, the other 15 correctly see `already-enabled`).

### 4c. ⚠️ Loyalty tier evaluation crashes on any fractional spend — a real bug, likely live in production

`pnpm loyalty:evaluate-tiers --all` → `ran=9 skipped=3 failed=1`:

```
d0d48118: FAILED  insert into "customer_tiers" … "window_spend" …
  cause: PostgresError: invalid input syntax for type bigint: "1107090.91"
```

`customer_tiers.window_spend` is **`bigint`** — migration `0041` chose that deliberately, its own
comment warning that overflow would crash the nightly job. But the evaluator passes an
**unrounded** currency value straight in. Any tenant whose windowed spend carries cents fails.

This is **not caused by this deploy** — it is latent in code production has been running since
session-034, where the same job is scheduled nightly at 03:20 UTC. A prod tenant with a fractional
`grand_total` would fail silently every night and simply never have its tier updated. Filed as a
follow-up rather than patched here: it needs a code change and a test, not a deploy-time hotfix.

## 8. `db:backfill` fixed for PostgreSQL 14 — grobiz `a1046557` (same session)

The §4a workaround was left in place only long enough to finish the deploy. The underlying bug was
then fixed on `main`, because skipping `0007` on dev is **not neutral**: dev was carrying the exact
defect that file exists to prevent — `pos_offline_mode`, `whatsapp_bot` and `multi_currency` each
held **3 global copies** (11 flag rows where 5 were correct).

**Why upgrading Postgres was rejected as the fix.** dev's PG14 is **shared infrastructure**: 20
databases across ~15 products (`wagrab` 550 MB, `asiaweek`, `pasarbesar`, `eventopia`, `seenow`,
`hoteru` ×4, `ytgrab` ×2, `miaw`, `iccn`, `rekrutme`, `pahala`, `travelan`, `feyfa`) — grobiz is
15 MB of it. A major-version upgrade is a cross-product migration needing its own window and an
extension audit (seenow uses pgvector). Dev↔prod major-version parity is a real gap and still worth
scheduling, but it must not ride along on a grobiz backfill bug.

**The fix.** `0007`'s failure happens inside a `DO $$` block via dynamic `EXECUTE`, so a version
branch is clean and the **PG15+ path is byte-identical to before — production behaviour unchanged**.
The pre-15 branch reproduces `NULLS NOT DISTINCT` with an expression index, `COALESCE` folding NULL
into a sentinel, reusing the **same object name** so `db:check-drift` (which compares names, not
definitions) stays clean on both majors. Safe on the data: `scope_value` holds a plan tier
(`growth`/`max`) or NULL — the empty string is not a legal value.

Also gave `db-backfill.ts` the **`--from`** flag `db:apply-sql` already had, plus a resume hint on
failure. Its absence is precisely why one bad file made the whole list unresumable.

**Verified on dev (PG 14.20), with the DELETE scoped to captured ids:**

| Check | Result |
|---|---|
| Row count | 11 → **5** |
| The 6 captured duplicate ids | **all gone** |
| The 5 expected survivors | **all present** — no collateral deletion |
| Index definition | `… btree (key, scope, COALESCE(scope_value, ''::character varying))` |
| **Constraint actually bites** | duplicate global flag **REJECTED**: `Key (key, scope, COALESCE(scope_value, ''))=(multi_currency, global, ) already exists` (tested in a transaction, rolled back) |
| Re-run | true **no-op** — the "already emulated" guard prevents drop/recreate churn |
| `--from 0027` | skips 4, applies 2 |
| `db:check-drift` | clean — 50 tables / 588 columns / 103 indexes |
| API | unaffected: `online`, restarts still 39, health green |

All six data migrations (`0007`, `0014`, `0015`, `0023`, `0027`, `0028`) now replay cleanly on dev
via the documented `pnpm db:backfill` — the first time that command has ever worked on this host.

## 9. Loyalty tier evaluation fixed — grobiz `2b61155d` (same session)

§4c's crash was traced to a single conversion point. ERPNext returns
`SUM(base_net_total)` as a DECIMAL; `customer_tiers.window_spend` is `bigint`; Postgres does not
coerce. `fetchCustomerWindowMetric` delegates to `fetchWindowMetrics`, so **one** boundary
(`tier-evaluation.ts`) feeds both the nightly job and the on-sale promotion path.

The fix rounds rather than truncates — the stored figure stays the faithful total, off by at most
half a rupiah, below the smallest unit anyone transacts in — and guards `isFinite`, so a malformed
aggregate becomes `0` instead of a `NaN` that reaches the driver and fails identically.

**Both new tests were mutation-checked**: with the rounding removed they fail and the other nine in
the file still pass. That matters — a test that passes with and without the fix proves nothing.
Full loyalty suite: **92 tests across 9 files, all passing**; typecheck clean.

**Proven on dev against the tenant that actually crashed:**

| | Before | After |
|---|---|---|
| `loyalty:evaluate-tiers --all` | `ran=9 skipped=3 **failed=1**` | `ran=10 skipped=3 **failed=0**` |
| `d0d48118` tier rows | 0 (whole tenant aborted) | **8** |
| The failing value | `1107090.91` → rejected | stored as **`1107091`** (customer `fany`) |
| Estate total | — | 8 tenants, 109 tier rows |

The API was then rebuilt and restarted (`toWholeCurrency` confirmed present in `dist`), because the
script runs from source but the **scheduled** job runs from the compiled bundle — fixing only the
former would have left the nightly failure in place.
