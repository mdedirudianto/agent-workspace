## Why this session

Session-035 closed four of session-034's five follow-ups and turned the fifth — the online-shop
routing conflict — into a decision document, CR-009. The user chose **option C**: move ERPNext into
its own zone rather than build per-tenant nginx sync machinery for the shop.

That option was chosen for one reason above the others. `shopSlugSchema` accepts `f4c91773` — 8 hex
chars, which is exactly the shape of a live tenant's site label. Under **any** scheme that keeps
both in `gro.biz.id`, a merchant could claim a slug that shadows another tenant's ERPNext desk, and
it runs in reverse too (signup mints a random tenantId and never consults `shop_slug`). Separate
zones make that impossible by construction instead of guarded in three places forever.

## 1. Three things measured before writing any code — two of which corrected CR-009

CR-009 named a certificate cost as the gating decision. It was wrong, and so was I.

- **The certificate is free.** Both `proxy` and `erp` already run certbot with the `dns-cloudflare`
  plugin and working zone credentials (`/etc/letsencrypt/cloudflare-gro.ini`,
  `/etc/letsencrypt/cloudflare.ini`). One command each. There was never an ACM purchase to weigh.
- **Grey-clouding is forced, and the record must point at `proxy`.** Cloudflare proxies wildcards on
  Enterprise only, so DNS-only was the only option — but erp's ufw allows 80/443 **only from
  `10.0.0.0/22`**, so pointing the record at erp would have meant exposing a Frappe desk to the
  internet. Proxy stays in the path.
- **nginx wildcards match MULTIPLE labels, unlike DNS wildcards.** I had asserted the opposite when
  presenting the options. Measured: `curl --resolve testtenant.erp.gro.biz.id:443:<proxy>` already
  returned *Frappe's* "site does not exist" while an unrelated host got the default server's 403 —
  so `*.gro.biz.id` was already routing 3-label hosts to erp and the only missing piece was the
  cert. The explicit `*.erp.gro.biz.id` block is still required, for a better reason: nginx picks
  the **longest** matching wildcard, so that block is what will keep ERPNext when `*.gro.biz.id` is
  later repointed at the shop.

**The rename itself was proved safe before touching anything.** All 22 site databases scanned: zero
absolute URLs in `tabFile`, zero host-bound `Singles` (the two `gro.biz.id` hits are `modified_by`
user emails, not URLs), no `host_name` in any `site_config.json`, and erp's nginx is `$host`-driven
throughout (`try_files /$host/public/$uri`). A Frappe site's identity is purely its directory name;
the DB is keyed by a hash inside `site_config.json` and moves with it.

**And no forced re-login.** `siteName` is baked into every JWT, so after the rename every live token
carries a stale value — but the only reader is the refresh endpoint copying it forward. Routing goes
through `plugins/tenant.ts` → `tenants.site_name`. Merchants stayed signed in.

## 2. Code — the landmine CR-009 named, fixed test-first

`isProtectedTeardownSite` derived the protected master as `erp.${baseDomain}`. Correct only while
tenants lived at `<id>.gro.biz.id`; the moment `ERPNEXT_BASE_DOMAIN` became `erp.gro.biz.id` it
computes `erp.erp.gro.biz.id`, and because the check is an exact `Set.has` with no suffix fallback,
**the real master would have silently lost teardown protection** at the exact instant the variable
changed. The new assertion was verified RED against the old code before the fix went in.

It now takes `masterSiteName` = `new URL(ERPNEXT_URL).hostname`, correct under any base domain. The
same rule existed as a **second hand-maintained copy** in `cleanup-orphan-sites.ts` with the
identical bug; both fixed, and both now state that they mirror each other.

New `pnpm tenant:migrate-zone` reuses the existing `renameSite` (a `mv` + clear-cache, already
exercised on every pool-claimed provision) and `invalidateTenantConfig` — never the hand-written
cache key, which caused a real 2026-07-27 incident. Three guards, each for a measured hazard: it
refuses a non-erp target zone, refuses with no bench runner, and refuses per-site if the target
already exists, because `renameSite` **drops** an existing target and a mistyped `--only` would
otherwise destroy a live merchant's site.

## 3. Cutover — six gated steps, in a no-traffic window

Ordering was load-bearing at two points and both are worth keeping:

1. **Code first.** The teardown fix had to be running before the env flip, or the master loses
   protection in the gap.
2. Certs + vhosts. **Gate:** `testtenant.erp.gro.biz.id` returns Frappe's 404 with `ssl_verify=0`,
   and `openssl s_client -servername x.erp.gro.biz.id` presents the `*.erp.gro.biz.id` cert while
   `x.gro.biz.id` still presents `*.gro.biz.id`. That second half proves the longest-wildcard
   precedence the future shop cutover depends on — with nothing yet moved.
3. **Env flip BEFORE the renames.** `ERPNEXT_BASE_DOMAIN` is read only at registration, by the pool
   warmer and by the teardown worker — never at request time — so existing tenants were unaffected
   (verified: `f4c91773.gro.biz.id` still 200 immediately after), and it closed the race where a
   signup mid-migration would mint a tenant back into the old zone.
4. Migrate: idle pool sites first (harmless, proves the mechanism), then suspended, then active.
5. Legacy 301, **after** the renames so it never points at a site that does not exist yet.

## 5. Two traps worth carrying forward

- **Cloudflare cached my own pre-redirect 404s.** After the 301 landed, `f4c91773.gro.biz.id` still
  returned 404 through the CDN while the origin was answering 301 correctly — because I had probed
  that exact URL minutes earlier, between the rename and the redirect. Confirmed with `--resolve`
  against the origin and with a cache-buster. This is the same lesson `health-check.sh` already
  carries: a check that reads the CDN is not checking the deploy.
- **`deploy.sh`'s health check races the API reload.** This deploy's in-script check reported
  API/web/bundle/PWA as FAIL; re-running it seconds later gave all-OK, and the API was serving 200
  with `postgres`/`redis`/`erpnext` all `ok` throughout. Last session it happened to pass. The check
  needs a readiness wait, or it will keep crying wolf on exactly the gate that is supposed to matter.
