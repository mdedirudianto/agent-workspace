## What was fixed

### 1. Midtrans credential rejection surfaced as a generic 500 (real backend defect)

A QRIS charge whose server key Midtrans rejects (`401 "Unknown Merchant server_key/id"`) came back as a
blanket `500`. Every Core API caller threw a bare `Error`, so the route had nothing to branch on. Two
consequences: a **Mode-B merchant** who mistyped their own key got a generic server error instead of a fix,
and a merchant-side mistake counted against our 5xx rate as if it were a platform fault.

Now split by whose key it is — `400` for Mode B (actionable, names the settings page), `502` plus a distinct
`qris_platform_key_rejected` log event for Mode A (our key; the merchant is a bystander and it takes QRIS
down for every Mode-A tenant). Also fixed an adjacent leak found on the way: the payment anchor is reserved
*before* the charge, so a failed charge stranded it `pending` forever.

**Verified live on dev** with a deliberately-invalid Mode-B key on the `e2eret001` fixture: HTTP 400 with the
Indonesian message, anchor `void` not `pending`, and a structured WARN carrying Midtrans's real
`httpStatus: 401` / `statusMessage: "Unknown Merchant server_key/id"`. Fixture QRIS settings restored to
`platform` and diffed byte-identical against the pre-test baseline.

### 2. `order.dev.gro.biz.id` was serving a bundle baked against the PRODUCTION API host

**This one is ours.** `apps/order` inlines `VITE_API_URL` at build time and its vhost has no `/api` proxy, so
a plain `pnpm build` bakes `.env.production`'s production host. Session-025 rsync'd `apps/order/dist/` from
exactly such a build (step 7), which pointed dev's diner app at `app.gro.biz.id`. Everything looked healthy —
all vhosts 200, bundle hash matching the fresh build — while the app was dead in a real browser.

It is the **third** occurrence (CR-002 "Bug #7" 2026-06-17, then this). The recurrence is structural, not
carelessness: the mandatory override lived only in `deployment-dev.md` **§2.10**, a first-time-setup section,
while **§3 "Redeploy"** — the recipe a redeploy actually follows — built and rsynced `apps/web` alone.

Fixed three ways: rebuilt and redeployed dev correctly; added
`deployment/scripts/verify-bundle-host.sh`, which greps the built JS and fails if the expected host is absent
**or** a forbidden one is present; and put that gate into §3.1 and into `deploy.sh --with-order`.

The insight worth keeping: `vite.config.ts` already warned when `VITE_API_URL` resolved **empty**, and that
guard structurally cannot catch a value that is present, well-formed and wrong — which is the only shape this
bug has ever taken. **A build-time-inlined value needs an artifact assertion, not a config-time one.**

**Verified:** the served bundle now contains only `app.dev.gro.biz.id`; the diner e2e suite went from
6 pass / 3 blocked to **9/9**.

### 3. The fraud review queue never closed a flag whose condition cleared

The QA pass reported a real merchant (`Cafe Suhat`) with a captured QRIS payment unbooked since 2026-07-10.
Re-querying dev's ERPNext directly: **that invoice was submitted on 2026-07-21**, and so was a second Cafe
Suhat invoice the pass missed. There were **3** open `stranded_paid_draft` rows on dev, not 1, and 2 of them
described a condition that no longer existed.

Root cause: `recordFlag` opens rows and refuses to reopen resolved ones, but nothing ever *closed* one — the
sweep's `docstatus === 1` branch did nothing at all. Added `autoResolveFlag` (conditional on `status='open'`,
so an operator's verdict is never overwritten; `reviewedBy` left NULL and the note prefixed `[auto]`).

The QA pass is its own evidence of the cost: a careful reviewer read the admin queue in good faith and
escalated a two-week-old incident that had been resolved for days.

**Remediated by running the real sweep** (new `pnpm sweep:dine-in-paid`) rather than hand-writing UPDATEs —
that fixes the data *and* demonstrates the fix on real data. It closed exactly the 2 stale rows, left MyCafe's
genuinely-stranded one open, and a second run closed 0.

Blast radius stated precisely rather than inflated: `countOpenFlagsSince` is time-windowed, so stale rows were
**not** keeping alert rules breached. The harm was confined to the admin queue and the humans reading it.

### 4–8. Test-harness fixes (not deployed code, but the reason dev QA was unreliable)

All five are "correct on a single-company laptop, wrong on a shared deployment":

- **`getBinQty` read an arbitrary tenant's stock.** `warehouse LIKE 'Toko Utama%'` with `limit 1` and no
  company scope; dev has **21** such warehouses. Measured on dev: 266 Bin rows, **38 items existing in more
  than one company**. `KRT-005` is in 4 — the old query returned MyCafe's 15 when the tenant under test held
  30. Now company-scoped, and — the load-bearing half — it **throws naming every candidate** rather than
  picking a row. `order_by` would have made it worse: a deterministically wrong row is harder to spot.
- **`MODE: value` had no consistency poll** while `MODE: delta` always had one.
- **`erpnext-verify` substituted a `site_name`** that is a different app entirely on dev.
- **`live-smoke.spec.ts` was reachable through no Playwright project.**
- **`real-backend-admin.spec.ts` could suspend a real tenant or WhatsApp every merchant on the box** by
  clicking "the first active row". Now opt-in behind `ADMIN_E2E_DESTRUCTIVE=1` and fixture-scoped.

### 9. New capability: dev has real dynamic-QRIS coverage

`MIDTRANS_MOCK` is hard-off in production and must not be switched on for a shared box, so every dynamic-QRIS
spec was unrunnable against dev. They now settle through **Midtrans's own hosted sandbox simulator**, which is
*stronger* evidence than the mock: a real Core API charge, a real QR, and Midtrans itself POSTing the
settlement to our webhook — so signature verification, the `pending → paid` transition and the Mode-A fee
engine all run for real. The mock bypasses all four.

⚠️ **Operational detail worth recording:** use **`/v2/qris/…`**, not `/qris/…`. Midtrans's docs describe
`/qris/index` as the path for older sandbox accounts; for our merchant it is the one that does **not** work —
it answers HTTP 200 with "Transaction is unsuccessful" while the transaction stays `pending`. `/v2` answers
"Status PAID" and the webhook lands in under 4 s. Both return 200, so the status **text** is the only signal.

## Midtrans key on dev — checked, and it is fine (record this, the doubt will recur)

Finding #1 above is an **error-handling** defect, not a credentials one. The `401` came from a deliberately
fake merchant key that the Mode-B test spec configures (`SB-Mid-server-DUMMYKEY-B`); it is harmless locally
because the mock short-circuits before any network call, and dev has no mock, so it reached real Midtrans.
The bug was that we answered `500` instead of telling the merchant their key is bad.

While confirming that, dev's **platform** key looked alarming: it has **no `SB-` prefix**
(`Mid-server-…`, 35 chars), which normally denotes a PRODUCTION key — and `MIDTRANS_IS_PRODUCTION=false`
points the code at the sandbox host. A production key pointed at sandbox would be a real problem.

**It is not.** Settled with a read-only status query for a nonexistent order against both hosts (creates
nothing, moves nothing):

| Host                        | Response                                                              | Meaning                    |
| --------------------------- | --------------------------------------------------------------------- | -------------------------- |
| `api.sandbox.midtrans.com`  | `200` → `{"status_code":"404","status_message":"Transaction doesn't exist."}` | key **authenticates**  |
| `api.midtrans.com` (prod)   | `401` → `{"status_code":"401","status_message":"Unknown Merchant server_key/id"}` | key **rejected**   |

So it is a sandbox key that simply lacks the conventional `SB-` prefix — this Midtrans account issues them
that way. No production credential on dev, no real-money path through it. (Incidentally the production 401 is
the exact response shape the new `MidtransError` classifier keys on, which independently corroborates it.)

⚠️ **One genuinely open question for whoever owns the Midtrans account.** The generated sandbox QR is not
anonymous — decoding the EMVCo payload from a Rp 12.000 dev charge:

| Tag                 | Value               |
| ------------------- | ------------------- |
| 59 merchant name    | `GroBiz`            |
| 60 merchant city    | `PALEMBANG`         |
| 61 postal code      | `30152`             |
| 52 MCC              | `6381`              |
| `merchant_id`       | `M073614114`        |
| 51 QRIS NMID        | `AID319775505877`   |

Those are real registration details, and Midtrans's own testing documentation states that **for QRIS
specifically the sandbox reference points at the same Merchant ID as the production environment**. If that
holds here, a dev QR could be scannable by a real e-wallet and route real money. **Not verified — the only
test is scanning with a real wallet, which was deliberately not done.** Until someone confirms in the
dashboard whether `M073614114` / NMID `AID319775505877` is shared with production, the working rule is:
**never scan a dev/sandbox QRIS code with a real phone.** Payment simulation goes through
`simulator.sandbox.midtrans.com/v2/qris/`, which cannot move real funds.
