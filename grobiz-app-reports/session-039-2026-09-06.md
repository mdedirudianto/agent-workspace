# Session 39 — Xendit in PRODUCTION: the subscription rail proven with real money, and a 92-second outage the boot guard caused on purpose

**Date:** 2026-09-06 (immediately following session-038)
**Scope:** Production (`devops@app`), the production Xendit account, and `db`'s Postgres.
**Code deployed:** none — this session changed only `.env` and remote Xendit configuration.
Prod stays on `e83ada31`.
**Outcome:** `CHECKOUT_GATEWAY=xendit` and `PAYOUT_GATEWAY=xendit` are live; **`PAYMENT_GATEWAY`
stays `midtrans` and cannot be moved**. All three Xendit callback URLs registered against
`api.gro.biz.id`. The subscription rail was proven end to end with a **real Rp 49.000 QRIS
payment**.
**Incident:** ⚠️ **92-second API outage** (23:11:23 → 23:12:55 WIB) — `PAYMENT_GATEWAY=xendit` made
the API refuse to boot. §1.
**Rollback:** `.env.bak-xendit-incident-20260906-181250` (pre-fix state) and
`.env.bak-pre-1075-20260906-172738` (pre-Xendit state) on the host.

---

## 1. ⚠️ Incident — the API refused to boot for 92 seconds

**What happened.** The Xendit environment was set on the host including
`PAYMENT_GATEWAY=xendit`, and `grobiz-api` was restarted. It then refused to start on every
attempt:

```
Error: Refusing to start: PAYMENT_GATEWAY=xendit but the Xendit adapter cannot refund yet,
so a Mode-A tenant could take money that cannot be given back through the app.
Refusing to route real money through it.
    at buildApp (apps/api/src/app.ts:130:11)
```

| | |
|---|---|
| First crash | `2026-09-06 18:11:23` host (+02) = **23:11:23 WIB** |
| Last crash | `18:12:42` = 23:12:42 WIB |
| Recovered | process start `16:12:55Z` = **23:12:55 WIB**; `/health` confirmed `ok` at 23:13:16 |
| **Outage** | **92 seconds** |
| Crash-loop iterations | **8**, against `max_restarts: 10` |
| Blast radius | `api.gro.biz.id` and `app.gro.biz.id` → **502**. `admin`, `order` and `landing` stayed **200** (separate PM2 processes) |

**It was two iterations from a hard stop.** `ecosystem.config.cjs` sets `max_restarts: 10` with
`min_uptime: 5000`; a boot that throws never reaches 5 s, so every attempt counted. At 10 PM2 marks
the process `errored` and stops retrying — self-recovery ends there and a human has to
`pm2 start` it. The incident was caught at 8.

**The fix**, applied after backing up `.env`:

```bash
cp .env .env.bak-xendit-incident-$(date +%Y%m%d-%H%M%S)
sed -i 's/^PAYMENT_GATEWAY=xendit/PAYMENT_GATEWAY=midtrans/' .env
pm2 startOrRestart deployment/pm2/ecosystem.config.cjs --only grobiz-api --update-env
```

The other two rails were **kept** — they are governed by different guards and both booted clean,
which is itself the evidence that D15/D19's split is real rather than cosmetic.

**The guard is right and this is not a configuration gap.** `XENDIT_REFUND_IMPLEMENTED` is a
constant `false` in `core/payments/xendit/gateway.ts` because a legacy QRIS payment does not exist
in Xendit's Payments v3 API at all, so `/refunds` has no `payment_request_id` we could supply.
Clearing it is a **charge-creation migration onto Payments v3**, not a flag. A Mode-A tenant takes
a diner's money into GroBiz custody; being unable to return it is an obligation we cannot meet, so
production must not be able to opt in by setting one variable. The refusal did exactly what it
exists to do — loudly, at boot, before a single charge.

**The transferable lesson is about the restart, not the variable.** The guard is FATAL by design and
was documented in `docs/guides/deployment-xendit-gateway.md` §0 and in `.env.example` lines 327–328.
What turned a refused configuration into an outage was restarting a live API to pick it up. **A
`.env` change that touches a boot guard should be validated against a throwaway process on a spare
port before `pm2 restart` touches the live one** — `PORT=47xx node apps/api/dist/.../server.js` exits
non-zero in about a second and costs nothing.

## 2. What is live now

```
PAYMENT_GATEWAY=midtrans     ⛔ blocked — structural, see §1
CHECKOUT_GATEWAY=xendit      ✅ live, PROVEN with real money (§4)
PAYOUT_GATEWAY=xendit        ✅ live, key has write scope, UNTESTED (§5)
XENDIT_SECRET_KEY=xnd_production_…
XENDIT_PUBLIC_KEY=xnd_public_…
XENDIT_CALLBACK_TOKEN=…  (48 chars)
```

Boot guard coverage differs per rail and that is the whole point of the split:

| rail | guard | why |
|---|---|---|
| `PAYMENT_GATEWAY` | key + token + **refund** → FATAL in prod | Mode A holds a diner's money |
| `CHECKOUT_GATEWAY` | key + token only, **no refund term** | a merchant pays GroBiz into GroBiz's own account, refundable from our dashboard, manual transfer as fallback |
| `PAYOUT_GATEWAY` | **no guard at all** | boots unvalidated — see §7 |

### Key validation

Probed the way a permission-scoped key has to be probed — **a green read proves nothing about the
write**, so the write is probed with a deliberately invalid body:

```
POST /disbursements  {}   -> 400   (permitted, merely wrong)
GET  /balance             -> 200   (balance scope present)
```

`403` on the first would have meant no money-out scope.

## 3. Registering the webhooks — by API, and the call returns the token

The guide says "set in the dashboard", but `POST /callback_urls/{type}` does it, and **the response
carries `callback_token`** — which is the only sane way to obtain `XENDIT_CALLBACK_TOKEN`. All three
webhook routes read that one account-wide value.

```bash
KEY=$(grep '^XENDIT_SECRET_KEY=' .env | cut -d= -f2-)
for T in qr_code invoice disbursement; do
  case $T in
    qr_code)      U=https://api.gro.biz.id/api/webhooks/xendit/qris ;;
    invoice)      U=https://api.gro.biz.id/api/webhooks/xendit ;;
    disbursement) U=https://api.gro.biz.id/api/webhooks/xendit/disbursement ;;
  esac
  curl -s -X POST "https://api.xendit.co/callback_urls/$T" -u "$KEY:" \
    -H 'content-type: application/json' -d "{\"url\":\"$U\"}"
done
```

All three registered, and **all three returned a token identical to the one already in `.env`** —
which is what proves the account and the variable agree. `disbursement` worked, closing a caveat
recorded earlier the same day: only `qr_code` and `invoice` had ever been exercised in this
codebase, so the third type's name was documented but unproven.

**Registration is account-wide and replaces whatever was there.** The sandbox account's three
callbacks still point at `api.dev.gro.biz.id`; production is a **separate account** with a separate
key, so registering here took nothing away from dev. That separation is what made this safe, and it
is worth restating because the hazard is silent — a stolen callback URL produces no error anywhere,
just settlements that stop arriving.

## 4. Verification — six refusals, then a real payment

**Every webhook fails CLOSED, and every one is reachable:**

| test | `/xendit/qris` | `/xendit` | `/xendit/disbursement` |
|---|---|---|---|
| no token | **401** | **401** | **401** |
| wrong token | **401** | **401** | **401** |
| correct token, unknown reference | `unknown` | `unknown` | `ignored` |

That proves Cloudflare → nginx → Fastify → token verification → route logic, and that the stored
token is byte-identical to what Xendit sends. **But every one of those was posted by us**, which
proves the route and not the reachability — a WAF rule or IP reputation could still block Xendit's
own servers, and that failure is the silent kind.

### The real payment closed that gap

A genuine subscription invoice was minted on the retail canary `d6f28680` and **paid for real**:

| | |
|---|---|
| Our invoice | `f8595389-0b2e-48f5-8a39-e7fb94144627` |
| Xendit invoice | `6a9d92d96e1bf50018e28d8e` |
| Hosted checkout | `https://checkout.xendit.co/web/6a9d92d9…` (200) |
| `paymentMode` | `redirect` — correctly NOT Snap |
| Amount | Rp 49.000, plan `starter` |
| **Paid via** | **QR_CODE / QRIS** |
| Xendit `paid_at` | `2026-09-06T16:25:38Z` |
| **Inbound callback** | `POST /api/webhooks/xendit` **from `18.142.72.148`** at `16:25:41Z` |
| Our settlement | invoice `paid` 3 s after Xendit took the money |
| Subscription | `free → starter`, `active`, period **2026-09-07 → 2026-10-07** |
| `tenants.plan` | `starter` |
| Flags raised | **0** |
| Xendit HOLDING balance | **IDR 49.000** |

`18.142.72.148` is AWS Singapore — **Xendit's own infrastructure**, not ours. That is the
reachability proof, and it means the whole chain works: mint → hosted checkout → real QRIS payment
→ Xendit callback → token verify → re-fetch verification → invoice settled → plan granted.

**`invoices.gateway_provider` read `xendit` from the moment the row was created** (migration `0049`),
which is why settlement resolved the right adapter. The provider mix is now 13 `midtrans` +
1 `xendit`, and because it is read off the row rather than from the environment, that invoice would
keep settling on Xendit even if the variable were flipped back. That is D2 working on the
subscription rail.

Balance sits in **HOLDING** rather than CASH — normal, Xendit moves QRIS to CASH on their own
settlement cycle. Nothing to do.

## 5. What is NOT proven

- **Payouts.** `PAYOUT_GATEWAY=xendit` is set and the key carries write scope, but nothing has been
  disbursed. Testing it means moving real money to a real bank account.
- **QRIS acceptance.** Blocked, and no amount of configuration changes that.
- **Invoice-expiry callbacks.** "Also notify my application when an invoice has expired" is a
  separate dashboard opt-in that is off by default and not reachable from `/callback_urls`.
  Unconfirmed whether it was ticked.

## 6. The payout economics nobody has modelled

Measured at CR-013 M9 across six real disbursements: **Xendit's disbursement fee is Rp 2.775 flat**,
and **nothing in the code models it**. Margin on a payout is 0.723% of gross, so **a payout only
breaks even at roughly Rp 383.800** — that run's first payout earned Rp 872 and cost Rp 2.775.
Partial payouts make it sharper, because `amount_idr` is a CEILING claimed FIFO. A minimum payout
threshold is a product decision that should be made before this rail sees traffic.

Related figure while it is in view: Xendit's QRIS MDR is **0.777%** (0.700% + 11% PPN) against
Midtrans's **0.700%** all-in.

## 7. Follow-ups

- [ ] **`PAYOUT_GATEWAY` has NO boot guard at all**, unlike the other two rails. A host can be
  configured for automated disbursement with a missing or wrong key and learn about it only when a
  payout fails. Worth a `checkPayoutGatewayConfig` sibling.
- [ ] **Set a minimum payout threshold before enabling payouts in anger** (§6). Below ~Rp 383.800 a
  payout loses money, and the fee is modelled nowhere.
- [ ] **Validate a boot-guard `.env` change against a throwaway process before restarting the live
  API** (§1). Two more crash-loop iterations and PM2 would have marked `grobiz-api` `errored` and
  stopped retrying.
- [ ] **The canary `d6f28680` is now a paying `starter` tenant** with a period to 2026-10-07 and a
  real paid invoice behind it. Deliberately left rather than reverted — reverting would leave a paid
  invoice contradicting the plan. It inflates the paid-tenant count by one; exclude it from any
  revenue figure, exactly as the `ZZ Smoke Test *` tenants are already excluded from loyalty metrics.
- [ ] **Confirm the invoice-expiry callback opt-in** is ticked in the Xendit dashboard (§5).
- [ ] **Unblocking QRIS acceptance needs a Payments v3 migration**, not a flag — tracked in the repo
  at `docs/ops/2026-09-02-cr-013-xendit-followups.md` §1. Until then `PAYMENT_GATEWAY` must stay
  `midtrans` on production, and anyone setting it otherwise takes the API down.
