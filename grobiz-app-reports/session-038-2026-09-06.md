`CHECKOUT_GATEWAY` and `PAYOUT_GATEWAY` are all absent from prod's `.env`, so all three default to
Midtrans and every Xendit code path plus all five gateway migrations ship dormant. Verified after
the deploy, not assumed:

| check | result |
|---|---|
| the six gateway env vars | **0 present** |
| `dine_in_order_payments.gateway_provider` | **15 rows, all `midtrans`** (`0047`'s default) |

Every `NOT NULL` column added to a populated table carries a default, and both defaults are the

Pre-flight also confirmed **no newly-required env var** (the whole `env.ts` diff is `.optional()`
or `.default()`), and that the one FATAL boot guard — `ADMIN_ENFORCE_2FA=false` in production — is
satisfied because prod has that line **commented out**, so the schema default (`true`) applies.

## 2. The billing cron was the headline risk, and reading it changed the picture

`jobs/subscription-lifecycle.ts` becomes a real billing cycle in this release. Its cron is
`0 2 * * *` with an explicit `timezone: 'UTC'` — **09:00 WIB**, which the observed `past_due_at`
timestamps (`10:00:00+08` = 02:00 UTC) confirm. The runbook's §2 pre-flight was run against
production before anything was deployed, and block 5 (suspend) **returned a row**:

```
2caaaf0a  Salon Fany  growth  past_due_at 2026-08-30  tenant=active
```

It holds an **admin comp** — `planOverride {fromPlan: free → toPlan: growth, reason: "kebutuhan
testing program loyalty", adminName: "Fany", expiresAt: 2026-09-28}` — its only invoice is
`cancelled`, and it owes nothing.

**Then reading the OLD job changed the conclusion.** The version already running on prod suspends
anything `past_due` for 7+ days with **no `plan <> 'free'` guard at all**, so Salon Fany was
scheduled for suspension at 09:00 WIB tomorrow *whether or not this deploy happened*. Meanwhile
three free-plan tenants — **Bahlil**, **ES TELER HAPI LULU**, **Katalog Supplier** — were sitting in
`past_due` and the old code would have suspended all three for a debt that cannot exist; the new
code **heals** them (block 1b). So deploying was strictly safer than not deploying, which is the
opposite of what the block-5 row first suggested.

### The fix, and why clearing `past_due` alone would have been wrong

Salon Fany was repaired before the deploy, on the user's explicit decision. The non-obvious part is
`current_period_end`: **`lapse` runs BEFORE `plan-override-expiry`** in the same tick
(step order: trial-ended → free-past-due-repair → past-due-anchor → renewal-invoice →
cancel-at-period-end → **lapse** → suspend → **plan-override-expiry** → trial-warning). With the
period end left in the past, the very next run would have minted a real Rp 99.000 invoice against a
comp'd account and put it straight back to `past_due`.

```sql
UPDATE subscriptions
SET status = 'active', past_due_at = NULL,
    current_period_end = TIMESTAMPTZ '2026-09-30 00:00:00+00', updated_at = now()
WHERE id = '8add8cb1-…' AND tenant_id = '2caaaf0a' AND status = 'past_due';   -- UPDATE 1
```

`2026-09-30` is two days past the comp's expiry, so the 09-29 run reverts the plan to `free` first
and `lapse`'s `plan <> 'free'` excludes it permanently thereafter. `planOverride` was deliberately
**not** touched — the comp is Fany's decision. Blocks 2, 4 and 5 were re-run afterwards and all
three are now empty; tomorrow's cron will do only the harmless block-1b heal.

## 4. Deploy order — one deliberate departure from `deploy.sh`

`deploy.sh` was **not** run wholesale. Its step 3 is `pnpm -r build`, and Fastify serves the seller
SPA from `apps/web/dist` **in-process**, so building everything before the API restart puts the new
bundle live *first* — the exact direction the runbook warns fails silently (`graceEndsAt` and
`dueDate` are optional, so a new bundle on an old API renders a past-due subscription with no
countdown and reads as a working page that lost its dates). Session-037 made the same departure on
dev for the same reason.

Executed order:

1. `pg_dump` + `.env` backup
2. `git pull` + `pnpm install --frozen-lockfile` (lockfile up to date, +10 packages, 11.6 s)
3. build **shared → api → wa-gateway only**
4. **`backfill:shop-fields --yes`** (23 ERPNext sites)
5. `db:check-drift` baseline → `db:apply-sql` → drift gate *(run in parallel with 4 — different
   system, additive-only, and old code ignores new columns)*
6. `pm2 startOrRestart --only grobiz-api --update-env`, then `grobiz-wa-gateway`
7. assert `POST /api/assistant/ask` → **401** (it was **404** pre-deploy — the proof the API rolled)
8. build **web → admin → landing**, reconcile the two static servers from the ecosystem file
9. `db:backfill` (6 data migrations, all previously applied, all idempotent)
10. order app: build with `VITE_API_URL`, `verify-bundle-host.sh`, relay to `proxy`

`pnpm` inside the project resolves to **9.15.4** via corepack (`packageManager` field) even though
the host's global pnpm is 10.33.0 — worth knowing, since `pnpm -v` outside the project misleads.
Node is `/usr/bin/node` v24.18.0.

## 7. Gro is LIVE in production, on an OAuth subscription session

`pnpm seed:defaults` created the `ai_assistant` feature-flag row **disabled** with empty credentials,
as designed. The credential was then stored and the flag enabled, on the user's explicit decision.

**The OAuth values never entered a chat, a ticket or a log** — the script's own rule. Rather than
typing them into the admin form, a one-off local script read the Keychain
(`security find-generic-password -s 'Claude Code-credentials'`) and `PUT`
`https://api.gro.biz.id/api/admin/ai-config` with a bearer token lifted from the logged-in admin
session, printing only the outcome.

Two schema fields are **required** and are easy to miss when driving the route by hand:
`temperature` and `max_tool_iterations` (the first attempt 400'd on `temperature: Required`).

### The redaction fix, proven on real production data

That PUT exercised the exact route that used to write provider keys to `audit_log` in plaintext
(CR-012 §1). The pre-flight sweep found **0 pre-existing hits**, and afterwards:

- `audit_log` row `ai_config.updated` exists, attributed to `admin@gro.biz.id`'s user id
- **`SELECT count(*) FROM audit_log WHERE details::text LIKE '%sk-ant-%'` → 0**
- the row records `"oauth_credential_stored": true` — a **boolean**, never the value

The credential itself is AES-256-GCM at rest in `platform_config.ai_assistant`, with `ackBy` and
`ackAt` recorded.

### The first real answer

That is exactly the smoke test's own `ACC-SINV-2026-00039`. A tool computed it, the model narrated

### ⚠️ A recorded claim is now contradicted: prompt caching **IS** firing

`CLAUDE.md` and `docs/engineering-notes/57-prompt-caching-captured-wired-and-measured-not-firing.md`
both state, from a 2026-09-05 measurement, that Anthropic **answered zero on both cache figures**
across two identical back-to-back calls, and that the one uncontrolled variable was the auth mode —
an OAuth subscription session. That document explicitly asks for a re-measurement.

**This is that re-measurement, and the answer is now yes.** The first production turn, on the same
auth mode (OAuth, `max` subscription):

| figure | value |
|---|---|
| `prompt_tokens` | 15 381 |
| `cache_read_tokens` | **7 195** |
| `cache_write_tokens` | **7 195** |
| uncached input | 991 |
| **prompt served from cache** | **47 %** |
| `cost_nano_usd` / `cost_micro_idr` | 11 119 250 ($0.01112) / 183 467 625 (Rp 183,47) |
| `outcome` / `auth_mode` | `ok` / `oauth` |

Read == write == 7 195 exactly, which is what a two-call turn looks like: the tool-selection call
writes the cache and the narration call reads it. The admin console reports the same figure
independently — *"Prompt served from cache: 47% (7.195 tokens) across 1 answers that reported it."*
**The repo's docs should be corrected**; this is filed as a follow-up rather than changed here,
since it is a repo change and not an ops one.

The console also correctly shows the auth-mode cost split (*"Claude subscription · 1 answers ·
notional, not billed"*), the honest FX disclosure (*"No rate has ever been fetched; using the
shipped fallback"* — `ai_fx_rate` self-heals at the 09:05 WIB job), topic derivation from the first
tool called, and tool health (`sales_summary`).

### The credential-sharing hazard, stated plainly

The token in production **is** this machine's Claude Code login, and the refresh token rotates —
whichever side refreshes first invalidates the other. The user accepted this ("paste fresh and leave
enabled"). The clean mitigation is that Anthropic OAuth supports concurrent sessions per account:
running `/login` locally mints an independent session so prod holds session A and the laptop holds
session B, neither rotating the other. **Not yet done — see follow-ups.**

## 8. Xendit exercised locally against the real sandbox, stealing nothing

Prod keeps Xendit dormant (§1). The rail was proven on this machine instead, on a dedicated port
with every gateway variable passed **inline** so nothing survives the process and `.env` is
untouched:

```
PORT=4794 PAYMENT_GATEWAY=xendit PAYOUT_GATEWAY=xendit CHECKOUT_GATEWAY=midtrans \
  API_BASE_URL=http://127.0.0.1:4794 pnpm --filter @grobiz/api dev
pnpm --filter @grobiz/api xendit:local-circuit -- --api=http://127.0.0.1:4794 \
  --phone=081200000003 --pin=123456
```

Boot emitted exactly the expected warning — *"PAYMENT_GATEWAY=xendit but the Xendit adapter cannot
refund yet"* — the documented asymmetry where **dev warns and production refuses**.

All eight steps green: credentials → login (`e2eret001`) → product → **real charge on the Xendit
rail** (`qr_ba69407b…`; there is no mock branch for Xendit, so every tap is a real `POST /qr_codes`)
→ anchor open/unpaid → **sandbox settled the QR for real** → **webhook accepted the replay, D4
re-fetch passed** → anchor PAID.

Step 7 is the one that matters: Xendit signs nothing, so the route's authentication is asking
Xendit's own API whether a SUCCEEDED payment exists for that charge at that amount. A replayed
envelope has to survive that, and it did.

**The shared sandbox account's callback registration was not touched.** Three paths would have
re-pointed it away from `api.dev.gro.biz.id` and broken dev's settlements silently —
`xendit:verify`, `xendit:capture-webhook`, and **saving Mode B with a secret key on
`/settings/payments`** (a button in the UI). None was run. There is no read-back endpoint, so this
is negative-by-construction: the rule is *don't run those three*, not *check afterwards*.

Local anchors now read **806 `midtrans` / 6 `xendit`** — the provider is captured per anchor, never
re-read from env at settlement, which is precisely what makes flipping the variable safe.

The local API was stopped and port 4794 released.
