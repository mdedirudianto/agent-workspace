**None of these streams has a merchant opt-out.** The only related switch (`platform_config.ai_assistant.digest.enabled`) gates AI narration, never delivery; CR-016 §3.3 records "no settings flag … no opt-out".

Nobody replied BERHENTI/stop (0 inbound matching `stop|berhenti|jangan|ganggu|unsub|matikan|spam`), but inbound volume overall is only 68 messages in 3 weeks: merchants do not talk to the platform number, so the window is almost always closed.

### 2.2 Every platform template has failed

| Template | Failed rows | Reason (all identical) |
|---|---|---|
| `trial_ending` | 3 | `Meta API error (404): (#132001) Template name does not exist in the translation` |
| `piutang_reminder` (buyer reminder) | 3 | same |

| `account_suspended` | 2 | same |
| `trial_expired` | 2 | same |
| `payment_success` | 1 | same |

The subscription lifecycle, which is the one stream merchants *should* get, has **never** reached anyone over WhatsApp. The templates do not exist (in language `id`) in the WABA.

### 2.3 Delivery receipts are not arriving

- `receipt_status` is NULL on **all 151** outbound rows since migration `0073` (receipt columns, session-046).
- Only **~35** POSTs to `/api/webhooks/whatsapp` in 7 days of PM2 logs (09-23 → 09-29), against ~45 outbound/day that should each yield sent/delivered/read statuses. 1,856 POSTs hit `/api/webhooks/whatsapp/gateway` (the miaw gateway) in the same period.
- Consequence: the admin inbox shows every out-of-window free-form send as "sent", although Meta drops them with 131047. **We cannot tell from our data whether any digest was delivered.**
- Likely cause (not investigated, read-only session): the Meta app's webhook subscription or the forwarding path (`WHATSAPP_FORWARD_SECRET`) passes inbound messages but not `statuses`.

### 2.4 Merchant-own channel

Quiet and healthy: loyalty point replies / tier-ups (gated by `loyaltyEnabled`), staff replies, device-sent messages. No scheduled blasts. Receipts (`autoReceipt`) and bot (`botEnabled`) already default **off**.

### 2.5 Tenant settings

Only 3 tenants have any `whatsappSettings`; none have any notification preference (the key does not exist). `customerSettings.reminderEnabled` / `autoWA` default **true** in code, so the buyer `piutang_reminder` is attempted for every tenant with overdue invoices (and fails, §2.2).

## 3. Queries used (all read-only)

- Outbound grouped by `send_purpose`, `template_name`, `status`; free-form grouped by `left(body, 45)`.
- 24h window: for each outbound row, `max(created_at)` of inbound rows on the same `contact_id` before it, compared to `created_at - 24h`.
- Send hour: `extract(hour from created_at at time zone 'Asia/Jakarta')`: digests at 21 and 07 only.
- Per-contact cadence of the piutang reminder: `count(*)`, `count(distinct created_at::date)`.
- Receipts since `2026-09-27 05:00+00`; webhook POST counts via `grep` on `~/.pm2/logs/grobiz-api-out*.log`.

## 4. Decisions (owner, 2026-09-29) → repo change `feat/wa-notif-optin`

| # | Decision |
|---|---|
| D1 | Every merchant-business WhatsApp notification is **OFF by default**; no stored preference = off, so all current recipients stop on deploy (no backfill). |
| D2 | Sent **only inside the 24h window**. Each message asks the merchant to reply to keep receiving it, with quick-reply buttons **Oke, lanjut / Berhenti**. No reply → no next send. |
| D3 | Platform messages use Meta **UTILITY** templates. Claude drafts them in the repo; **devops submits them via the Graph API** later. |
| D4 | One toggle per notification (Gro: daily/weekly summary; WhatsApp notifications: payment-due alert, channel-disconnected alert); buyer reminder default also flips to off. |
