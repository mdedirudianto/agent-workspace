# Session 27 — Root-cause: `checkin.eventopia.my` white-screens on boot (`invalid base64url character`)

**Date:** 2026-07-21
**App:** `eventopia` (github.com/biji-dev/eventopia, branch `main`)
**Hosts:** `app` (`devops@10.0.0.5`), `proxy` (`46.250.234.153`), `dev` (`root@154.26.130.96`) — **read-only investigation, nothing changed**
**Env:** **prod AND dev — both broken**
**Status:** diagnosis complete, fix NOT applied (handed to a coding agent)

The user reported this in the browser console on `checkin.eventopia.my`:

```
index-DJKbUFQ1.js:96 Uncaught Error: invalid base64url character
    at v (index-DJKbUFQ1.js:96:7836)
    at ks (index-DJKbUFQ1.js:96:7933)
    at index-DJKbUFQ1.js:96:9139
```

**Answer to "is that due not yet built?":** No — the opposite. It **was** built, and the build is
what's broken. A malformed env var got baked into the bundle at build time, and the decode of it
throws during module evaluation, before React ever mounts. The check-in PWA is a **white screen
on both dev and prod**, and has been for weeks.

---

## Verdict

| | |
| --- | --- |
| **Root cause** | `VITE_TICKET_PUBLIC_KEY` is set to a **standard-base64 SPKI DER** value (`MCowBQYDK2VwAyEA…=`), but `apps/checkin/src/config.ts` decodes it as **base64url of the raw 32-byte key**. The `/` and `=` characters are not in the base64url alphabet → throw. |
| **Where it throws** | `packages/qr/src/encoding.ts:57` (`base64urlDecode` → `sextet()` → `throw new Error('invalid base64url character')`), called from `apps/checkin/src/config.ts:32` at **module top level**. |
| **Blast radius** | Total. Top-level throw → the ES module never finishes evaluating → `main.tsx` never runs → `#root` stays empty. No error boundary, no Sentry/GlitchTip event (Sentry init is in the same dead module graph). |
| **Prod affected?** | **Yes.** Reproduced live with Playwright against `https://checkin.eventopia.my/` — identical error, bundle `index-BqzWQyxm.js`. |
| **Dev affected?** | **Yes.** `index-DJKbUFQ1.js` (the hash in the user's report) is **dev's** bundle, on `dev:/var/www/eventopia-checkin/assets/`, built 2026-07-21 12:21 (session-025). |
| **Broken since** | **At least 2026-06-24** on prod (both archived pre-Jul-10 dists on `proxy` contain the same bad value). Realistically since the env var was first set on 2026-06-12 (session-001/002). |
| **Fix complexity** | Low. One env value per host + rebuild. Plus repo hardening so it can't recur silently. |
| **Fix proven?** | **Yes.** Controlled A/B against the live prod bundle: swapping that one string in-flight (nothing else) takes the page from `invalid base64url character` + empty `#root` to **0 console errors and a fully rendered staff login screen**. See Evidence §5d. |

## Evidence

### 1. The env value is the wrong encoding *and* the wrong key format

Both hosts (`app:/home/devops/eventopia/.env` L66, `dev:/home/deploy/eventopia/.env` L68) carry a
value copy-pasted straight from the *adjacent* `EVENTOPIA_ED25519_PUBLIC_KEY` line:

| Host | `EVENTOPIA_ED25519_PUBLIC_KEY` (correct as-is) | `VITE_TICKET_PUBLIC_KEY` (wrong — same value) |
| --- | --- | --- |
| prod | `MCowBQYDK2VwAyEAJRLeS3Gqgqa6Hb/Qfg9aYxgbcV8MpIaf3kxNje4DNds=` | **identical** |
| dev | `MCowBQYDK2VwAyEASXKtc6W8+wRzdT0JkxuRRJGUag/mDzzCR0Xeyhw5f54=` | **identical** |

Decoding prod's value confirms two independent defects:

```
len: 44 bytes
hex: 302a300506032b657003210 0 | 2512de4b71aa82a6ba1dbfd07e0f5a63181b715f0ca4869fde4c4d8dee0335db
     └─ 12-byte Ed25519 SPKI DER prefix ─┘ └────────── the raw 32-byte key ──────────┘
invalid base64url chars present: ['/', '=']      first offender: '/' at index 30
length 60 → 60 % 4 == 0, so the length guard passes and it reaches the character guard
```

So the value is (a) **DER-wrapped**, not raw — 44 bytes instead of 32 — and (b) **standard base64**,
not base64url. Either alone would break it.

The two env vars are consumed by completely different code paths with different encodings, and
nothing in the repo says so:

| Var | Consumer | Expects |
| --- | --- | --- |
| `EVENTOPIA_ED25519_PUBLIC_KEY` | `packages/keys/src/index.ts` — `Buffer.from(b64,'base64')` → `crypto.subtle.importKey('spki', …)` | **standard base64 of SPKI DER** ✅ correct today |
| `VITE_TICKET_PUBLIC_KEY` | `apps/checkin/src/config.ts:32` — `base64urlDecode(…)` | **base64url of the raw 32 bytes**, 43 chars, no padding ❌ |

The in-repo DEV fallback constant proves the intended relationship — it is literally the SPKI value
with the 16-char `MCowBQYDK2VwAyEA` prefix stripped and `/`→`_`, `=` dropped:

```
packages/keys      DEV_PUBLIC_KEY_BASE64 = 'MCowBQYDK2VwAyEA/Z9yJqS7l8KMnYlyE7nb5oBXKhKoXb8um1dCOjYfCBk='
apps/checkin       DEV_PUBLIC_KEY_B64URL =                 '_Z9yJqS7l8KMnYlyE7nb5oBXKhKoXb8um1dCOjYfCBk'
```

### 6. ⚠️ New finding — the service worker will serve the broken bundle *after* the fix ships

My first patch attempt silently failed (`occurrencesReplaced: 0`) because the SW served the bundle
from CacheStorage and **bypassed network interception entirely**. Inspecting the precache:

```
workbox-precache-v2-https://checkin.eventopia.my/
  /index.html?__WB_REVISION__=5fb8e46b…      ← points at the OLD bundle
  /assets/index-BqzWQyxm.js                  ← the crashing bundle
  /assets/index-CQ_hhpOh.css, zxing_reader…wasm, icons
sw: { active: true, waiting: false, controlled: true }
```

This settles the open question from item 7 of the fix plan, and the answer is **not** "it just works":

1. **First load after the fix deploys → still a white screen.** The SW serves the cached
   `index.html` + old bundle from precache before the network is consulted.
2. In parallel `registerSW.js` (which *does* run) fetches the new `sw.js`, whose precache manifest
   has changed → installs → `registerType: 'autoUpdate'` activates it → `cleanupOutdatedCaches`
   purges the stale entries.
3. **Second load → new bundle, app boots.**

So it self-heals, but it takes **two page loads**. Door staff must be told explicitly: *if it's still
blank after the fix, close it and open it again once.* Discovering that at a gate is exactly the
scenario to avoid. Worth verifying on a real installed device immediately after deploying.

## Why nobody caught it

1. **Deploy verification was `curl` status only.** Sessions 009 and 014 both recorded
   `checkin.eventopia.my | 200 — new build live`. A static SPA returns 200 whether or not its
   JavaScript throws. The check proved nginx worked, not that the app did.
2. **No error telemetry from a top-level throw.** `VITE_SENTRY_DSN` is configured (GlitchTip project
   `eventopia-checkin`, id 19, session-009) but `Sentry.init()` lives inside the module graph that
   never evaluates. A crash this early is invisible to the very tool meant to catch it.
3. **Nothing validates the value at build time.** Vite happily inlines any string; the failure
   surfaces only in a browser.
4. **Check-in is only exercised at an actual event.** Unlike checkout, nobody hits this daily.
5. **`.env.example` documents the format correctly but not the conversion** — and the correctly-encoded
   `EVENTOPIA_ED25519_PUBLIC_KEY` sits ~500 lines above it with a nearly identical name. The
   copy-paste is the obvious thing to do and it is wrong.

## Fix recommendation (for the coding agent)

### Correct env values (computed and verified)

Strip the 12-byte DER prefix, re-encode base64url:

```bash
node -e "console.log(Buffer.from(process.env.EVENTOPIA_ED25519_PUBLIC_KEY,'base64').subarray(12).toString('base64url'))"
```

| Host | File / line | Set `VITE_TICKET_PUBLIC_KEY` to |
| --- | --- | --- |
| prod `app` | `/home/devops/eventopia/.env:66` | `JRLeS3Gqgqa6Hb_Qfg9aYxgbcV8MpIaf3kxNje4DNds` |
| dev `dev` | `/home/deploy/eventopia/.env:68` | `SXKtc6W8-wRzdT0JkxuRRJGUag_mDzzCR0Xeyhw5f54` |

Both are 43 chars, decode to exactly 32 bytes, and match the SPKI tail of each host's own
`EVENTOPIA_ED25519_PUBLIC_KEY` — i.e. tickets signed by that host's API will verify.
On prod, `apps/checkin/.env` is a symlink → `../../.env`, so one edit covers it.

### 1. Repo — accept every sane encoding, and never throw at module scope *(the real fix)*

Add a shared normalizer to `packages/qr/src/encoding.ts` (checkin must **not** import
`@eventopia/keys` — that package carries private material, see the security note in
`apps/checkin/src/config/runtime.ts`):

```ts
/** Normalize any reasonable Ed25519 public-key encoding to the raw 32 bytes. */
export function parseEd25519PublicKey(input: string): Uint8Array
```

It should handle, in order:
- base64url, 43 chars → decode as-is (today's happy path);
- standard base64 → translate `+`→`-`, `/`→`_`, strip `=`, then decode;
- 44-byte SPKI DER (prefix `302a300506032b6570032100`) → return the last 32 bytes;
- anything else, or a result that isn't exactly 32 bytes → throw a **descriptive** error naming the
  var, the observed length, and the expected format.

Then:
- `apps/checkin/src/config.ts:32` — wrap in try/catch. On failure: `console.error` with the full
  diagnostic **and fall back to `DEV_PUBLIC_KEY_B64URL` so the app still boots.** A misconfigured
  key must degrade to "can't verify yet", never to a white screen — this is door software.
- `apps/checkin/src/config/runtime.ts:92` (`resolvePublicKey`) — same treatment for the
  IndexedDB-synced value, which is currently an unguarded `base64urlDecode(synced)` and would throw
  the same way if the API ever returned a differently-encoded key.

**Security caveat on the fail-soft path.** The DEV fallback's *private* half is committed in
`packages/keys/src/index.ts`, so a device verifying against it would admit forged tickets. In
practice this window is closed: `useCheckin` requires a completed `RuntimeConfig`, gate selection
always runs `EventGateSelector.tsx:58 savePublicKey(bundle.publicKey)`, and the API encodes that
correctly (`container.ts:315` `base64urlEncode(keypair.rawPublicKey)`) — so a device that can scan
has already overwritten the build-time key. Still, make the degraded state **visible**: when
`VITE_APP_ENV === 'prod'` and the configured key failed to parse, render a persistent warning
banner rather than falling back silently.

### 2. Repo — fail the build, not the browser

Add a `buildStart` check in `apps/checkin/vite.config.ts` that runs `parseEd25519PublicKey` over
`VITE_TICKET_PUBLIC_KEY` when it's non-empty and **throws**, aborting the build. A red build beats a
white screen discovered at the door. This is the single highest-value item here — it would have
caught this on 2026-06-12.

### 3. Repo — kill the copy-paste trap at the source

- `packages/keys/scripts/generate-keypair.ts` currently prints two lines. Make it print a third:
  `VITE_TICKET_PUBLIC_KEY=<base64url of rawPublicKey>`. Whoever generates a keypair then has all
  three values in the right encodings and never has to convert anything.
- `.env.example:554-557` — state explicitly that this is **not** the same encoding as
  `EVENTOPIA_ED25519_PUBLIC_KEY`, and include the one-liner conversion command above.
- `docs/launch/fm11-runbook.md:37` already flags "check-in PWA rebuilt with the prod
  `VITE_TICKET_PUBLIC_KEY`" at T-7d — add the conversion + a browser-render check to that step.

### 4. Repo — a test that would have failed

`apps/checkin/test/` has no coverage for `config.ts`. Add cases asserting `parseEd25519PublicKey`
returns the same 32 bytes for all three encodings of one key, and that a garbage value throws a
descriptive error rather than `invalid base64url character`.

### 5. Ops — deploy (needs approval per workflow rules)

Per host: back up `.env`, correct the one line, rebuild `apps/checkin`, redeploy the static dist
(prod: build on `app` → relay to `proxy:/var/www/eventopia-checkin`, tar the current dist first, then
`chown www-data:www-data`, per session-014 step 7; dev: build + rsync to `dev:/var/www/eventopia-checkin`).
No API restart, no migration, no PM2 change — `checkin` is pure static.

### 6. Ops — verify in a browser, not with `curl`

Replace the `200 OK` check in the deploy checklist with a real render assertion:

```
Playwright → https://checkin.eventopia.my/
  assert console errors == 0
  assert the login screen renders (not an empty #root)
  assert the bundle contains a 43-char base64url key, not "MCowBQYDK2VwAyEA"
```

The last grep is a cheap, direct regression guard and can run in CI against the built `dist/`.

### 7. Ops — PWA cache after the fix ⚠️ **takes two loads, tell the staff**

Measured, not assumed (Evidence §6): the Workbox precache holds both the stale `index.html` and the
crashing `index-BqzWQyxm.js`, and serves them ahead of the network. After the fix deploys, an
already-installed device **white-screens once more on the first load**, updates the SW in the
background, and boots correctly on the **second**.

- Include "if it's still blank, close and reopen the app once" in the deploy note to door staff.
- Verify on a real device that already has the broken build installed, immediately after deploying —
  before any event, not at the gate.
- If it does *not* self-heal in two loads, the fallback is Clear-site-data / reinstall. Worth
  considering a `skipWaiting` + reload prompt in the app so future bad builds recover in one load.
