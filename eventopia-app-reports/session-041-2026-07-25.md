# Session 41 — Fix `eventopia.my` `/e/<code>` short-link 404: root cause was `proxy`'s own nginx, not Cloudflare (contradicts the app repo's own docs); hit + fixed a classic nginx phase-order bug along the way

**Date:** 2026-07-25

**App:** `eventopia` (github.com/biji-dev/eventopia) — no app-repo changes this session.

**Hosts:** `proxy` (`root@46.250.234.153`) — nginx config edit + reload (the actual fix); `app`
(`devops@154.26.129.104`) — one read-only DB query to find a real published event's short code to
test with. No writes on `db` or `app`.

**Env:** production only (`eventopia.my` zone + the `proxy` vhost fronting it).

## Report

Session-040 deployed the share-QR/short-link feature and found `eventopia.my/e/<code>` 301-redirects
into a real 404 on the marketing site, following the app repo's own launch doc
(`docs/launch/event-share-qr-deploy.md` §1), which states plainly: *"The apex redirect is a
Cloudflare edge rule... a dashboard rule, nothing in this repo"* — the same claim repeated in
`brimo-sandbox-validation.md`. That was deferred to the user as a Cloudflare dashboard fix.

**Chased the Cloudflare side first, per the docs' own claim.** Found prod already has a scoped
`CF_API_TOKEN`/`CF_ZONE_ID` in `app:~/eventopia/.env` (used by the custom-domains provisioner),
confirmed read-only it points to the correct `eventopia.my` zone (Free plan) — but it was scoped to
DNS-only. Over three rounds, the user added **Page Rules** and then **Single Redirect** permissions
to the token. Checked each systematically:

| Mechanism | Check | Result |
| --- | --- | --- |
| Page Rules | `GET .../pagerules` | 0 rules |
| Redirect Rules (`http_request_dynamic_redirect` phase) | `GET .../rulesets/phases/.../entrypoint` | "could not find entrypoint ruleset" — 0 rules |
| Bulk Redirects (account-level) | dashboard (user checked directly) | empty |
| Workers Routes | dashboard (user checked directly) | empty |

**All four Cloudflare mechanisms came back empty — the redirect isn't a Cloudflare rule at all.**
`grep -rl eventopia.my /etc/nginx/sites-*` on `proxy` found it in 30 seconds:
`/etc/nginx/sites-available/eventopia.conf` has a plain
`server { server_name eventopia.my; return 301 https://eventopia.co.id$request_uri; }` block. The
docs' "no origin headers, `server: cloudflare`" reasoning was a **false signal** — Cloudflare
always overwrites the `Server` header to `cloudflare` regardless of whether the redirect
originated at the edge or at the origin behind it, so that check never actually distinguished the
two. DNS confirms the apex `A` record is proxied (orange-cloud) straight to `proxy`
(`46.250.234.153`), consistent with an origin-side redirect all along.

## The fix (and a self-inflicted gotcha)

**First attempt (wrong):** added a `location /e/ { proxy_pass ...; }` block inside the same
`server{}`, ahead of the existing bare `return 301 ...;`, expecting location-block specificity to
win. Deployed clean (`nginx -t` passed, reload succeeded) but **verification still showed the same
301** — including tested directly against the origin IP via `--resolve` + `Host` header, bypassing
Cloudflare entirely, to isolate nginx from any CDN-layer effect.

**Root cause of the failed fix:** a bare `return` directive placed directly in a `server{}` block
(not inside any `location{}`) executes during nginx's **server-rewrite phase**, which runs *before*
location matching happens at all. It fires unconditionally for every request reaching that server
block and short-circuits the response — the `location /e/` block was correctly configured but
never got a chance to compete, because processing never reached the location-matching phase.

**Real fix:** moved the fallback into its own `location / { return 301 https://eventopia.co.id$request_uri; }`,
sitting alongside `location /e/ { proxy_pass http://eventopia_web; ... }` (proxy config mirrored
exactly from the existing wildcard-tenant block in the same file, including its deliberate
omission of `X-Forwarded-Proto` — that header is known to trip a Next.js standalone
self-rewrite/EPROTO on this same `eventopia_web` upstream). Now both are real `location` blocks,
matched by nginx's normal prefix-specificity rules — `/e/*` proxies, everything else 301s.

**Deploy steps:** `cp eventopia.conf eventopia.conf.bak-20260725-pre-e-route` (backup first, per
user instruction) → edit → `nginx -t` (clean; only pre-existing unrelated "protocol options
redefined" warnings across other vhosts on this shared proxy, not from this change) →
`systemctl reload nginx`.

## Findings summary

1. **Fixed:** `eventopia.my/e/<code>` now correctly resolves to the tenant event page, both
   through Cloudflare and hitting `proxy` directly. Share-QR posters/links are safe to print now.
2. **Docs corrected same session:** `docs/launch/event-share-qr-deploy.md` §1 and
   `docs/launch/brimo-sandbox-validation.md`'s "apex redirect is a Cloudflare edge rule, not
   anything in this repo" claim was wrong — it's `proxy`'s own nginx. Rewrote both to state the
   real mechanism, explain why the header-based reasoning was a false signal (Cloudflare rewrites
   `Server:` on every proxied response regardless of origin), and add a bypass-Cloudflare curl
   recipe so a future session can tell the two apart directly instead of re-deriving it. Committed
   locally in the app repo (`885289cf`), **not yet pushed — awaiting user decision**, same pattern
   as sessions 032/033/036/039.
3. **Reusable lesson:** a bare `return` in an nginx `server{}` block always wins over any
   `location{}` block in the same server, regardless of order or specificity — it must be wrapped in
   its own `location / { ... }` to compete normally. Worth remembering for any future "add an
   exception path to an existing catch-all redirect" nginx task on this fleet.
