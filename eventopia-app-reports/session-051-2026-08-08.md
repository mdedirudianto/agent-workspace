## Full live smoke test — every shipped feature, real prod infra

No shortcuts taken on scope: all four features driven through their real code paths against
real production DB/Redis/Xendit, using one disposable organizer (`org_339b3e520f594d86`,
`smoke050-test-org` — name predates a session-numbering fix, see Findings #5, harmless)
pushed to `PAID_PLATFORM` via the proven [[reference_eventopia_payment_smoke_test]] recipe
(email-OTP signup, disposable-operator KYC approval, self-serve MoU).

**New technique this session**, extending the session-045 precedent (direct-calling a worker
turn function against real DB/Redis instead of faking a WhatsApp delivery): wrote one
ephemeral stub script (`apps/workers/scripts/_smoke050-stub.ts` — name also predates the
numbering fix, deleted after use, never committed) exposing `createWorkerTicketRequestTurn`, `createWorkerBoothVisitTurn`, and
`createWorkerWaVerifyService`/`handleVerifyTurn` — the exact same factories
`apps/workers/src/index.ts` wires into the real wa-inbound processor. Used it to prove three
separate WhatsApp-gated flows end-to-end without a real phone.

  resolved 200.

## Findings summary

1. **Clean deploy, zero incidents.** No repeat of the sessions 032/033/038/040
   migration-tooling landmines — proactive cursor check + the known-good `run-migrate.mjs`.
2. **All 4 features proven working against real prod infra**, not just "deploy succeeded" —
   including the two highest-risk items called out in their own deploy notes: the RLS half of
   migration 0125 (verified via `pg_class`, not assumed from the file running clean) and the
   console-rebuild-vs-restart distinction for the report charts (verified visually, not via
   build-artifact grep — closes the exact gap session-049 flagged when no browser was
   available).
3. **Minor gap, not a regression:** the booth check-in QR's WhatsApp-vs-form branch was
   verified by reading `route.tsx`'s condition against the live env, not by decoding the
   PNG's actual QR payload (no `zbar`/`pyzbar` available on this machine). Source + env both
   point at the WA branch with no ambiguity, but a pixel-level decode would be strictly
   stronger evidence — worth having a QR decoder on hand for a future booth-QR-touching
   session.
4. **The direct-turn-stub technique now covers three FSM entry points**
   (`handleVerifyTurn`, `ticketRequestTurn`, `boothVisitTurn`), all via one ephemeral script —
   reusable pattern for any future WhatsApp-gated feature, per session-045's original note.
5. **Session-numbering collision caught and fixed.** This session was drafted as
   "session-050" before discovering `session-050-2026-08-08.md` already existed (a same-day,
   already-committed support-diagnosis session, `99a26c5`) — the `Write` tool overwrote it
   without the pre-read guard triggering. Restored the original from git (`git checkout
   HEAD --`) and renumbered this work to session-051. No data was permanently lost since git
   history had the real content, but worth flagging: always `ls` the reports directory
   immediately before picking a session number, not just at conversation start, when a
   session runs long enough that a concurrent session could land in between.
