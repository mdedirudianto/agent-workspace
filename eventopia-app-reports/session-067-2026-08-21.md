## The four defects

1. **A synchronous ticket correction never re-delivered the e-ticket it invalidated.**
   `rotateTicketToType` revokes the old nonce and re-mints **both** token and `short_code` — its own
   docstring says *"the caller MUST redeliver the e-ticket"*. The paid `COLLECT` path does
   (`exchange-settlement.ts`); the synchronous EQUAL/WAIVE/REFUND_DIFFERENCE path had **no
   redelivery at all**. The attendee keeps a QR that fails revocation (`BLOCK_INVALID`) while the
   roster still lists them, so their **name** admits them — exactly the reported symptom.
   **Not covered by the new delivery sweeper**: it requires `PENDING/ENQUEUED/FAILED`, and a
   corrected ticket is still `SENT` from its first delivery.
   *Live blast radius: 6 tickets / 2 buyers, all `settlement_mode=WAIVE`, applied 08-19 and 08-20.*
2. **The console admitted ANY day.** `checkin/module.ts` resolved the day as
   `dayId ?? payload.day_scope` — the ticket's own day, compared to itself, so `matchesDay` could
   never fail. The console's picker defaulted to "Auto (from ticket)", so nearly every request hit
   it. The offline PWA pins an exact day and was correctly refusing exactly those passes, so the two
   surfaces returned opposite verdicts for the same ticket. **1124 of 2067 tickets (54%) are for a
   day other than Day 1.**
3. **The typed code skipped revocation.** `admitFromRoster` synthesised `nonce: ''`, so the check
   the camera runs could not run at all. The roster now carries each ticket's current nonce and the
   rule moved into `decideCheckin` (pure, exhaustively unit-tested; `useCheckin` has no unit test).
4. **Refusals were never recorded.** `checkin_record` held only `VALID`/`DUPLICATE` — every
   rejection the gate ever made left **no trace**, which is why the original question could not be
   answered from data. Now recorded (reconciler, console path, and the offline outbox via a new
   optional `verdict`), filed under the **reason**. No migration needed: `status` has no CHECK
   constraint and `checkin_record_valid_uq` is **partial on VALID**, so a refusal cannot consume the
   genuine attendee's slot or inflate any count.

## Live verification (not just tests)

- **Roster carries the nonce in prod:** bundle for the live event returned **1099 roster rows, 1099
  with a nonce**.
- **The day fix, proven live and safely** — scanned a real Day-3 pass with **no `dayId`** against a
  **past test event** (never the live festival, so a wrong admit could harm nobody):
  `{"kind":"BLOCK_WRONG_DAY","code":"R8Y8TJZ4GSQH"}`. Pre-fix this returned `ADMIT`.
- **The PWA bundle carries the PROD key** — verified the built `I1` constant is
  `JRLeS3Gqgqa6Hb_Qfg9aYxgbcV8MpIaf3kxNje4DNds` (not the committed DEV fallback) **and** that it
  verifies a real production token, *before* publishing to proxy. This is the check that would have
  caught the historical six-week key-encoding outage.
- **It caught real tickets within 3 minutes of deploy:** 3 `BLOCK_WRONG_DAY` rows at 19:59–20:00 for
  `E8MBNYNXCKKW`, a genuine **Day-3** pass presented on Day 1, retried 3× by the crew — which is
  precisely what "the scanner fails on some tickets" looks like from the door.

## 🔴 The finding that mattered most

The console bug had **already admitted 29 people on Day-2/Day-3 tickets** — and, because it resolved
the day *from the ticket*, filed each admission under **that ticket's own day**. It therefore does
**not** show up as a day mismatch in the obvious query; it looks like a normal Day-3 admission that
simply happened early. The consequence was that those attendees' real-day slot was **already
consumed**, so on 08-22 / 08-23 they would have scanned `DUPLICATE` ("SUDAH MASUK") and been turned
away at the gate they actually paid for.

Re-filed onto Day 1 (the day they physically entered) rather than deleted, so the history stays
truthful and their real day is free. Verified **0 collisions** with an existing Day-1 record first.

**Still open — an operational, not code, issue:** 4 of the 33 were created **after** the fix went
live (20:08–20:09, one staffer, holder "Rendi", 4 Day-3 tickets). Post-fix that requires
**deliberately selecting Day 3** in the console's Day dropdown — an explicit `dayId` still wins by
design. The crew appears to have found that as a workaround for the refusals, and it burns the real
day exactly as the bug did. **The crew must be told to leave the Day selector on "Today
(automatic)"**, and the organizer needs a policy answer for attendees arriving on the wrong day.

## Gotchas hit

- **Server OOM during the build.** Running api + checkin + console builds in one chain got the
  console `typecheck` **SIGKILLed (exit 137)** — swap was at 3967/4095 MB. api and checkin had
  already built fine. Rebuilt console alone with `NODE_OPTIONS=--max-old-space-size=4096`. Typecheck
  had already passed locally, so only the build was actually needed on the host.
- **The old hashed chunk still returns 200** after `rsync --delete` — it is **Cloudflare edge cache**
  (`age` small, `max-age=14400`), confirmed `GONE_FROM_DISK`. Harmless: `index.html` serves the new
  hash, and a device mid-load keeps working.
- **A count taken twice during a live event will differ.** The wrong-day set was 29 at first query
  and **33** by the time the backup ran, because the crew kept scanning. The backup was re-taken
  immediately before the UPDATE and both keyed on the same table, so the write matched exactly what
  was recorded.
- Two identical `let outboxId` blocks in `useCheckin.ts` — a naive string replace hits neither
  safely; anchor on the surrounding comment.
