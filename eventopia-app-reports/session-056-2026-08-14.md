## Full live smoke test — every shipped lane, real prod infra, plus a general transaction pass

**Migration + planner check.** `EXPLAIN (COSTS OFF)` on a real organizer's `orders` query returned
`Index Scan Backward` (no `Sort` node — the performance cliff the notes warn about). It picked the
pre-existing `orders_created_idx` rather than the new `orders_organizer_created_id_idx`; at 994
rows the planner has no cost incentive to prefer one index over another, so this is expected on a
table this small, not a defect — separately confirmed the new index is present and `indisvalid=t`.

**CORS.** `Access-Control-Expose-Headers: X-Correlation-Id,X-Export-Capped,X-Export-Cap` survives
the proxy unmodified (curl with a real `Origin` header against `/readyz`) — the capped-export
banner the csv-export note calls out as "silently dead if this is missing" is live.

**Hardware scanner.** `source:"WEDGE"` and `source:"SCAN"` against a real event id produced
byte-identical `404 NOT_FOUND` responses (auth-scoped lookup failure from the intentionally-bogus
test bearer token) — proves the new enum value is accepted by the same code path as the pre-existing
one, not rejected by a stale zod schema (which would 400 mentioning `source`).

**New route existence.** All 4 new endpoints answered `401` (not `404`) unauthenticated —
`GET /v1/events-orders/export.csv`, `GET /v1/events/{id}/attendees`, `POST
/v1/tickets/{id}/exchange/preview`, `GET /admin/orders/export.csv` — confirming every new route
actually registered on the running API.

**Full general transaction flow (real prod infra, no browser needed).** Disposable organizer via
real email-OTP signup (`smoketest-session056@example.com`, `example.com` per the standing Gmail-
canonicalization gotcha) → `org_a33013d3653d4a32` → published a real `FREE` event/ticket type (no
KYC/MoU gate on FREE tier) → real guest-buyer signup → reserved order → the `free-order-fulfill`
sweep auto-finalized it to **`PAID`** within its normal cadence, issuing a real signed ticket token
+ `shortCode` + WhatsApp deep link → **`GET /t/<shortCode>`** (the apex nginx carve-out) resolved
`200` end-to-end. Also ran the exact check `ticket-exchange-deploy.md` asks for post-deploy: `select
distinct txn_group_id from ledger_entry where order_id = '<this order>'` returned **exactly**
`order:<id>:paid` and nothing else — confirms the exchange feature's new optional `txnGroupId`
settlement parameter left the ordinary money path untouched.

**Bonus: this deploy also ships session-055's same-day e-ticket data-loss fix, undocumented until
now.** Session-055 (earlier today) traced a real bug — WA e-ticket delivery capped at 30/min with
**no backoff**, so all 3 delivery retries fired within the same one-minute window and a paid
buyer's ticket could be permanently stuck `ENQUEUED` with no alert — and wrote a worker-side fix
(exponential backoff, retry attempts 3→6, per-queue concurrency). That fix landed in a same-day
`chore(release)` commit (`a08a14c1`) that swept it in incidentally while bumping other package
versions, without bumping `workers`' own version — `e3929ddf` (the tip of tonight's pull) is the
follow-up commit correcting that miss. Confirmed live in tonight's `eventopia-workers` restart log:
`wa-send limit=30/min attempts=6 backoff=5000ms exponential; concurrency: wa-send=20 emails=10
wa-inbound=10`. This was not one of the 4 documented deploy-note lanes and nearly went unnoticed —
worth calling out because it means tonight's deploy fixes a real, previously-invisible money-safety
gap (paid orders with no ticket delivered) as a side effect, not because anyone asked for it.

## Findings summary

1. **This deploy silently ships session-055's e-ticket data-loss fix** — WA delivery's 30/min cap
   had no backoff, so a paid buyer's ticket could get permanently stuck `ENQUEUED` with no alert;
   the fix (exponential backoff, attempts 3→6, per-queue concurrency) rode in via an unrelated
   `chore(release)` commit (`a08a14c1`) and was confirmed live via tonight's workers startup log.
   Not one of the 4 documented lanes, not called out in any deploy note — worth flagging so it
   isn't lost, since it closes a real money-safety gap. See the smoke-test section above for detail.
2. **Transient `502` on `eventopia-api`'s public `/readyz` for a few seconds immediately after its
   own restart** — the local `:38001/readyz` was already `200` at the same timestamp, so this was
   a proxy-upstream reconnect window, not an app failure. Worth remembering: don't trust the very
   first post-restart health check through the public edge; check the local port too before
   concluding a restart failed.
3. **A testing mistake, not a bug** — see the smoke-test section above. `eventopia.my/<org-slug>`
   redirecting to `.co.id` is long-standing, deliberate nginx behavior (apex = capability paths +
   marketing only, org pages live on `<org>.eventopia.my`), unrelated to and unchanged by this
   deploy.
4. **WhatsApp template appeal (side-check, not part of this deploy): 4 of 5 previously-rejected
   templates are now `APPROVED`**, including both e-ticket delivery templates — `#132001`'s actual
   blocker is closed. `pin_security_idn` is still `REJECTED`/`INCORRECT_CATEGORY`, now filed under
   `MARKETING` while every sibling is `UTILITY` — needs a category fix in
   `packages/whatsapp/src/templates.ts` + resubmission, not done this session.
5. **`dev` is 920 commits behind** (stale since session-025, `f8515b9b`) and has not served as a
   pre-prod gate for several sessions now — deployed straight to prod per the established recent
   pattern, but this is a widening gap worth a deliberate decision (catch it up, or formally retire
   it as a validation step) rather than continuing to silently skip it.
