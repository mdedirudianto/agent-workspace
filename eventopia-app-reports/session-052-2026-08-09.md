## Full live smoke test — every shipped feature, real prod infra

### Late-payment seat reclaim

The 3 pre-existing stranded orders were the test. **All 3 recovered on the sweep's very first
pass** (`RECOVERED 3 stranded paid order(s) (of 3 checked)`, 17:00:24–17:00:37): orders flipped
`SUCCEEDED`/`PAID`, tickets `ISSUED` (2 tickets on the newest order), all 3 `recon_mismatch`
rows flipped `OPEN`→`RESOLVED`. Ledger check: all 3 were `DIRECT`-collection orders, so (per
design) no `buyer_refundable`/`no_inventory_hold` leg was booked — only the normal
`direct_settlement` DEBIT/CREDIT pair, confirming `settlement_clearing`/`buyer_refundable`
accounting is correctly skipped for DIRECT per the followups doc's item #1. New `POST
/v1/payments/{orderId}/recheck` endpoint exercised end-to-end with real org auth against a genuine
PENDING QRIS order: correctly polled Xendit and returned `NO_PAYMENT_FOUND` / `not_captured`.

### Checkout lead capture

`POST .../checkout-lead` on an unknown event → 404 (no existence leak). On a real published
event (`National Ocarina Festival`) → `{ok:true, resumeToken}`; DB row confirmed tenant-scoped
(`org_b6966137a3254ada`), `status:OPEN`, `furthest_step:TICKETS`, `name`/`phone` both NULL — the
identity-free step-write the RLS policy is built to protect. Smoke row deleted, re-verified gone.

### Operator invite / removal

Bootstrapped a disposable Super Admin (properly this time), logged in (`/admin/auth/login` on
`api.eventopia.my`, not the console frontend — first attempt 404'd hitting the wrong host),
invited a throwaway `@example.com` address via `POST /admin/access/operators`. Confirmed:
- `sent:true, url:null` — correct, since prod has `EMAIL_PROVIDER=resend` configured (the raw
  link is only surfaced when mail is provably unconfigured).
- **Delivery write-back proven truthful**, the release's headline feature: real Resend send
  attempted, real `RESEND_422` (expected — `example.com` bounces, same as session-051's
  ticket-resend test), `invite_delivery_status` correctly landed `FAILED` with the error code
  visible via the list API.
- `includeRemoved=false`/`true` coercion fix confirmed both ways (the release's `z.coerce.boolean()`
  bug: `"false"` used to parse as `true`) — `false` correctly excludes the removed row, `true`
  correctly shows it with `status:DELETED`.
- `DELETE /admin/access/operators/{id}` (remove/tombstone) and `POST .../purge` (redact) both
  exercised — purge correctly redacted email/displayName to `removed+<id>@invalid` /
  "Removed operator", refused nothing since the row was already removed first.
- Audit trail: `operator.invite` (seq 184) and `operator.remove` (seq 185) both recorded with
  correct before/after snapshots, reasoned; `operator-audit-verify` sweep re-ran clean afterward
  (only the known pre-existing seq-56 break, no new one — confirms the audit-chain Date-hashing
  fix holds for real writes).

**Gap, not a blocker:** could not complete the accept-link→sign-in leg of the lifecycle. The raw
invite token only ever exists in the BullMQ `emails` job payload, which is configured
`removeOnComplete:true` — no reliable read-after-the-fact window, and no throwaway inbox was
available to receive the actual email. Everything up to and including delivery, plus removal and
purge, was proven live; the "click the link, set a password, sign in as the new operator" step
was not. Worth a real inbox on hand for a future session touching this surface.

## Findings summary

1. **Clean deploy, zero incidents** — but the highest-stakes one yet: caught a real,
   already-live money-affecting bug (the reclaim pre-flight query) before it could cause a
   silent false-negative, and it wasn't hypothetical — 3 real orders were sitting exactly where
   the corrected query said they would be.
2. **All 3 features proven working against real prod infra**, including the two riskiest
   mechanisms in the release: the auto-retry sweep (proven on real pre-existing data, not
   synthetic) and the delivery-truthfulness pipeline (proven via a real failed Resend send, not
   assumed).
3. **One process gap surfaced and corrected in real time**: running `bootstrap-operator.ts`
   without the full `.env` silently degrades to an insecure PII-encryption fallback — caught via
   the script's own warning, not a downstream failure. Worth remembering: any one-off script
   invocation on this app must use `--env-file=../../.env`, not manually-extracted individual
   vars, even for scripts that look like they only need `DATABASE_URL`.
4. **Minor gap, not a regression:** the operator-invite lifecycle's accept-link→sign-in leg
   wasn't verified end-to-end — the raw token has no after-the-fact read path
   (`removeOnComplete:true` on the email job) and no test inbox was available. Delivery,
   audit, remove, and purge were all proven; only the "click the link" step wasn't.
5. **Carried forward, unchanged:** `operator_audit_log` hash-chain break at seq 56 is now 6
   sessions and 30 days old (017→025→048→049→051→this one), still isolated to one known
   QA-test row, still non-urgent.
