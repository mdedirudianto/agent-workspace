## Report

### Root cause — one line, and two artefacts that hid it

`packages/payments/src/xendit.ts:823` (pre-fix):
```ts
const ok = isSuccess(data.status ?? raw.status);   // → 'payment.succeeded' : 'payment.failed'
```

Xendit's **VA-paid callback (`fva_paid`) carries no `status` field**. It is a "this happened"
event — the callback's *identity* is the success signal. The payload is flat: `id`, `payment_id`,
`callback_virtual_account_id`, `external_id`, `account_number`, `bank_code`, `amount`,
`transaction_timestamp`, `merchant_code`.

So `isSuccess(undefined)` → `"UNDEFINED"` → not in
`['COMPLETED','SUCCEEDED','PAID','ACTIVE','SUCCESS']` → **`payment.failed`**. Settlement
(`apps/api/src/modules/payments/settlement.ts:177`) then marked the intent `FAILED` and left the
paid order to die on its TTL.

The wrong belief was written down in two places, which is why it survived ~6 weeks:

1. `xendit.ts:235-236` — *"`ACTIVE` … is meaningful on an inbound webhook (**a VA-paid callback
   carries it**)"*. It does not. `ACTIVE` is the VA **object's** lifecycle status, confirmed live
   via `GET /callback_virtual_accounts/{id}`.
2. `packages/payments/test/xendit.test.ts:363` — a test literally named *"a REAL flat VA paid
   callback"* that passed **only because its fixture injected `status: 'ACTIVE'`**. It asserted a
   shape Xendit never sends. A green test suite was actively vouching for the bug.

### Evidence gathered before touching anything (read-only)

| Method | SUCCEEDED | FAILED |
|---|---|---|
| QRIS | 36 | 0 |
| **BRIMO** | **0** | **42** |
| VA | 1 | 10 |

**BRImo had never once settled in production.** QRIS is unaffected — its webhook nests under
`data` with a real `status`. The single VA success was `pr-9dbec9a6…`, a **v3 payment_request**,
whose webhook *does* carry a status. `isSuccess` was unchanged since the original Xendit commit
(`62d452cf`), so this was **long-standing, not a regression from session-047**.

Confirmed the money truly landed via Xendit's Transactions API (`status: SUCCESS`,
`settlement_status: SETTLED`, `cashflow: MONEY_IN`, matching amount, `reference_id` = our order
id, `product_id` = the exact `provider_event_id` we had recorded).

**Blast radius, measured not assumed:** cross-checked **all 70** non-succeeded VA/BRIMO intents
across both orgs against Xendit — exactly **2 were really paid**. The other 68 were genuine
non-payments (VA *lifecycle* callbacks, which *do* carry a status and correctly mapped to failure).
Preserving that behaviour became an explicit requirement of the fix.

**Why nothing recovered it:** `getPaymentStatus` returned `null` for VA ids *by design* — an
unpaid VA also reads `ACTIVE`, so polling the VA object could mint free tickets. The
`payment-reconcile` worker therefore skipped VA entirely. One bad webhook = permanently lost
ticket, with no backstop.

## The fix (`6899e8b8`, 5 files, +323/−25)

1. **Recognise a VA payment by identity, not status.** `isVaPayment` = has
   `callback_virtual_account_id` **and** a payment marker (`payment_id`/`transaction_timestamp`/
   `amount`) **and** `!isFailureStatus(status)`. The last clause is belt-and-braces in the
   money-losing direction: if Xendit ever adds that field to a lifecycle callback, an explicit
   `EXPIRED`/`INACTIVE` still wins and we never mint a ticket for an unpaid VA.
2. **Three-way mapping, matching the other adapters.** `doku.ts:378` and `midtrans.ts:486` both
   route unknown statuses to `payment.pending` (which settlement ignores *before* claiming the
   idempotency key, so a later terminal notify still processes). Xendit was the only adapter
   turning "not a recognised success" into a **terminal** failure. Disbursement left binary on
   purpose — routing an unknown payout status to `pending` would silently stall payouts.
3. **Reconciler backstop (new).** VA can finally self-heal. `getPaymentStatus` gained an optional
   `ctx: { orderId, amountMinor }`; for VA it now polls `GET /transactions?reference_id=<orderId>`
   — the **capture ledger**, not the VA object — accepting only `type=PAYMENT` +
   `status=SUCCESS` + `cashflow=MONEY_IN` + **exact amount match**. The VA object is still never
   polled, so the original free-ticket hazard is untouched.
4. **Observability.** `parseWebhook` now logs the decision *inputs* (event name, whether a status
   was present, `isVaPayment`, `isDisbursement`, resolved type/ref) — never the body, which
   carries buyer PII and account numbers. Raw bodies were logged nowhere, which is precisely why
   the payload shape had to be inferred from Xendit's docs during diagnosis.
5. **Tests.** Fixed the misleading fixture; added the real statusless `fva_paid` payload, the
   `INACTIVE`/`EXPIRED` guards, unknown-status→`pending`, the unpaid-`ACTIVE` free-ticket guard,
   and four `getPaymentStatus` ledger cases (capture / none / amount-mismatch / `MONEY_OUT`).

**Suites green before restart:** payments **285 pass / 0 fail**, api **1755 pass / 0 fail**.
(`tsc --noEmit` on `apps/api` OOMs — the documented session-009/020 gotcha, pre-existing and
unrelated; Bun strips types at runtime and both suites execute the changed code.)

## Findings summary

1. **A green test suite was vouching for the bug.** The fixture that made
   *"a REAL flat VA paid callback"* pass contained a field Xendit does not send. Worth remembering
   as a class: a test whose fixture is invented rather than captured proves only that the code
   agrees with the author's belief.
2. **The same wrong belief was load-bearing in a code comment**, which made it read as
   deliberate design during review rather than an error.
3. **Xendit was the only gateway adapter without a `payment.pending` path.** DOKU and Midtrans
   both had it, and settlement already supported it — the convention existed and simply hadn't
   been applied here, turning every unrecognised status into a terminal failure.
4. **"Deliberately not polled" had drifted into "unrecoverable."** The money-safety reasoning for
   not polling the VA *object* was correct, but it left VA with no backstop at all. The
   Transactions API answers the right question ("was there a capture?") and was available the
   whole time.
5. **Minting is not settling.** Session-047's BRImo smoke test exercised VA minting and redirect
   decryption and passed — it could never have caught this, because the failure is in the inbound
   settlement path. Payment features need a test that closes the loop, not just opens it.
6. **The 409 burst seen during the restart was a symptom, not a regression** —
   `ORDER_NOT_PAYABLE` from buyers retrying orders this very bug had already expired.

## Open follow-ups (new, session-048)

- **A FAILED intent whose order already EXPIRED is still not auto-recovered.** The sweep only
  picks up `PENDING` intents with a live reservation, and settlement would record such a case as
  terminal `SETTLED_NO_INVENTORY` rather than fulfil it (`settlement.ts:198-206`). That is correct
  when seats are genuinely gone, but it means any *future* money-in/no-seat case still needs the
  manual reopen-and-replay treatment used here. Worth an operator-facing tool.
- **A flat VA lifecycle callback with no `callback_virtual_account_id` is classified as a
  disbursement** (it has `bank_code` and no collect marker), so it is *ignored* rather than
  failed. Benign today and pre-existing — surfaced by the new tests, not introduced by them —
  but the disbursement heuristic is doing more work than its name suggests.
- **Consider a paid-webhook canary.** BRImo settled 0 of 42 for weeks with nothing alerting. A
  simple "gateway X has had N captures and 0 settlements in 24h" check would have caught this on
  day one.
