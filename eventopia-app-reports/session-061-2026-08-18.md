### The real bug: gate #1 and gate #2 disagreed on consent

Ran an independent adversarial `/code-review high` pass in the background while standing up
`LANE=5`. Before it returned, **live testing against the real lane already caught something the
review would also catch**: seeded a real EXPIRED order whose only consent signal was a linked
`checkout_lead` (no CRM contact) — the exact shape session-059/060 identified as the highest-value
case (a buyer who typed a phone/consent at checkout, then let payment lapse). The API's
create/preview endpoints correctly counted this recipient as sendable (gate #1, in
`events-broadcast/repo.ts`, added in session-060). But `POST /v1/events/{id}/broadcasts` followed
by the real worker fan-out **silently re-skipped the exact same recipient as `NO_CONSENT`**.

**Root cause:** `apps/workers/src/processors/broadcast-repo.ts::loadPending` — the worker's
send-time consent re-check ("gate #2") — joins `checkout_lead` only via
`broadcastRecipient.leadId`, which is **always null for an ORDER subject**. It never looked at
`checkout_lead.order_id`, the link session-060's new audience actually depends on. Before this
branch, every ORDER-sourced MARKETING recipient (`EVENT_ATTENDEES`) got its consent from `contacts`
only, so this gap was invisible — the worker's `contactId`-based join always agreed with reality by
coincidence, never exercised for lead-only consent.

**Fixed** with the same `bool_or` scalar subquery pattern the create-time query already uses
(order_id-keyed, avoiding join fan-out since nothing constrains `checkout_lead.order_id` to be
unique), in the same lead-wins-over-contact precedence — getting *that* backwards is silent too:
`??` only skips `null`/`undefined`, so a real `false` contact value would be used ahead of a `true`
lead value instead of falling through past it.

**Proven both ways**: added a real end-to-end regression itest (real HTTP create → real worker
fan-out) in `apps/api/test/event-broadcast.itest.ts`. Confirmed it fails against the pre-fix code
(`git stash` the fix, re-run — fails exactly as the live test showed) and passes against the fix.
Writing that test surfaced its own trap: `createInMemoryAppDeps()` defaults **both** the core
events module and the events-broadcast module's write side (`broadcastsRepo`) to in-memory fakes —
only `eventAudienceRepo` (the read side) is real by default. Without overriding `eventsRepo` and
`broadcastsRepo` too, the test's `POST /v1/events` and campaign-create calls would have silently
written to memory instead of the test DB, and every assertion would have passed vacuously against
empty tables (id patterns like `evt_fake_0001`/`bct_fake_0001` were the tell).

## Findings summary

1. **A real, would-have-shipped-silently bug**: the worker's independent consent re-check
   disagreed with the API's create-time decision for the highest-value segment of this feature
   (lead-only consent, no CRM contact) — found by live testing, confirmed by independent review,
   fixed, and pinned with a regression test proven to fail on the old code.
2. **6 more real findings from independent review, fixed**: a defense-in-depth gap, a latent
   click-routing fragility, a missing parity test, an inaccurate (and pre-existing, now also fixed)
   UI caption, and two stale doc/comment spots.
3. **2 legitimate items explicitly deferred**, filed in a dedicated follow-up doc rather than
   expanded into this branch — an unmeasured performance question and a 2-site DRY call.
4. `createInMemoryAppDeps()`'s "which deps default to real DB vs. in-memory fake" split is a real,
   non-obvious trap for anyone writing a fresh real-HTTP itest in this codebase — worth remembering
   for next time (`eventAudienceRepo` real by default; `eventsRepo`, `broadcastsRepo` fake by
   default; check each dependency's default individually rather than assuming `runTenantFor` alone
   routes everything to the real DB).
