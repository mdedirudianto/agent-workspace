## Report

Follow-up to [session-059](session-059-2026-08-18.md)'s read-only finding: for "Festival Mbois 11 -
Concert," 220 EXPIRED orders (real buyers who reached payment and had a live cart) were unreachable
by either existing broadcast audience — `EVENT_UNPAID_ORDERS` deliberately excludes them (dead
payment link), `EVENT_LEADS` only reads `checkout_lead`, never `orders`. User asked to close this
gap; planned in plan-mode with 3 parallel Explore agents (audience/campaign pipeline,
checkout_lead↔order consent linkage, WA template send path) before writing any code, then
implemented per the approved plan.

### What shipped (code, not yet deployed)

New **`EVENT_EXPIRED_ORDERS`** ("Expired orders") audience, `orders.status IN ('EXPIRED',
'CANCELLED')`, paired with a **new** MARKETING template `order_expired_recovery` — deliberately a
different body from `lead_recovery_promo` (which falsely claims "keranjang kamu masih tersimpan"
for a dead payment session; the new copy honestly offers a fresh purchase, "Pesan tiket baru").
`linkKind: 'EVENT'` — a union member that existed in `contract.ts` since the first release but was
never used — sends the click straight to the plain public event page via the existing
`resolveCampaignClick` fallthrough (proven by direct read: needed **zero** new code there).

**Consent, the actual blocker session-059 named:** `orders` has no consent column. Resolved from
data that already exists rather than a schema change — `checkout_lead.consent_marketing` via
`checkout_lead.order_id` (a scalar `bool_or` subquery, not a join — nothing constrains
`order_id` to be unique, confirmed by one research agent, and directly itest-proven: two lead rows
sharing one order do not duplicate it), falling back to `contacts.consent_whatsapp` (the same
signal `EVENT_ATTENDEES` already uses), defaulting `false` — fail-closed — when neither exists.
**No migration**: `audience_kind`/`template_key`/`link_kind` are plain `text` columns, confirmed by
reading `packages/db/src/schema/crm.ts` directly rather than assuming.

### A pre-existing lint gap, found and left alone

`campaignVariables`'s existing `order_payment_reminder` / `_self_serve` fallthrough already fails
ESLint's `no-fallthrough` on unmodified `main` — proven by lint-checking the file's `main` content
in isolation. My own new fallthrough (`lead_recovery_promo` / `order_expired_recovery`) initially
replicated the same bug; traced it to a real ESLint quirk — the `falls through` comment pattern is
only recognized when it is the LAST comment line immediately before `case`, not anywhere in a
preceding multi-line explanatory block (isolated with 3 scratch-file experiments before finding the
exact rule). Fixed for my own new code; left the pre-existing one alone as out of scope.

## Findings summary

1. Closed the gap session-059 found: 220 real, high-intent EXPIRED-order leads on one live event
   are now reachable by a bulk campaign, gated on a real (if partial — box-office/manual orders and
   some browser sessions will still show `NO_CONSENT`, by design) consent signal, with **zero
   schema migration**.
2. Found and worked around a pre-existing (main) `no-fallthrough` ESLint gap in
   `campaignVariables`, without fixing the pre-existing instance (out of scope).
3. `packages/api-client/src/schema.d.ts` drift is a real, silent trap for any OpenAPI-schema
   change in a fresh worktree/branch — `gen:openapi` then `gen:types` must both run, or the
   frontend typechecks against a stale contract with no compile error until the new field is
   actually used.
