## What prompted this

A user report: *"user buy 100 tickets, but only few or around 60 tickets sent."*

## Root cause

Production data, not inference. Order `ord_e11d404a` ("BRI SPONSOR"): **100 tickets
issued, 43 delivered.** The other 57 sat at `delivery_status='FAILED'` with Meta's
verdict recorded 937 times in `order_event`:

```
(#131056) (Business Account, Consumer Account) pair rate limit hit
```

A per-**(business, consumer)** throttle. Nothing to do with our own limiter — prod runs
`WA_SEND_LIMIT_PER_MINUTE=600`. E-tickets were sent one message **per ticket**, so any
bulk order to one buyer was guaranteed to trip it. And the delivery sweeper matched
`delivery_status = 'PENDING'` only, so a ticket written `FAILED` was out of reach of
every recovery path that existed.

**Issuance was never the problem.** All 100 rows existed, `seat_index` 0–99, one
statement, no truncation.

**Blast radius, measured:** 216 tickets across 22 orders had reached the buyer on
**neither** channel (every one of those orders has `buyer_email IS NULL` — checkout is
WhatsApp-first, so email could not back it up). 211 belonged to **Festival Mbois 11,
which started the same day.** Independent confirmation of the pair-limit diagnosis:
Pengurus KORMI, Ketua INORGA and Sekretaris INORGA are three orders on **one** phone
(`+6285745208894`) totalling 125 tickets.

## What was already fixed, and by whom

(`5ad50b95` + release `bd147b38`): grouping by **recipient**, `orders.pass_code` →

migration 0162. Better than the by-order grouping this session had planned. **It was
merged and pushed but never deployed** — prod was still on `1b462705`. This session
deployed it, rescued the stranded tickets, and then closed the one hole it left.

## 🔴 Mistake made, and its cost

**I restarted only `eventopia-api` after deploying the other-channel guard. The delivery
sweeper runs in `eventopia-workers`.** Workers kept the previous build, and its first
tick re-drove every WhatsApp-failed ticket whose **order email had already been sent** —
the population the user had explicitly said to leave alone.

- **~911 tickets / ~731 e-ticket messages** went out (`695 eticket` + `36 eticket_link`).
- **Est. cost ≈ Rp 313,000** (~USD 20).
- **Mitigating:** 895 of them were **Festival Mbois 11 — the event running that same
  day**, so those recipients got a usable QR in WhatsApp alongside the email they had.
  Only ~15 went to genuinely past/test events.
- Caught within one tick; workers restarted; verified quiet afterwards (subsequent
  traffic was `INBOX_REPLY` only, zero `ETICKET`).

**Lesson, now in the deploy note:** api and workers are ONE unit for anything touching
delivery. The sweeper, the write-back and the send all live in workers; api only
produces. Restarting half is not a partial deploy, it is a silent no-op on the half
that matters.

A second, related near-miss was caught *before* it fired: migration 0163's fresh columns
read as "never tried", making all 911 already-emailed tickets newly eligible. Parked them
above the attempt ceiling on prod to stop the tick, then made it principled in code
(`ne(emailDeliveryStatus,'SENT')` on the recovered states only) and restored the honest
counters. That guard is what finally held.

## What shipped in Phase 3 (the hole grouped delivery left)

Grouped delivery stopped the fan-out but built no way back. A ticket outside `PENDING`
was unreachable: retries exhausted on a retryable error left the row `ENQUEUED` with
nothing writing the final word; a permanent error wrote `FAILED`; the sweep matched
`PENDING` alone.

- Sweep now reaches `PENDING | ENQUEUED | FAILED`, **bounded** — `PENDING` keeps its old
  immediate/unbounded contract (it means no send was ever made), while the recovered
  states are paced by `tickets.delivery_attempts` + a cooldown, and skipped entirely when
  the order email already landed.
- `wa-send.on('failed')` writes `FAILED` once BullMQ has no attempts left, so an
  exhausted job stops reading "in flight" forever.
- Rate limiter returns the token on refusal (it was `INCR`-before-check, so a refused
  attempt spent budget and starved later windows).
- Operator order view now carries `delivery_attempts` / `delivery_last_attempt_at`.

## Addendum — `eticket_order_idn` submitted, and the template mirror de-drifted

**Submitted `eticket_order_idn` to Meta via the API.** Status: **PENDING**, category
**UTILITY**, Meta id `2251706935625924`. `WA_ETICKET_ORDER` stays **unset** (verified
absent from both `.env` and the running api process) until it is APPROVED — grouping
works without it by borrowing the approved `eticket_delivery_link_idn` body.

The risk was surfaced before submitting and accepted by the user: this exact family was
rejected `INCORRECT_CATEGORY` twice via the API (`_id`, then `_v2_id`), and the versions
approved today were submitted by hand in Business Manager. **A `(name, language)` slot is
locked at Meta permanently once created, even rejected**, and this codebase has no
delete/edit call — so a rejection would burn the name the code references. It did NOT
reject instantly the way the `_v2` batch did (those came back within minutes), so it is
in genuine review.

Payload verified before sending: 4 body vars / 4 examples, and a DYNAMIC_URL button on
`https://eventopia.my/p/{{1}}` — the real prod apex, whose `/p/` nginx block this same
session added. Meta freezes that prefix at approval, so it had to be right the first time.

**Removed 10 stale rows from the `wa_template` mirror.** The user asked for the `_v2`
templates; checking first changed what the job was:

- **Meta holds 28 templates and none of the five `_v2` names are among them** — they had
  already been deleted at Meta, along with the five original `_id` rejects.
- The rows were stale in OUR mirror. **`syncTemplatesFromMeta` upserts and never prunes**
  (`packages/whatsapp/src/template-ops.ts:232`), so anything deleted at Meta lingers
  forever showing REJECTED in the operator console. That is the root cause and it will
  recur — see follow-ups.
- Checked before deleting: `registry_key` is **not** unique, and 5 of the stale rows
  shared a key with a live APPROVED row. That would matter if the send path resolved
  templates from this table — **it does not.** The mirror is read only by the operator
  console's Template registry view and by the sync itself; sends use the in-repo registry
  and address Meta by name. So the rows were display-only noise, not a send hazard.
- Snapshotted to `db:/root/eventopia-backups/wa_template-stale-20260821.csv` first, then
  deleted by explicit name. Mirror went 38 → **28, exactly matching Meta**; a re-sync
  resurrected nothing. The only two non-APPROVED rows left are both real:
  `eticket_order_idn` (PENDING) and `pin_security_idn` (REJECTED, still at Meta).
