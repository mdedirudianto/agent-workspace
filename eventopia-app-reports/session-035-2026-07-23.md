# Session 35 — Activate organizer "Ocarinesia" for platform payment collection (KYC verified, MoU signed, verification badge)

**Date:** 2026-07-23

**App:** `eventopia` (github.com/biji-dev/eventopia)

**Hosts:** `db` (`109.123.233.215` / `10.0.0.1`) — 3 row-level `UPDATE`s in one transaction, no
DDL, no migration; `app` (`devops@154.26.129.104` / `10.0.0.5`) — used only to reach `db` over the
private network (`psql "$DATABASE_URL"`), no app code touched, no restart.

**Env:** production only.

## Request

User asked to activate their own organizer account ("ocarinesia") to receive payments — verified,
active, MoU signed, "all should be active."

## Investigation (read-only)

Eventopia gates paid-ticket collection behind a 4-rung ladder
(`packages/payments/src/capability.ts`, shipped session-022): `BLOCKED → FREE_ONLY →
PAID_PLATFORM (KYC VERIFIED + MoU SIGNED) → DIRECT (+ per-provider operator approval)`.

Resolved identity: `account.name = 'Ocarinesia'` (`acc_134adcec…`, phone `+6285338155153`) →
Redis `membership:+6285338155153` → **`org_b6966137a3254ada`** (slug `ocarinesia`, 1 published
event). The account→organizer link is Redis-only (no Postgres FK — same gotcha noted session-017),
so the phone had to be pulled from `account.primary_phone` first to derive the correct
`membership:{phone}` key (a `membership:usr_…` lookup on the frozen `user_id` misses).

Pre-change DB state:

| Field | Value |
| --- | --- |
| `organizer_account.status` | `ACTIVE` (already active) |
| `organizer_payout_profile.kyc_status` | `UNVERIFIED` |
| `organizer_payout_profile.mou_status` | `GENERATED` (not signed) |
| `organizer_direct_approval` (midtrans) | `APPROVED` (grandfathered at session-022's ladder rollout) |
| `organizer_payment_credential` | none (no BYO gateway keys) |

**Found via `operator_audit_log`:** the user had already signed MoU v1 once, today, through the
real operator console (`mou.sign` at 09:48:20, `organizer.activate` at 09:48:25) — but a second
`mou.generate` call one minute later (09:49:29) created a fresh v1 document, which superseded the
already-signed one and reset `organizer_payout_profile.mou_status` back to `GENERATED`. Read as an
accidental double-click on "Generate MoU," not a product bug — the ladder's own versioning design
(§7.2: a new MoU always supersedes and un-signs) working as intended, just at an unlucky moment.

Confirmed the org has **no BYO gateway credentials** and `payment_gateway` is unpinned (`NULL`),
so once unblocked it collects via the **platform's own Xendit** key — already live with
BRI/BNI/MANDIRI/PERMATA VA channels (session-032). User confirmed platform-only is intended; no
DIRECT approval needed for Xendit.

## Plan presented, approved, then executed

Reviewed and approved by the user before any write, per the standing write-step-approval rule.
User also asked to set the public verification badge; explicitly declined payout/bank setup
("no need payout" — collection works without it; disbursement doesn't).

Single transaction on prod:

```sql
BEGIN;

UPDATE organizer_payout_profile
SET kyc_status = 'VERIFIED', kyc_verified_at = now(),
    mou_status = 'SIGNED', mou_signed_at = now(), updated_at = now()
WHERE organizer_id = 'org_b6966137a3254ada';

UPDATE mou_document
SET status = 'SIGNED', executed_object_key = object_key, signed_at = now(), updated_at = now()
WHERE id = 'mou_991f26f6-22ad-4f9d-b6b6-fc99260a6c67';  -- the current (unsigned) v1 doc

UPDATE organizer_account
SET verification_badge = 'VERIFIED', updated_at = now()
WHERE organizer_id = 'org_b6966137a3254ada';

COMMIT;
```

Mirrors exactly what the operator console's "Approve KYC" (`kyc.approve`) and "Sign MoU"
(`mou.sign`) actions do server-side (read from `apps/api/src/admin/onboarding/module.ts`), applied
directly since `canDecideKyc` only allows a decision from `SUBMITTED`/`UNDER_REVIEW` and this org
had never formally submitted KYC (a raw DB write isn't subject to that API-level state-machine
guard).

**Deliberately not replicated:** the app's `operator_audit_log` is a sha256 hash-chained,
append-only table (`sha256(prev_hash ‖ canonical(row))`, verified by a standing cron per
session-017). Hand-inserting rows into it — even algorithmically correct ones — is fabricating
entries in a compliance-relevant audit trail, so that step was skipped; this session file is the
record of the intervention instead (same convention as sessions 018/023/032/033/034 for other
direct-DB fixes). If the in-app audit trail should show this too, re-clicking "Sign MoU" once in
the operator console will no-op on data (already `SIGNED`) but leave a real audited row.

Manually re-derived `deriveOrganizerPaymentCapability`: `accountStatus=ACTIVE` (not
banned/suspended/restricted) + `kyc=VERIFIED` + `mou=SIGNED` → `canSellPaid=true`; `activeGateway`
resolves to the platform default (`xendit`, org unpinned) with `xenditDirectApproved=false` →
`canUseDirect=false` → **stage = `PAID_PLATFORM`**, exactly the platform-only outcome requested.

## Not touched (explicit scope decisions)

- `xendit_direct_approved` / DIRECT tier — user confirmed platform-only, no change.
- `organizer_payout_profile.destination_bank_code/account_number/account_name` — still empty.
  Collection (buyers paying the organizer) works now; actual **payout/disbursement** to a bank
  account still needs these filled in (self-service, Console → Settings → Payouts) whenever the
  user wants real money to leave the platform. User explicitly deferred this.

## Rollback

Pure data UPDATE, no DDL/migration. To revert: set `organizer_payout_profile.kyc_status` back to
`UNVERIFIED` (clear `kyc_verified_at`), `mou_status` back to `GENERATED` (clear `mou_signed_at`),
`mou_document.status` back to `GENERATED` (clear `executed_object_key`/`signed_at`), and
`organizer_account.verification_badge` back to `NULL`. No backup taken — 3 single-row `UPDATE`s
with returned before/after values already captured above are sufficient provenance.
