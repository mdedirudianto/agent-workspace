# Session 30 — Root-cause: creating a duplicate-name event 500s ("Terjadi kesalahan internal")

**Date:** 2026-07-22
**App:** `eventopia` (github.com/biji-dev/eventopia, branch `main`)
**Hosts:** `app` (`devops@10.0.0.5`), `db` (`root@109.123.233.215`) — **read-only investigation, nothing changed on either server**
**Env:** production
**Status:** diagnosis complete, bug filed in-repo, fix NOT implemented (user's explicit call)

The user reported a generic *"Terjadi kesalahan internal"* toast in the organizer console while
creating an event named **"Festival Mbois 11 - Concert"** on prod.

## Investigation

`pm2 logs eventopia-api --lines 300 --nostream` on `app`, grepped for errors around the report time,
surfaced the real exception (structured pino log, not swallowed):

```
level:50  requestId: 831707fc-6552-41ad-82c9-a068053b8228
err.type: DrizzleQueryError
err.message: Failed query: insert into "event" (...) values (...)
  params: evt_feadf973-…, org_03f297927f184c0d, festival-mbois-11-concert, Festival Mbois 11 - Concert, …
  duplicate key value violates unique constraint "event_organizer_slug_uq"
```

Confirmed on `db`: the organizer already had an event with that exact slug —

```sql
select id, organizer_id, slug, name, status, created_at from event
 where organizer_id='org_03f297927f184c0d' and slug='festival-mbois-11-concert';
--
 evt_8543d237-2d6a-4873-97d8-391bbc2ffd0b | org_03f297927f184c0d | festival-mbois-11-concert
   | Festival Mbois 11 - Concert | DRAFT | 2026-07-17 11:34:39.561422+08
```

**Root cause:** `apps/api/src/modules/events/module.ts:73-88` (`createEventRoute`) generates the slug
from the name (`slug: body.slug ?? slugify(body.name)`) with no de-duplication, and does not catch a
unique-violation on the insert. `apps/api/src/app.ts:721-746` (`app.onError`, the global catch-all)
special-cases only the retryable SQLSTATEs (lock/timeout/deadlock/serialization) — nothing for
`23505` — so the uncaught `DrizzleQueryError` falls through to the generic
`INTERNAL_ERROR` / *"Terjadi kesalahan internal."* 500, with no indication to the organizer that the
real problem is "an event with this name already exists."

**Confirmed as a real gap, not a one-off:** this codebase already has an established pattern for
exactly this class of error — `platform/auth/account.ts` (`isUniqueViolation`, `email-taken`/
`phone-in-use`), `modules/events-promos/repo.ts` (duplicate promo code → clean conflict), plus
`modules/checkin/module.ts`, `modules/domains/module.ts`, `modules/growth/referral/module.ts` all
catch `23505` and return a friendly error. The events module is the one place that doesn't follow
its own codebase's convention for its own unique constraint.

**Not a data problem, not caused by anything this session touched:** the pre-existing `DRAFT` event
was created 2026-07-17, five days before this report and unrelated to session-029's deploy earlier
today. The organizer simply tried to create a second event with the same name, which should be a
normal, allowed action (or at minimum fail with a clear, actionable message) — not a hard crash.

## Action taken

Filed the bug in the eventopia repo's own `docs/engineering/known-issues.md` — the project's
established convention for prod-found bugs not yet scheduled as their own fix session (exact
file:line pointers + concrete scenario, so a future fix session doesn't have to re-investigate).
Also removed that file's now-stale check-in white-screen entry, since session-029 shipped and
verified that fix earlier today — closing the loop in the doc, not just in prod.

**Per explicit user instruction, the code fix itself was NOT implemented this session** — diagnosis
and documentation only. The `known-issues.md` edit is currently a local uncommitted change in the
`eventopia` repo (`/Users/dedi/Projects/eventopia`), left for the user to commit/push on their own
schedule (or ask for in a future session).

**Suggested fix direction** (recorded in the doc): catch the `23505`/`event_organizer_slug_uq`
violation in `createEventRoute` (same `isUniqueViolation` shape used elsewhere in this codebase) and
return a `409 CONFLICT` naming the conflict — or better, auto-disambiguate the generated slug on
collision so two events sharing a display name just works, since that's a normal thing for an
organizer to want.
