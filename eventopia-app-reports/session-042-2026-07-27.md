# Session 42 — Investigate "expired tickets but details say failed" — confirmed NOT a data bug, filed as a UX-clarity gap for the dev agent

**Date:** 2026-07-27

**App:** `eventopia` (github.com/biji-dev/eventopia) — docs-only change (`docs/engineering/known-issues.md`).

**Hosts:** `app` (`devops@154.26.129.104`) — read-only (deployed commit, source files). `db`
(`root@109.123.233.215`) — read-only SQL (`orders`/`tickets`/`payment_intent` counts). No writes on
any host, no deploy.

**Env:** production only.

## Report

User spotted a discrepancy in the admin console: orders shown as `EXPIRED` in the operator order
list, but the order's own detail page appeared to say "failed" somewhere. Asked to crosscheck
app/repo/DB read-only and determine whether it's a real bug before filing anything.

**Investigation.** Checked the deployed commit on `app` (`9d06e015`, session-040's deploy — session-041
was proxy-only, no app-code change since). Read the DB schema (`packages/db/src/schema/sensitive.ts`):
`orders.status` is `PENDING | PAID | CANCELLED | REFUNDED | EXPIRED`; `tickets.status` is
`ISSUED | TRANSFERRED | VOIDED | CHECKED_IN` — no `EXPIRED` value exists on tickets at all, and no
`FAILED` value exists on orders at all. Those live only on a third, separate table:
`payment_intent.status` (`PENDING | SUCCEEDED | FAILED`), one row per gateway attempt.

Pulled the actual admin order-detail page from prod
(`apps/admin/app/(app)/orders/[organizerId]/[orderId]/page.tsx`): the order's own status badge sits
at the top (line 205, renders `d.order.status` directly); further down the same page, a "Payment
attempts" card lists every `payment_intent` row with its own badge (line 322, `p.status`). Two
different objects, two disjoint enums, same screen — "Expired" up top and "Failed" in a row below
is two correct, independent facts, not the same field disagreeing with itself. Confirmed the same
shape in the organizer-facing console (`apps/console/components/orders/order-detail.tsx`), and that
every frontend (admin/console/buyer-facing `pesanan` page) renders `EXPIRED` consistently — nowhere
does the order's own status ever render as "Failed".

Found the design is deliberate, not incidental — `apps/api/src/modules/payments/settlement.ts:176`
has a comment: on a `payment.failed` webhook the code marks the intent `FAILED` and explicitly does
**not** touch the order, so the buyer can retry a different method inside the same reservation
window; the order only flips to `EXPIRED` later via the `order-expiry` sweep
(`apps/workers/src/index.ts:266`) once `expiresAt` passes with no successful attempt.

**Cross-checked against live prod data** (`db`, read-only):

| order.status | orders | tickets (via LEFT JOIN) |
| --- | --- | --- |
| EXPIRED | 95 | 0 |
| PAID | 39 | 33 |
| REFUNDED | 2 | 10 |

| order.status | payment_intent.status | n |
| --- | --- | --- |
| EXPIRED | *(none)* | 52 |
| EXPIRED | PENDING | 34 |
| EXPIRED | FAILED | 9 |
| PAID | SUCCEEDED | 27 |
| PAID | *(none)* | 12 |
| REFUNDED | *(none)* | 2 |

0 tickets exist for any `EXPIRED` order — expected, since tickets only issue at settlement, which
also means "expired ticket" isn't a real state; what the user saw was an *order* that never became
a ticket. Of the 95 `EXPIRED` orders: 52 never had a payment attempt, 34 have one still stuck
`PENDING` (abandoned mid-payment), and 9 have one that's `FAILED` — that last group is exactly the
case that reads as contradictory in the admin UI (order card says Expired, a row below says
Failed).

**Verdict: not a bug.** Working as designed and consistently labeled everywhere; the confusion is
purely presentational — an order-level lifecycle status and a payment-attempt-level gateway status
sit close together on one screen with no explanatory copy tying them together. Filed as a UX-clarity
entry (not a "fix the logic" bug) in the app repo's `docs/engineering/known-issues.md`, with exact
file:line pointers, the live-data breakdown above, and a possible fix direction (an explainer line
under "Payment attempts", or visually separating the two badges) — left as an open call, not
prescribed. Committed locally in the app repo; **not yet pushed**, same "push decision needed"
pattern as prior sessions (032/033/036/039/041).

## Findings summary

1. **Not a bug.** `orders.status` (order lifecycle: PENDING/PAID/CANCELLED/REFUNDED/EXPIRED) and
   `payment_intent.status` (per-attempt gateway result: PENDING/SUCCEEDED/FAILED) are separate,
   correctly-independent fields — both enums are disjoint, so no order ever literally reads
   "Failed," and no payment attempt ever reads "Expired."
2. **Deliberate design, documented in code:** a failed payment attempt doesn't kill the order —
   it's left `PENDING` so the buyer can retry, and only the reservation-TTL sweep moves it to
   `EXPIRED`.
3. **"Expired tickets" is an operator-vocabulary imprecision, not a system state:** tickets have no
   `EXPIRED` status and are never created for an order that didn't reach `PAID` — confirmed 0
   tickets across all 95 `EXPIRED` orders in prod.
4. **Filed for the dev agent** as a UX-clarity gap (not a logic fix) in
   `docs/engineering/known-issues.md`, commit local-only, not pushed.
