**Found + fixed live: the `/i/` nginx exemption alone wasn't enough.** Unlike `/e/`'s pure
302-redirect route (no client bundle), `/i/[code]` is a real rendered page with its own
`/_next/static/*` JS/CSS/font chunks. Those asset requests fell through the apex's blanket
`eventopia.my → eventopia.co.id` redirect (only `/e/` was exempted before this session) and the
resulting cross-origin font fetch got CORS-blocked — fonts failed to load (confirmed via a real
Playwright render: 22 console errors, all font-CORS; page itself fully functional — masked phone,
event name, Confirm button all correct, just system-font fallback). Fixed by adding a third
`location /_next/` block alongside `/e/` and `/i/` on the apex server; verified fixed at the
origin directly (`curl --resolve` bypass → `200`, correct `font/woff2`) — Cloudflare's edge cache
held the earlier 301 briefly (self-corrects within the hour, same documented pattern as the
OG-image cache rule). Documented as an addendum to `docs/launch/crew-invite-confirmation-deploy.md`
for the next apex capability-path launch.

## Findings summary

1. **Nginx apex asset-routing gotcha — found live, fixed live, documented for next time.** A new
   rendered page at the apex needs its own `location` block AND a shared `/_next/` static-asset
   exemption, not just the page path — `/e/`'s pure-redirect precedent didn't need this, `/i/`'s
   real page did.
2. **`check-xendit-va-activation.mjs:339-340` crashes** when `BANKS=` doesn't include `BRI` (Part
   B unconditionally dereferences `fixed['BRI']`) — filed in `known-issues.md`, not fixed this
   session.
3. **`NEXT_PUBLIC_WEB_PUBLIC_BASE`/`NEXT_PUBLIC_SITE_URL`/`PUBLIC_WEB_BASE_URL` drift** from the
   new domain-split table — confirmed functionally harmless live, left as an open alignment
   decision for whoever owns it.
4. **Crew invite, partner-gate, and the Xendit 422 fix all verified live and working correctly** —
   no regressions found in this deploy's core features.
