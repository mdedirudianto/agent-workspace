## Cleanup — verified, not just trusted

The recipe needed extending this session: the admin identity's org-scoped `organizerId` in its JWT
(`org_29e5fc429a23443a`) turned out to be a **different id form** than `organizer_account.id` in
Postgres (`oacc_f649d446-…`) — the public-facing org id used in `org_member`/`event` rows is not the
table's own primary key. First delete attempt against `organizer_account` using the JWT's id
silently matched 0 rows; caught by explicitly re-querying the table by `display_name`/`slug` before
declaring cleanup done, per [[feedback_never_delete_real_data]]'s standing rule to verify residue
rather than trust `DELETE n` output.

Deleted in FK-safe order, single transaction with explicit `COMMIT` (avoiding the
[[reference_eventopia_payment_smoke_test]] silent-rollback gotcha): `org_member` (1) → `event_day`
(1) → `event` (1) → `organizer_account` (1, by its real `oacc_` id) → `account` (2, owner + admin).
Redis: `org:meta:`, `org:slug:`, and the owner's `membership:acc:<id>` home key (no `:org:` suffix —
older per-account schema) — deleted. **Left in place, deliberately:** the admin identity's
`membership:acc:<id>:org:org_demo` key — `org_demo` is the platform's pre-existing shared demo
tenant the bare `intent: attendee` signup lands on by default, not something this session created;
confirmed by pattern-matching before any delete. Re-queried every table and re-scanned every Redis
pattern after deletion — zero residue confirmed.
