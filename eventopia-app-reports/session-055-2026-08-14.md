## FINDING 1 — Paid buyers can permanently lose their e-ticket (critical, pre-existing)

This is the most important thing in this document and it has nothing to do with scaling
architecture. It was found while tracing whether delivery could keep up with "sell out".

### The chain

| Step | Mechanism | Source |
|---|---|---|
| 1 | WhatsApp sends are limited to **30/min per number**, fixed window | `workers/src/index.ts:116` — `WA_SEND_LIMIT_PER_MINUTE ?? '30'` |
| 2 | Over the limit, the processor **throws** — it does not defer | `processors/wa-send.ts:195` — `if (!(await deps.rateLimiter.tryConsume(...))) { … throw }` |
| 3 | Jobs were enqueued `{ attempts: 3 }` with **no backoff**, so all 3 retries fire within milliseconds — **inside the same 60s window**, so all 3 fail | `workers/src/index.ts:137` (pre-fix) |
| 4 | The throw happens **before** `deps.eticketDelivery` runs, so the ticket is never marked FAILED — it stays **`ENQUEUED`** | `wa-send.ts:195` precedes the `eticketDelivery` call |
| 5 | The recovery sweeper only re-enqueues tickets left **`PENDING`** | `payments/delivery.ts:617` — `eq(tickets.deliveryStatus, 'PENDING')` |
| 6 | **Result: ticket stuck at `ENQUEUED` forever. Buyer paid. No ticket. No retry. No alert.** | — |

Step 4 is what makes this unrecoverable rather than merely late. Had the ticket been
marked `FAILED`, it would at least be visible to an organizer chasing it. `ENQUEUED` reads
as "in flight" indefinitely.

### Why it will trigger tonight

30/min is **0.5/sec**. The goal is to sell thousands. Even at BullMQ's serial default the
worker attempts ~2–3 sends/sec, so **the limiter is already the binding constraint at
normal speed** — it does not take a spike. Roughly: any minute in which more than 30
tickets settle starts dropping e-tickets permanently.

**Correction from the first draft:** `.env` on `app` did not leave this at the code
default — line 40 explicitly set `WA_SEND_LIMIT_PER_MINUTE=30`. Someone deliberately
configured the conservative value, which changes nothing about the risk but matters for
the record: this was a live, intentional setting, not an oversight of an unset default.

### Mitigation — DONE, verified live (18:14 WIB)

**M1 — raised `WA_SEND_LIMIT_PER_MINUTE` 30→600 in `.env`.** This makes the limiter
non-binding under any plausible tonight volume, so the throw path in step 2 stops firing.

```
app .env line 40:  WA_SEND_LIMIT_PER_MINUTE=30  →  WA_SEND_LIMIT_PER_MINUTE=600
```

600/min = 10/s — 20× the prior value, still an order of magnitude under Meta Cloud API's
~80/s default throughput. Backup taken first: `~/eventopia/.env.bak-20260814-pre-onsale`.

> ⚠️ **`pm2 restart --update-env` does NOT reload `.env` here** (session-054).
> `ecosystem.config.cjs` parses `.env` itself at load time. Used
> `pm2 startOrRestart ecosystem.config.cjs` and verified — see
> [Execution log](#execution-log-1814-1816-wib).

Also set `PG_POOL_MAX=25` in the same `.env` (was unset, defaulting to 10) — the read path
(order lookups, `/pesanan/…`, ticket views) was queueing behind checkout transactions in a
10-slot pool against a `max_connections=200` ceiling with only 19 eventopia connections in
use.

**M2 — the code fix — DEPLOYED to prod** (see [Code status](#code-status)). Exponential
backoff spreads retries across *several* rate-limit windows, which is what a fixed-window
limiter actually needs, and raises the attempt ceiling so a sustained spike *delays* an
e-ticket instead of dropping it. Plus per-queue concurrency (`wa-send` 1→20, `emails`
1→10, `wa-inbound` 1→10) so BullMQ is not the narrower constraint. Confirmed live via the
worker's own startup log:

```
[workers] concurrency: wa-send=20 emails=10 wa-inbound=10 (others=1);
          wa-send limit=600/min attempts=6 backoff=5000ms exponential
```

M1 and M2 together mean the limiter is both higher AND the retries that do hit it are
spread out — belt and suspenders.

## FINDING 2 — The checkout lock (config, untouched per user)

Every order creation funnels through `reserveOrder`
(`apps/api/src/modules/events-orders/quota.ts`). Its lock ladder:

1. `pg_advisory_xact_lock(eventId)` — **only when `event.max_tickets` is set**
2. `SELECT ticket_type … FOR UPDATE` — **always**, ascending id
3. `SELECT event_day … FOR UPDATE` — **only for days where `capacity IS NOT NULL`**

### How the events are actually configured

| Config | State | Consequence |
|---|---|---|
| `event.max_tickets` | **NULL** on all 7 mbois events | ✅ No event-level advisory lock |
| `ticket_type.quota` | **NULL** on the concert types | ✅ Per-type usage `SUM` skipped (`quota.ts:349`) |
| `event_day.capacity` | **SET — 4000 / 5000 / 10000** | ❌ Day lock **and** day scan both run |

So two of the three lock paths are already inert. **Only the day capacity is biting — and
per answer 1, it is not even wanted.**

### Why it costs what it costs

The day-capacity check runs a three-table aggregate whose `OR` spans **two different
tables**, which no index can satisfy:

```
Join Filter: ((oi.event_day_id = 'evd_23de…') OR (tt.scope = 'FULL_EVENT'))
->  Seq Scan on order_item oi  (actual time=0.009..1.438 rows=1026)   <-- whole table
Aggregate (actual time=3.431..3.436)
```

It runs **once per capacity-bearing day**, so a 3-Day Pass checkout runs it three times
while holding `FOR UPDATE` on all three day rows. And the `event_day` lock is far wider
than a ticket-type lock: it serializes buyers of *every* type touching that day.

**Honest caveat:** the `Seq Scan` is chosen *because* the table is currently 1026 rows. As
`order_item` grows while a single event's `orders` set stays comparatively small, the
planner will likely switch to a nested loop on `order_item_order_idx`, which scales with
the event's orders rather than the whole table. So degradation is real in direction,
**uncertain in magnitude**. That uncertainty is itself an argument for removing the lock
rather than modelling it.

### Decision: leave the capacity values as the organizer set them

The user was explicit: **do not touch DB values set by the organizer — focus only on
infra, code, or config.** `event_day.capacity` is organizer data, not infrastructure.
**The null-capacity change described in the first draft of this document was NOT
executed, and per the user's instruction it will not be.**

The code is explicit (`quota.ts:414`) that a null capacity skips both the lock and the
scan — that remains true and is recorded here for completeness, not as a live option:
*"**Both branches filter `capacity IS NOT NULL`** so a day with no cap is NEVER locked —
an unlimited single-day event stays fully concurrent."*

### Why this is acceptable to leave as-is

With the lock and scan both still in play, the estimate from the first draft was ~50
orders/sec at current row counts (1026 `order_item` rows), degrading toward ~14–25/sec if
`order_item` grows to 5–10k rows **and** the planner stays on a Seq Scan. Even at the
pessimistic end, that is roughly 1000/min — **10k tickets in ~10 minutes**. The 10s
`PG_LOCK_TIMEOUT_MS` only starts shedding requests around ~140 concurrent checkouts
queued on the same day lock simultaneously, which is a lot of simultaneous buyers on one
event.

**The mitigation actually applied is [infra step 3](#step-3--db-planner-statistics-not-organizer-data),
below: refreshed Postgres planner statistics.** That doesn't touch capacity — it only makes
it more likely the planner picks the cheaper nested-loop plan (via `order_item_order_idx`,
which scales with the event's own order count rather than the whole table) as the table
grows tonight, instead of staying on the Seq Scan the whole time. It's insurance against
the pessimistic case, not a guarantee — the plan choice is the planner's, not something
`ANALYZE` can force.

**If lock contention does bite tonight** (watch `pg_stat_activity` for `wait_event_type='Lock'`
per [What to watch](#what-to-watch-from-1845)), the fix is still available as a decision
for the organizer to make live, not something to pre-empt:

```sql

FROM event_day ed JOIN event e ON e.id = ed.event_id

  AND e.slug LIKE 'festival-mbois-11%'
```

[Follow-ups](#follow-ups)).

## FINDING 3 — nginx ceiling on `proxy` (fleet-wide) — FIXED

`worker_connections 768` (Ubuntu default) × 4 workers, but `worker_rlimit_nofile` was
**unset** and the master's soft `nofile` was **1024**. Each proxied request costs two
descriptors, so the fd limit bound first: **~512 in-flight proxied requests per worker,
~2000 fleet-wide** — shared with hoteru, grobiz, seenow, ytgrab, meetgrab and everything
else behind this proxy.

Also **no `keepalive` on any eventopia upstream block**, so every proxied request opened a
fresh TCP connection to `10.0.0.5`. At idle the proxy already showed 274 sockets in
`TIME_WAIT`.

### Applied at 18:15 WIB, reloaded, verified

Backed up first: `/root/nginx-bak-20260814/{nginx.conf,eventopia*.conf}`.

`/etc/nginx/nginx.conf`:
```diff
+worker_rlimit_nofile 65535;
 events {
-	worker_connections 768;
+	worker_connections 4096;
 }
```

`/etc/nginx/sites-enabled/eventopia.conf` — keepalive on all 4 upstreams, and the
`Connection` map fixed so keepalive can actually take effect (nginx keepalive requires
`proxy_http_version 1.1` + a non-`close` `Connection` header on non-upgrade requests; the
original map sent `close` for every non-WS/SSE request, which defeats keepalive silently):
```diff
-upstream eventopia_api     { server 10.0.0.5:38001; }
-upstream eventopia_web     { server 10.0.0.5:38100; }
-upstream eventopia_console { server 10.0.0.5:38200; }
-upstream eventopia_operator { server 10.0.0.5:38400; }
-map $http_upgrade $eventopia_conn { default upgrade; "" close; }
+upstream eventopia_api     { server 10.0.0.5:38001; keepalive 64; }
+upstream eventopia_web     { server 10.0.0.5:38100; keepalive 64; }
+upstream eventopia_console { server 10.0.0.5:38200; keepalive 32; }
+upstream eventopia_operator { server 10.0.0.5:38400; keepalive 32; }
+map $http_upgrade $eventopia_conn { default upgrade; "" ""; }
```

`nginx -t` clean (pre-existing "protocol options redefined" warnings on unrelated vhosts,
not introduced by this change) → `systemctl reload nginx`.

**Verified post-reload:**
- All 4 nginx workers confirmed at `Max open files: 65535` via `/proc/<pid>/limits`
- `https://api.eventopia.my/healthz`, `www.eventopia.my`, `app.eventopia.my` → 200/301 as
  expected
- **The map change was the riskiest part of this — it could have broken WebSocket/SSE
  upgrade.** Retested explicitly: WS handshake → **101 Switching Protocols**; SSE request
  reaches the API (403, i.e. an auth response, not a proxy-level rejection)
- Zero `Connection refused` in nginx error log after 18:14:40 (the ~3s window during the
  earlier `pm2 startOrRestart` on `app` — see Finding 1's deploy — briefly did surface a
  handful, fully recovered)

## FINDING 4 — Load balancing: the app tier is not the constraint

| Host | vCPU | RAM | Load | Verdict |
|---|---|---|---|---|
| `app` `10.0.0.5` | 6 | 12 GB (5.2 free) | 1.19 | API at **0% CPU**; 42 PM2 procs |
| `db` `10.0.0.1` | 12 | 48 GB (28.6 free) | 0.27 | **Best LB target** |
| `proxy` `10.0.0.2` | 4 | 5.9 GB | 0.25 | Ingress only |
| `numa` `10.0.0.7` | 4 | 7.9 GB (**2.2 free**, swapping) | 1.14 | **Reject** |

**On the proposal to add `numa`: measured evidence says no.**

| | `app` → `db` | `numa` → `db` |
|---|---|---|
| RTT | **1.013 ms** avg | **8.239 ms** avg, **32 ms** max, **12 ms** mdev |

`reserveOrder` makes ~15 sequential round-trips, and those after a lock is taken sit
*inside* the critical section. On `numa` that inflates to ~120 ms — and because the lock is
**shared**, a slow numa transaction stalls the fast `app` transactions queued behind it.
Heterogeneous latency behind a shared lock means **the slowest node sets the pace for
everyone**. numa would subtract capacity, not add it. (It *is* on the private cluster and
can reach `10.0.0.1` — connectivity was never the objection; latency and 2.2 GB free RAM
are.)

**`db` is the good target** — loopback to Postgres *shrinks* the serialized section, which
raises the ceiling for every node. Note Bun cannot use PM2 cluster mode (that relies on
Node's `cluster`), so it needs either distinct ports behind the nginx upstream, or
`reusePort: true` on the default export in `server.bun.ts` (currently absent).

**Not pursued tonight — correctly.** The API has abundant headroom (0% CPU at time of
writing). Treat it as capacity planning for 10k/day, not a pre-19:00 action.

## Step 3 — DB planner statistics (not organizer data)

Applied at 18:16 WIB on `db`. This is table *storage configuration*, distinct from the
`event_day.capacity` values Finding 2 explicitly leaves alone — no row data was touched.

```sql
ALTER TABLE order_item SET (autovacuum_analyze_scale_factor = 0.02, autovacuum_vacuum_scale_factor = 0.05);
ALTER TABLE orders     SET (autovacuum_analyze_scale_factor = 0.02, autovacuum_vacuum_scale_factor = 0.05);
ANALYZE orders;
ANALYZE order_item;
ANALYZE tickets;
```

Default `autovacuum_analyze_scale_factor` is 0.1 (Postgres stock) — autoanalyze only
triggers after ~10% of a table's rows change. At 0.02, it triggers 5× more often, so
`order_item`'s statistics stay fresh as tonight's rows land instead of drifting stale
through the sales window. `ANALYZE` was also run immediately so statistics are current as
of 18:16, not waiting for the next autovacuum cycle.

**What this is insurance for:** Finding 2's Seq Scan is the planner's current choice
*because the table is small* — cost-based, not hardcoded. As `order_item` grows, the
planner should prefer a nested loop through `order_item_order_idx` (which scales with a
single event's order count, not the whole table). Stale statistics are the one thing that
would keep it wrongly pinned to the Seq Scan plan after the data shape has changed. This
doesn't force the better plan — it removes the reason the planner would miss it.

Applied via read-only-adjacent `ALTER TABLE ... SET (...)` (storage parameters, not DDL on
columns) + `ANALYZE`. No lock contention, no downtime, no data touched. One correction
during execution: `tickets` is the actual table name (not `ticket`, as an earlier
mid-session message assumed).

## FINDING 5 — the custom-domain landing page is not cached (correction)

Earlier drafts of this document — and an earlier message in this conversation — stated
that browsing does not hit the API, citing `web-public`'s `revalidate = 300` ISR on the
`*.eventopia.my` tenant path. **That is true only for the `eventopia.my` host.**

**The organizer's actual Instagram-ad landing page is a custom domain**,
`ticket-concert.mcf.or.id`, routed through the separate `eventopia_web_custom` upstream
(`custom.eventopia.my` server block, catch-all `~^.+$`). Checked its response headers live:

```
cache-control: private, no-cache, no-store, max-age=0, must-revalidate
cf-cache-status: DYNAMIC
```

Fully dynamic, confirmed with 3 repeated loads at **1.25s / 1.25s / 1.75s**. The page fans
out to 4 API calls per view (`domains/resolve`, org lookup, event lookup, rundown — visible
as the top 4 hottest routes in `eventopia-api-out.log` even at current low volume). Every
ad click is a full SSR round trip through the API, not a cache hit.

**Left as-is, deliberately, not by oversight:**
- Current headroom absorbs it — `eventopia-web-public` and `eventopia-api` both at 0% CPU,
  host load 2.31 on 6 cores, at the time of writing
- Adding caching this close to the drop is itself a live-path risk: nginx micro-caching or
  a Cloudflare Cache Rule on a *custom domain* neither analysis nor testing confirmed is
  free of buyer-specific content (an edge cache serving one buyer's checkout state to
  another would be worse than the latency it fixes)
- The lower-risk lever, if the 19:00 spike turns out sharper than the current headroom can
  absorb, is a **Cloudflare Cache Rule** on `ticket-concert.mcf.or.id` (Cache Everything,
  short edge TTL ~10s) — touches no server config, one click to revert. Held in reserve,
  not applied.

**Watch `eventopia-web-public` CPU specifically** at 19:00 — this is the surface most
likely to show strain first, since it is the one buyer-facing path that is genuinely
uncached.
