## Root cause — PLATFORM vs DIRECT collection (same code, different Xendit account)

BRImo mints a **BRI Virtual Account** via Xendit's Fixed-VA API
(`POST /callback_virtual_accounts`, `bank_code:'BRI'`, `packages/payments/src/xendit.ts:530-567`),
then wraps that number into the AES-encrypted BRImo redirect. The error the user sees is the API's
`422 PAYMENT_METHOD_NOT_ACTIVATED` (`provider-registry.ts:500-502`), emitted **only** from a
Xendit `BANK_NOT_ACTIVATED_ERROR` on that BRI-VA mint. The difference between the two orgs is
purely **which Xendit account collects**:

| Field | Ocarinesia ✅ | Malang Creative Fusion ❌ |
| --- | --- | --- |
| `organizer_id` | `org_b6966137a3254ada` | `org_03f297927f184c0d` |
| `payment_gateway` | `NULL` → **PLATFORM** | `xendit` (pinned) → **DIRECT** |
| `xendit_direct_approved` | false | **true** |
| enabled Xendit credential | none (uses platform key) | **own prod key `…5GIJ`** |
| collects through | platform Xendit (BRI activated) | its own account (BRI **not** activated) |
| `brimo_enabled` / key last4 | true / `410e` | true / `410e` (identical) |
| KYC / MoU | VERIFIED / SIGNED | VERIFIED / SIGNED |

Everything BRImo-specific is identical; only the collecting account differs
(`collection-mode.ts`: DIRECT needs a pinned gateway + enabled credential + operator approval —
all true for MCF). Ocarinesia collects PLATFORM (platform account has BRI); MCF collects DIRECT
through an account that returns `BANK_NOT_ACTIVATED_ERROR` for BRI.

**Evidence (four independent):**
1. `organizer_payment_method_status`: `org_03f2 · xendit · DIRECT · BRIMO → NOT_ACTIVATED
   (BANK_NOT_ACTIVATED_ERROR)` vs `ocarinesia · PLATFORM · BRIMO → AVAILABLE`.
2. **10 live API log lines** today, all identical: `method:BRIMO, collectionMode:DIRECT,
   providerCode:BANK_NOT_ACTIVATED_ERROR` ("Bank code BRI is not activated yet…").
3. **Live Playwright repro** of `evt_0e2a87c1` → the exact "belum aktif" alert (created only a
   benign PENDING order, zero `payment_intent` — fail-loud-not-persist).
4. Scope: MCF has exactly **one** published BRImo embed (`embed_page` table); its other events
   404. On MCF's account only **QRIS** works DIRECT; all VA methods fail.

## Proof tooling — `scripts/check-xendit-va-activation.mjs` (new, committed)

A dependency-free Node script (safe to hand to the organizer: env-var key, masked, no email,
unpaid auto-expiring test artifacts) that runs the **exact** Xendit calls per bank and reports
activation. Ran it against the platform key **and** MCF's own decrypted key. It answered the
user's follow-up ("can we use the Invoice VA type alongside Fixed VA?") empirically by probing
three VA surfaces:

| Route (BRI) | Platform key `…0Ghm` | MCF key `…5GIJ` | BRImo-usable? |
| --- | --- | --- | --- |
| **Fixed VA** `/callback_virtual_accounts` | ✅ ACTIVE (raw number) | ❌ `BANK_NOT_ACTIVATED_ERROR` | needs a raw number |
| **Invoice VA** `/v2/invoices` (POOL) | ⚠️ offered, no `bank_account_number` | ⚠️ offered, no `bank_account_number` | ❌ hosted-page only |
| **v3 Payments** `/v3/payment_requests` | ✅ raw VA# (HTTP 201) | ✅ **raw VA# (HTTP 201)** | ✅ |

- **Invoice VA is not an escape hatch** — proven with the raw `available_banks[]` BRI dump on
  create AND GET-refetch: `collection_type: POOL`, **no `bank_account_number`** (minted only on
  Xendit's hosted page). Binding a Fixed VA into an invoice (`callback_virtual_account_id`) needs
  an *active* Fixed VA — the missing piece. Cross-checked Xendit's help center + main docs.
- **v3 Payments IS an escape hatch** — with BRI Fixed-VA still 400ing on MCF's key,
  `channel_code:'BRI_VIRTUAL_ACCOUNT'` returns a **17-digit BRIVA, prefix `13282`** (the same BRI
  corp code the working BRImo VAs carry, cf. session-036's `13282353816579687`), `status:
  REQUIRES_ACTION`, synchronously in `actions[]`. It taps the BRI **VA-Aggregator** activation the
  org already has (the same track the Invoice offers as POOL) but, unlike the Invoice API, hands
  back the raw number.

## Re-confirmation — the Fixed-VA failure is a Xendit-side bug

After MCF **re-activated** *Virtual Account (Fixed) · BRI* on their own Xendit dashboard and
confirmed it, a fresh re-run still returned `400 BANK_NOT_ACTIVATED_ERROR` on their key.
Dashboard-says-active / API-says-not now persists **across a fresh activation** → a Xendit-side
provisioning bug, not a missed toggle. Escalation: business `67e001d933376768bcd990ff`, live mode.
