## Migration 0102 — silently no-op'd, root-caused live, fixed

`run-migrate.mjs` reported `migrations applied OK` with no errors, but `information_schema.columns`
(a real independent check, not the migrator's own self-report) showed `event.archived_at`/
`deleted_at` did not exist. Investigated rather than re-running blindly:

1. First hypothesis (wrong, corrected): a "phantom" tracking row for migration 102. Deleted a row
   from `drizzle.__drizzle_migrations` believing it belonged to file `0102` — it did not (its
   `created_at` matched `0101`'s journal `when` exactly). Restored it immediately from the exact
   captured values before doing anything else.
2. **Real root cause, found by reading `drizzle-orm`'s actual migrator source
   (`pg-core/dialect.js`):** it applies a migration only if `MAX(created_at)` across the whole
   tracking table is less than that migration's own journal `when` (`folderMillis`) — a single
   high-water-mark cursor, not a per-file check. Hand-written migrations `0100`/`0101` carry
   synthetic, round `when` values (`1784710000000` / `1784720000000`) that are **larger** than
   `0102_tricky_harrier`'s real, normally-generated timestamp (`1784715884472`). The cursor check
   is false for 0102 forever, on any database that has 100/101 applied — silent, no error.
3. **Fixed on prod:** applied 0102's 5 DDL statements directly via `psql` in one transaction, then
   inserted its tracking row with `created_at` = real apply-time (safely past `1784720000000`, so
   the cursor is correct going forward). Verified independently via `information_schema.columns` +
   `pg_indexes` — columns present, partial unique index correct, all 16 existing events unaffected
   (`0` deleted, `0` archived).
4. **This is a repo bug, not a prod-only patch** — any fresh replay of the full migration chain
   (a new dev box, CI, a rebuilt prod) hits the identical silent skip. Filed for the developer
   agent in `docs/engineering/known-issues.md` (needs `_journal.json`'s `when` for entry idx 102
   bumped past `1784720000000`, plus a suggested CI check that journal timestamps are monotonic).
   **`dev` almost certainly has the same exposure** — it hasn't pulled forward since session-025.
