## Investigation

1. **Identified the organizer.** "Festival Mbois 11" is **two different organizers** across
   environments — dev's sandbox test org from session-026 (`org_3c6828c4cdd245af`) is unrelated;
   prod's real organizer is **`org_03f297927f184c0d`**, with a PUBLISHED event literally named
   "Festival Mbois 11 - Concert **by BRImo**".
2. **Ruled out `disabled_payment_methods`.** The org's row has
   `disabled_payment_methods = ["GOPAY","OVO","DANA","SHOPEEPAY"]` — `BRIMO` is not in it, and by
   design (`methodSupported()` in `provider-registry.ts:457-476`) BRImo is gated **only** by
   `brimo_enabled`, never by this opt-out list (a partner-only method is never in the advertised
   set the toggle operates over). Also, that code path returns a **different** error
   (`422 PAYMENT_METHOD_NOT_SUPPORTED`), not the `503` the user saw — confirms this wasn't it.
3. **Found the actual 503 message's source:** `provider-registry.ts:418-426`,
   `collectErrorToResponse()` — returned for **any** `PaymentProviderError`, a single generic
   message covering unrelated failure classes (unconfigured gateway, DOKU error, network failure,
   Xendit rejection, ...).
4. **Checked all three BRImo gates** (per `docs/launch/brimo-production-staging-deploy.md`):
   platform `BRIMO_SECRET_KEY`/`BRIMO_ENVIRONMENT=dev` present on prod (this is **intentional**,
   documented "Stage 1" — BRI's own published dev key run on prod infra, not a misconfig);
   `organizer_account.brimo_enabled = true`; gateway pinned `xendit`, `xendit_direct_approved =
   true`, `organizer_direct_approval` row `APPROVED`. All three pass.
5. **Verified the org's stored Xendit credential actually decrypts.** Wrote a small read-only
   script (`bun run` + the repo's own `decryptPii`), confirmed the encrypted `server_key_enc`/
   `client_key_enc` decrypt cleanly to a real `xnd_production_...` key + a 48-char callback token —
   rules out a PII-encryption-key mismatch/rotation (also cross-checked `EVENTOPIA_PII_ENC_KEY`'s
   hash across every `.env` backup back to 2026-07-14 — unchanged throughout).
6. **`pm2 logs eventopia-api`** showed dozens of `POST /v1/payments → 503` for this organizer
   going back to at least 04:22 that day, recurring every time the buyer retried (still live at
   the time of investigation, ~11:12–11:26). Cross-referenced `payment_intent`: **zero `BRIMO`
   rows ever exist for this organizer** — every prior successful payment used `QRIS`. Confirms the
   failure is BRImo-specific, not a general gateway outage, and that retrying (the message's own
   advice) can never succeed.
7. **No error detail was logged anywhere** — `module.ts`'s catch blocks map the error and discard
   it; nothing prints `err.message` before the generic response goes out. Diagnosing further
   required reproducing the exact call the app makes.
8. **Reproduced directly against Xendit** (the one external write this session): replayed the
   same request `packages/payments/src/xendit.ts:436-447` sends —
   `POST https://api.xendit.co/callback_virtual_accounts` with `bank_code: 'BRI'`, using the
   organizer's own decrypted key. Result:

   ```json
   400 { "error_code": "BANK_NOT_ACTIVATED_ERROR",
         "message": "Bank code BRI is not activated yet. Please contact support to activate" }
   ```

## Follow-up investigation (same session, user pushed back on the org-specific conclusion)

The user's own assumption: this might be a **platform-Xendit-account** problem, not the
organizer's — and pointed out eventopia's own Xendit dashboard shows BRI **Virtual Account
Invoice** = Activated, BRI **Virtual Account Fixed** = Not Activated. Asked for this to be tested
directly, including against dev/sandbox.

9. **Replayed the identical VA-creation call using the PLATFORM's own Xendit key** (`XENDIT_API_KEY`
   from prod `.env` — nothing to do with the organizer). Same request, same result:
   `400 BANK_NOT_ACTIVATED_ERROR`. **This disproves "organizer-specific"** — the platform's own
   account hits the exact same wall.
10. **Confirmed the Fixed-vs-Invoice VA distinction against Xendit's own documentation** (web
    search): "Fixed VA" is created via `POST /callback_virtual_accounts` (exactly what our code
    calls) and is activated per-bank in the dashboard separately from "Invoice VA" (a VA minted
    automatically inside Xendit's Invoice product, typically for one-off payments, randomly
    assigned VA number). The two are genuinely separate activation toggles per bank — matching the
    user's screenshot exactly.
11. **Attempted the same test on `dev`** (sandbox key + BRImo) per the user's request — **blocked**:
    `ssh` to `154.26.130.96` started refusing connections outright (`Connection refused` on port
    22, ICMP still responds fine) after a few failed credential attempts against that host earlier
    in this same investigation — almost certainly a fail2ban-style lockout triggered by this
    session's own guessing, not a code or infra issue. Did not press further to avoid extending
    any ban. The prod platform-key reproduction above is conclusive on its own regardless — it
    doesn't depend on any organizer's account state, so a dev-side confirmation would only be
    corroborating, not decisive.

## Root cause (corrected)

**Not an organizer-specific Xendit account gap.** The integration calls Xendit's **Fixed Virtual
Account** API (`/callback_virtual_accounts`) for both BRImo (`bank_code: 'BRI'`) and the plain `VA`
method (`bank_code: 'BCA'`) — but this Xendit business (platform account, and evidently the
organizer's too) only has BRI activated under the **Invoice VA** product, a separate Xendit
activation track. BCA's Fixed VA channel is activated (this org has working `VA`-method intents),
BRI's is not — on the platform account itself, which any DIRECT-collecting organizer's own account
would need to separately match. The recent `disabled_payment_methods` toggle work (session-029)
remains unrelated — confirmed by data in the initial investigation, unaffected by this correction.

This reframes the incident from "one organizer needs to call Xendit support" (this session's
initial, disproven read) to a **genuine integration/product decision**: either request Fixed-VA
BRI activation for the platform account (doesn't scale to DIRECT organizers, each would need their
own) or adapt the BRImo/VA integration to Xendit's Invoice-VA product instead (a real code change,
not a one-liner — see the doc entry for what that would touch).

The **separate, still-valid** code gap remains: the gateway rejection reason is never logged
anywhere, and every `PaymentProviderError` (transient or not) collapses to the same generic
"coba lagi" 503 — actively misleading for this class of failure.
