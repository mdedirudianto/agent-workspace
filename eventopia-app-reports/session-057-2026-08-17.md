### The nginx apex flip — found and fixed a real config-drift trap

**What happened.** Edited `/etc/nginx/sites-available/eventopia.conf` first (per the deploy
note's own instructions, which name that path), replacing the blanket
`return 301 https://eventopia.co.id$request_uri;` with the directory-serving `location /`
block from `infra/nginx/eventopia-apex-capability-paths.conf`, using the same
`proxy_http_version 1.1` / `Upgrade`/`Connection` / no-`X-Forwarded-Proto` house style as
every neighboring block in the file. `nginx -t` passed, reload succeeded — but a post-flip
curl still showed `eventopia.my/` 301ing, even hitting the origin IP directly with a `Host`
header (ruling out a DNS/CDN explanation at first).

**Root cause: `sites-enabled/eventopia.conf` is not a symlink to `sites-available` on this
host — it's an independent real file**, and it had already drifted from `sites-available`
*before* tonight (it carries `keepalive 64`/`keepalive 32` pooling on all four upstreams and
a different `$eventopia_conn` map default that `sites-available` never had). nginx loads
`sites-enabled`, so editing `sites-available` alone was a no-op — the live redirect never
changed, and `nginx -t`/reload only validated and reloaded the *unedited* file.

**Fix:** applied the identical apex-flip edit directly to `sites-enabled/eventopia.conf`
(preserving its existing keepalive tuning rather than overwriting it with the stale
`sites-available` copy). This surfaced a second, self-inflicted problem: the pre-edit backup
(`eventopia.conf.bak-pre-session057-*`) was written *inside* `sites-enabled/`, and nginx's
config glob picked it up as a second, unmodified copy of the same vhost — `nginx -t` failed
with `duplicate upstream "eventopia_api"` and the reload never applied. **No outage** — nginx
keeps serving the last-known-good config when a reload's syntax check fails, confirmed via
`systemctl status` showing the original master process (6-day uptime) still running throughout.
Moved the backup to `/root/nginx-backups/` (outside the glob), retested clean, reloaded
successfully. Afterward, copied the now-correct `sites-enabled` file back over
`sites-available` so the two are back in sync (they were **not** in sync before tonight
either — an untracked drift from some earlier hotfix, now reconciled).

**Lesson for next time this vhost is touched:** verify `sites-enabled/eventopia.conf` is what
you're actually editing (`ls -la` to rule out a plain-file vs symlink), and never drop a
backup file inside `sites-enabled/` itself — write it to a directory nginx's `include` glob
doesn't scan.

## Findings summary

1. **`sites-available` and `sites-enabled` had already drifted apart on `proxy` before
   tonight** (independent of this session's changes) — `sites-enabled` carries live
   `keepalive` tuning `sites-available` never had. Reconciled both to match after the flip;
   worth a standing reminder that this vhost's `sites-enabled` copy is the one that's actually
   live, not a symlink.
2. **Self-inflicted, fully resolved:** a pre-edit backup written inside `sites-enabled/`
   caused a `nginx -t` failure (`duplicate upstream`) on the first reload attempt. No outage
   — nginx's old master process kept serving through the failed reload. Fixed by relocating
   backups to `/root/nginx-backups/`, outside the config glob.
3. **Migrations `0143` and `0145` are missing their `meta/*_snapshot.json` files** — every
   other migration in the repo has one. Doesn't block applying migrations (confirmed via a
   clean `db:check`), but will affect the next `drizzle-kit generate`. Not fixed tonight —
   worth a small follow-up commit upstream.
4. **`robots.txt` served a stale Cloudflare-cached 301 for a few minutes post-flip** —
   confirmed self-resolving, origin was correct immediately. No action taken.
5. **Not a finding, ruled out during smoke-testing:** the `eventopia_operator` nginx upstream
   in `eventopia.conf` has no matching `proxy_pass` in that file — initially looked like a
   missing route, but the operator console has lived on `admin.eventopia.co.id` (a sibling
   vhost file) since session-013. Confirmed live (200) before writing this up.
