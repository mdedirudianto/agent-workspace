### Smoke test 1 — PIN auth (deploy-specific), fully automated against real prod infra

Same "stub only the unavoidable WhatsApp HTTP delivery" technique as session-045: called
`handleVerifyTurn()` directly (`@eventopia/api/auth-wa-verify-worker`) against real prod
Redis+DB from an ephemeral, never-committed script (`bun --env-file=../../.env` — **the env
file must be the repo-root `.env`, not `apps/api/.env`**; pointing at the wrong one silently
drops `REDIS_URL`/`PIN_PEPPER`/PII keys and the Redis client retries forever).

**Organizer A (phone-first, via the WA-verify stub):**
1. Started a challenge with `expectedPhone`, replied from the **wrong** number via the stub →
   status flipped to `mismatch` (not a silent 10-minute timeout).
2. Replied from the **correct** number → `verified` → `wa-verify/complete` minted a session.
3. `POST /v1/auth/pin` set a PIN → `POST /v1/auth/pin/login` with the phone identifier signed
   in with **no WhatsApp round-trip**.

**Organizer B (email-first, via the existing email-OTP recipe):**
1. Signed up via real email-OTP (code read from Redis). **Gotcha caught before it mattered:**
   the first attempt used a `+tag`'d Gmail address for the disposable identity —
   `canonicalizeEmail()` strips `+tags` and dots for `gmail.com`/`googlemail.com` specifically
   (folds them to one inbox, to block OTP-bombing/dupe accounts), which would have collapsed
   the "disposable" test account onto the user's real Gmail identity. Switched to an
   `example.com` address (IANA-reserved, never delivers real mail) before creating anything.
2. Set a PIN, signed in via the **email** identifier (confirms `identifier` correctly resolves
   phone vs. email server-side without leaking which).
3. **Self-service PIN reset over email:** requested `/v1/auth/pin/reset/email` (prod never
   returns `devToken`), captured the fresh single-use token by diffing `email-verify:token:*`
   Redis keys immediately before/after the request (same "read the real state directly" spirit
   as the OTP recipe) → confirmed the reset, then verified the **old** PIN was rejected
   (`401 PIN_INVALID`) and the **new** one worked.
4. **Admin clear-pin end-to-end:** bootstrapped a disposable `SUPER_ADMIN` operator, logged in
   (`OPERATOR_MFA_ENABLED=false` on prod, so no TOTP step-up needed), called
   `POST /admin/support/accounts/{userId}/clear-pin` with a reason → got back
   `{"cleared":true,"hadPin":true,"sessionsRevoked":true}`. Verified independently: PIN login
   now `401` (really cleared), a `account.pin.clear` row landed in `operator_audit_log` with the
   supplied reason, and `pm2 logs eventopia-workers` showed **5** `[workers:emails] not
   delivered (RESEND_422)` lines — one per real email attempted this test (signup OTP, PIN-set
   notice, reset-link, reset notice, clear notice), each correctly rejected by Resend only
   because `example.com` isn't a real deliverable domain. Confirms the notice producer fires on
   every PIN lifecycle event and genuinely calls the real `EMAIL_PROVIDER`, not a stub.

**Cleanup:** scanned all `organizer_id`-bearing tables for the 3 test organizers — only
`organizer_account` had rows (3, one per organizer; nothing else, since this test never touched
events/tickets). Deleted `organizer_account` (3) + `account` (3, matched by phone/`user_id`) in
one committed transaction, deleted the disposable operator, deleted the 6 `org:meta`/`org:slug`
Redis keys, removed the ephemeral script. **Verified zero residue** for all three organizer IDs
afterward.

## Findings summary

1. **Clean deploy, no incidents in the running services.** Two real mistakes were made and
   caught mid-session before they mattered: (a) an `--env-file` pointed at the wrong `.env`
   during the smoke-test script, silently dropping `REDIS_URL`/PII keys and hanging on infinite
   Redis reconnects — session-045 had already flagged this exact class of gotcha; (b) a
   `BEGIN`-without-`COMMIT` cleanup transaction that silently rolled back on disconnect, caught
   by re-verifying row counts rather than trusting `DELETE n` output. Neither touched prod
   service state — both were in ephemeral test tooling — but both are worth remembering.
2. **`PIN_PEPPER` is a real, verified hard gate** (`container.ts:245-254`, `throw`s in
   production when unset) — this session's single highest-risk step, executed correctly:
   generated and set before the first `eventopia-api` restart, confirmed via the doc's own
   `401` (not `503`) probe.
3. **All four PIN auth surfaces verified working against real prod infra:** phone mismatch
   reporting, phone-based PIN set/login, email-based PIN set/login/self-service-reset, and the
   new admin clear-pin route (including its session-revocation confirmation and audit trail).
4. **The PIN-change security notice is real, not a stub** — confirmed via 5 genuine `RESEND_422`
   attempts (one per lifecycle event), rejected only because the test used a non-deliverable
   domain on purpose.
5. **`canonicalizeEmail()`'s Gmail dot/plus-folding is a real trap for disposable-account test
   recipes** — worth remembering forward: any future "disposable organizer via email OTP" recipe
   must avoid `gmail.com`/`googlemail.com` addresses, or it risks operating on the tester's real
   identity instead of a throwaway one.
6. **Full event→ticket→payment path confirmed healthy**, independent of this deploy: QRIS mints
   real intents, BRImo mints and decrypts a genuine BRI VA, VA's known BCA-not-activated gap is
   still correctly a terminal 422. No regression since session-045's run earlier the same day.
7. **No new application bugs found.**
