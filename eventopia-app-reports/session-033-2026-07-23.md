## Migration 0103 — silently skipped again, same bug class as session-032's 0102

**First attempt at `db:migrate` failed outright** (exit 1, no readable error — a `pnpm --filter`
cwd issue: it runs with cwd at `packages/db`, which has no local `.env`, so `DATABASE_URL` wasn't in
the shell and drizzle-kit silently fell back to `DEFAULT_DATABASE_URL` = local dev, which doesn't
exist on `app`). Fixed by passing `DATABASE_URL` explicitly from the root `.env`. **Doc gap found:**
`docs/launch/payment-method-status-deploy.md`'s migrate line omits the `DATABASE_URL='<prod>'`
prefix that `docs/launch/payments-default-gateway-deploy.md:120` correctly includes — worth
reconciling so future sessions don't hit the same dead end.

**Retry reported `migrations applied successfully!` — but independent verification
(`information_schema.columns`, not the tool's own report, per session-032's lesson) showed
`0104`/`0105` landed (hashes byte-verified) while `0103_brimo_org_secret_key` did not** —
`organizer_account` had no `brimo_secret_key_enc`/`_last4` columns.

**Root cause, confirmed against the tracking table:** session-032's manual fix for `0102` (the
previous incident) inserted its tracking row using `Date.now()` as `created_at`
(`1784762595231`) rather than `0102`'s own journal `when`. That value is *greater* than
`0103_brimo_org_secret_key`'s own real, already-generated `when` (`1784761189123`) — so this
session's `db:migrate` fetched that inflated cursor and silently skipped 0103, applying only 0104
and 0105 (whose real timestamps happen to exceed it). Read `drizzle-orm`'s actual installed
migrator source (`pg-core/dialect.js`) to confirm the exact mechanism: the "last applied" cursor is
fetched **once** per `migrate()` call, not re-checked per file — so the danger is specifically a
database migrating across **separate invocations**, not a single fresh replay (which is safe,
confirmed from source — corrects an imprecision in how session-032 described the bug).

**Fixed, in order:**
1. `pg_dump -Fc` backup **before any manual write** →
   `db:/root/eventopia-backups/eventopia-prod-pre-0103-fix-20260723.dump` (450K).
2. Applied 0103's DDL (2 nullable `ALTER TABLE` statements) directly via `psql` in one transaction,
   then inserted its tracking row with the matching sha256 hash — verified independently via
   `information_schema.columns` (both columns present) and the tracking table (row present, correct
   hash).
3. **Fixed the repo-level root cause**, not just prod's live state — `packages/db/drizzle/migrations/meta/_journal.json`:
   - Bumped `0102_tricky_harrier`'s `when` past `0101`'s (per session-032's own documented "fix
     needed" note, never actually implemented until now).
   - **Audited the entire 106-entry journal for monotonicity** (not just the reported case) and
     found a second, older instance: a 9-migration span `0019`–`0027`, all below a synthetic
     `0018_tax_rate_config` timestamp. Confirmed **no live impact** — prod already has their DDL
     applied (checked `contacts_organizer_phone_idx`/`contacts_organizer_phone_hash_idx` from
     `0019` directly) — but renumbered them too, closing the landmine for any future multi-invocation
     catch-up (a fresh dev rebuild resuming mid-chain, CI, disaster recovery).
   - Verified via `pnpm db:check` (drift gate, unaffected/still green) and a Python monotonicity
     check confirming all 106 entries are now strictly increasing.
4. Documented the exact mechanism (confirmed from source) and a safer recovery recipe (use the
   skipped migration's own `when`, not `Date.now()`, when manually inserting a tracking row — using
   "now" is what caused this exact incident) in `packages/db/MIGRATIONS.md`.
5. Removed the now-fixed entry from `docs/engineering/known-issues.md` per its own "remove once
   fixed" convention; also repaired a pre-existing merge artifact there where that entry's last
   bullet had run directly into the next section's heading with no `##` line.
6. **3 commits, local only, not yet pushed** — `deeaec50` (journal + docs fix),
   `8a5201e8` (MIGRATIONS.md precision correction after reading the real source). **Awaiting user
