## Full live smoke test — every shipped feature, real prod infra

All disposable test data created via real signup/bootstrap flows (never synthetic DB inserts where
an API path exists), fully cleaned up and independently re-verified afterward.

**Operator Checkout Leads (`/admin/leads`).** Bootstrapped 3 disposable operators
(SUPPORT_OPS/FINANCE_OPS/COMPLIANCE_OPS). Support: real cross-org abandoned-checkout rows
(name/phone/email visible, tenant-scoped correctly). Finance: `403 FORBIDDEN` with the exact
documented message — the exclusion is the feature, and it held. Compliance: `/leads/export.csv`
400s without a `reason`, 200s with one. Audit trail confirmed `lead.list`/`lead.export` rows carry
a **keyed** hash of the search term (differs from a bare `sha256` of the same term, proving
`EVENTOPIA_PII_HMAC_KEY` is actually in the loop, not the dev fallback) — the raw term is never
stored.

**WhatsApp template registration.** Dry-run reviewed with the user before the real submit (9→24
templates once the full registry printed — `auth_otp_id` correctly skipped, needs button support
`sendTemplate` doesn't have). Real submit: **24 submitted, 0 failed**. Status check ~15 min later:
**19 approved/pending, 5 rejected** (`INCORRECT_CATEGORY`) — including both e-ticket delivery
templates, the ones this whole release exists to unblock. See Findings #2 — root-cause plan is a
separate follow-up, not fixed this session.

**Operator Insights GMV split.** Triggered `POST /admin/insights/refresh` live: PLATFORM (0) +
DIRECT (Rp44,395,820) + OFF_GATEWAY (Rp2,700,000) tiles sum exactly to the Rp47,095,820 GMV
headline. Take rate correctly rose 7bps (old, DIRECT-diluted `blendedTakeRateBps`) → 74bps (new,
DIRECT excluded from the denominator) — the fix working, not a regression, exactly as the deploy
note predicted.

**Operator self-service account.** Bootstrapped a disposable SUPER_ADMIN. `mfaEnrolled:false` →
`POST /admin/me/mfa/enroll` (secret + otpauth, row untouched) → **computed a real TOTP code from
the raw secret** (no authenticator app needed — RFC 6238 is just an algorithm) → `POST
/admin/me/mfa/confirm` → `mfaEnrolled:true`, full session reissued. This closes end-to-end what
session-052 couldn't for the operator-invite flow (no test inbox needed here, since the secret
itself is enough). Password gate refused both a <12-char password and email-as-password. Sessions
`revoke-all` returned `sessionsRevoked:2`. Audit trail confirmed `operator.mfa.enroll` +
`operator.sessions.revoke_all`, correctly silent on the enrol-begin step (nothing is committed
until a code proves it).

**WA auto-reply reclassification.** Sent a real signed synthetic inbound webhook (Meta envelope,
`x-hub-signature-256` HMAC over the raw body using prod's own `META_APP_SECRET` — same technique as
sessions 008/016) to the user's own WhatsApp number, saying *"tiket Festival Musik masih ada?"* —
the exact `isTicketKeyword` false-positive class the release fixes. Landed `kind='human'`
(previously would have been silently swallowed as `system` traffic and answered with a
ticket-not-found non-sequitur); the user received a real WhatsApp acknowledgment
(*"Terima kasih sudah menghubungi kami…"*). Contrasted against a real pre-existing `system`-kind
`tiket` (bare keyword) row from 2026-08-06 — confirmed the legitimate keyword form is unaffected.

**AI page-gen fetch fix.** First attempt failed — but not on the bug this release fixes. Root

fresh token live; applied to `.env`, api+workers restarted, re-tested against the **exact URL from
the bug report** (`https://eventopia.co.id`): `201 EXTRACTED`, real page title pulled correctly
(other fields correctly null — the URL is a marketing homepage, not an event listing). Confirms the
egress/inlining fix works; the OAuth revocation was a separate, coincidental outage.

## Findings summary

1. **Self-caught deploy-ordering mistake, no impact.** First migration attempt ran *before* `git
   pull`, so the new migration files (`0130`/`0131`) didn't exist on disk yet — the migrator
   correctly did nothing (clean no-op, not a partial apply; confirmed via the journal still
   reading 130 with no new hash rows). Re-ran in the right order after pulling; both migrations
   landed and verified clean. Worth remembering: this deploy pulls code *before* migrating,
   opposite of how session-052's write-up reads at a skim.
2. **5 of 24 WhatsApp templates rejected by Meta (`INCORRECT_CATEGORY`), including both e-ticket
   delivery templates — the ones #132001 needs.** Root-cause investigation and remediation plan are
   a separate follow-up (not this session) — see the app's `docs/launch/whatsapp-templates-deploy.md`
   follow-up work and the next session in this directory. 19 templates are approved/pending
   normally.
3. **`ANTHROPIC_AUTH_TOKEN` had been silently revoked since before this session** (first `401`
   revoked-token failure in `ai_page_draft` traces back to 2026-08-03, per its own failure log) —
   a **separate, unrelated outage** from tonight's fix, which would have been mis-diagnosed as
   "the deploy didn't work" without checking the actual error class. Fixed live (user supplied a
   fresh Keychain-extracted token); the standing "no refresh loop" design gap (session-024) is
   unchanged — this token will revoke again on its own schedule.
4. **Two accidental partial secret exposures in this session's tool output** (a `.env` grep
   redaction regex bug left most of `META_GRAPH_API_ACCESS_TOKEN` and all of `META_APP_SECRET`
   visible in transcript rather than masked). Flagged to the user both times; rotation left
   optional, matching the session-022/024 precedent for this exact category of incident.
5. **Carried forward, unchanged:** `operator_audit_log` hash-chain break at seq 56 (7 sessions
   now, 017→…→052→this one).
