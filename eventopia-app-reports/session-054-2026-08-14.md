# Session 54 — GA4 product property had never received a hit from a `.my` host: a destination-only measurement id, fixed in GA4 admin + one env value (no code deploy)

**Date:** 2026-08-14

**App:** `eventopia` (github.com/biji-dev/eventopia) — **code stays at `346d420f`**. No `git pull`,
no migration, no version bump. The only prod change is two `.env` values and a `web-public` rebuild
**from the commit already checked out**, so zero application code moved.

**Hosts:** `app` (`devops@154.26.129.104`, `.env`, rebuild, PM2). Plus **Google Analytics 4 admin**
(account `Eventopia` 400690724) — which is where the actual fault was.

**Env:** production only. **Severity:** medium — no money path, no schema, no code; but ten days of
product-side analytics were lost and the property that looked healthy was full of the wrong site's
traffic.

## Report

User reported GA tracking only the marketing site, not organizer subdomains, event pages or custom
domains, and showed a GA4 property with 139 new users against a Cloudflare figure of 14.85k unique
visitors on the `eventopia.my` zone.

**The application code was never the problem.** `apps/web-public` has exactly one HTML-rendering
layout (`app/layout.tsx`); it renders `<GoogleAnalytics/>` + `<GaRouteTracker/>`, and the tenant
layout (`app/%5Ft/[sub]/layout.tsx`) is a plain `<div>` that cannot remove it. Every tenant
subdomain, event page, custom domain and embed nests under it. The host→property split resolves
correctly in the browser, and the running build had all three env vars baked in (checked directly
in `.next/standalone`).

### Root cause — a measurement id is not always a loadable tag id

The `eventopia.my` **Web App** stream had **no Google tag of its own**. On 2026-08-04 GA4 attached
it as a *destination* of the marketing site's tag instead:

| Google tag "Landing Page" | Tag IDs `G-8YBGDDMSQ3`, `GT-NGWQSRNQ` |
|---|---|
| Destination — Landing Page | `G-8YBGDDMSQ3` (added 07/10/2026) |
| Destination — Website | `G-5KBH3CVVX6` (added 08/04/2026) |
| Destination — Web Organizer | `G-4PZM1X99X2` (added 08/04/2026) |
| Destination — **Web App** (`https://eventopia.my`) | **`G-VC3CXYRKK4`** (added 08/04/2026) |

`googletagmanager.com/gtag/js?id=X` is served only when `X` is a **tag** id. A destination-only id
404s:

```
gtag/js?id=GT-NGWQSRNQ    200      gtag/js?id=G-VC3CXYRKK4   404   <- what prod was loading on .my
gtag/js?id=G-8YBGDDMSQ3   200      gtag/js?id=G-5KBH3CVVX6   404
                                   gtag/js?id=G-4PZM1X99X2   404
```

Identical from the laptop and from `app`, so Google-side, not local or CF.

**Nothing about this is visible from the page.** Verified live on
`malang-creative-fusion.eventopia.my` before the fix: the `<script>` element was present with the
right id, `window.gtag` existed (it is the inline stub, defined either way), `dataLayer` held 4
queued entries — and **zero `/g/collect` requests were sent**. The pre-tag queue in
`lib/analytics/gtag.ts` worked exactly as designed; it simply never drained.

**And the property was not empty — it was wrong.** Because the shared tag loaded fine on
`eventopia.co.id`, it fanned that page view out to all four destinations. One co.id page view
produced `/g/collect` for all four `tid`s. So the 139 "product" users were **marketing traffic
mislabelled**, and GA's own stream page said *"Data collection is active in the past 48 hours"* for
that reason. Low-but-present numbers are far harder to notice than none.

GA's own **install snippet** for the `eventopia.my` stream handed out
`gtag/js?id=G-8YBGDDMSQ3` and `gtag('config','G-8YBGDDMSQ3')` — the *marketing* id. That is GA
stating the stream had no tag, and is the single clearest tell for next time.

### Why session-049 did not catch it

Session-049 (2026-08-04, the deploy that turned GA on) recorded: *"GA4's two property ids +
marketing-host string confirmed compiled into the live-served bundle (no browser extension
available this session, so verified via build artifacts rather than a live network request)."*

That verification was correctly executed and still could not have caught this. Checking the
artifact proves the id was **shipped**; it says nothing about whether the id **works**. Every check
available that day — env set, ids inlined, bundle served — passes identically in both worlds. This
is the gap `scripts/check-ga-tags.mjs` (below) closes.

## Findings

**#1 — `pm2 restart --update-env` does NOT reload `.env` on this host, and says nothing.**
`~/eventopia/ecosystem.config.cjs` parses `.env` itself at config-load time and bakes the result
into each app's `env:` block. `--update-env` refreshes from the *invoking shell's* environment, so
it re-applied the same stale values. First restart reported success and all three processes came up
green with the old `PUBLIC_WEB_BASE_URL` still in `/proc/<pid>/environ`. Only
`pm2 startOrRestart ecosystem.config.cjs` re-reads the file. **Verify env changes against
`/proc/<pid>/environ`, not `pm2 env`** — `pm2 env` reports pm2's stored copy, which is exactly the
thing that was stale.

**#2 — the failure mode produces a *populated* property, not an empty one.** Covered above. The
diagnostic that actually separates the two: `window.google_tag_data` is defined only if gtag.js
really ran. `typeof window.gtag === 'function'` proves nothing.

**#3 — `/g/collect` beacons read as HTTP 503 in the extension's network view while landing fine.**
Every collect request looked failed throughout this session, including ones GA4 Realtime then
counted. Chased briefly as a second bug; it is a capture artifact of keepalive beacons. **Trust
Realtime over the status column.**

**#4 — two of the three stray destinations belong to an account already marked for deletion.**
`Website` (`G-5KBH3CVVX6`) and `Web Organizer` (`G-4PZM1X99X2`) live in the struck-through
**`Eventopia - wrong` (403369982)** account, which also holds a duplicate `Website` property. They
had been fed nothing but `eventopia.co.id` page views since 08-04. Detached anyway.

**#5 — `www.eventopia.my` 301s *everything* to `eventopia.co.id`,** including `/tiket/`,
`/pesanan/`, `/t/` and `/e/`. With `PUBLIC_WEB_BASE_URL=https://www.eventopia.my`, every e-ticket
and order link the backend minted landed on the marketing host, so `purchase` and order-status
views were attributed to the **marketing** property even once the product tag worked. Aligned to
the bare apex, which serves those same-origin — the carve-outs
`infra/nginx/eventopia-apex-capability-paths.conf` calls "NOT YET NEEDED / pre-emptive" turn out to
be **already live on prod**, so this needed no nginx change. Re-verified after the switch:
`/tiket/x`, `/pesanan/x`, `/konfirmasi-tiket`, `/verifikasi-email` and `/_next/static/...` all 200
same-origin, no redirect. `/api/revalidate` is not carved out at the apex, but `www` did not carve
it out either — both 301 to co.id, which is the same web-public server, so ISR revalidation
behaves exactly as before.

**#6 — `console.eventopia.my` is not the console.** It is an unclaimed tenant subdomain that 404s
out of web-public; the organizer console is `app.eventopia.my`. Worth knowing before anyone reads a
404 there as an outage.

**#7 — the console *is* tracked, just not by GA.** `app.eventopia.my` posts to
`analytics.biji.uk/api/track` (OpenPanel, 200). GA is public-only by design
(`docs/engineering/observability.md` §5). No change made; the user's "console is tracked" was
right about the fact and wrong about the tool.

**#8 — the Cloudflare vs GA comparison is apples-to-oranges** and will stay that way. CF's 14.85k
unique visitors / 532.7k requests covers the whole `eventopia.my` zone: `api.`, `app.`, `checkin.`,
static assets and bots. It will never match a GA page-view count.

## Open follow-ups

1. **`NEXT_PUBLIC_GA_MEASUREMENT_ID=G-8YBGDDMSQ3` is still set on prod** (line 106). It is the
   deprecated pre-split var, honoured as the **product** fallback when `_PRODUCT` is blank — and it
   holds the **marketing** id. Inert today because `_PRODUCT` is set, but if anyone ever blanks
   `_PRODUCT` the product surface silently reports into the marketing property. `check:ga` cannot
   catch this: the id is perfectly valid, just wrong. Blank it on the next rebuild.
2. **Merged (`34672bd5`) but not deployed** — prod's `web-public` build predates the merge, so the
   `onError` guard is not protecting prod yet. It ships with the next `web-public` release; nothing
   else in the merge is runtime-visible. Deploy steps:
   [`docs/launch/ga-product-tag-id-deploy.md`](https://github.com/biji-dev/eventopia/blob/main/docs/launch/ga-product-tag-id-deploy.md).
3. **Prod is 63 commits behind `main`** (`346d420f` vs `168c1585`) with **3 unapplied migrations**
   (`0132` export keyset indexes, `0133`/`0134` ticket exchange) and version bumps across
   api/console/workers/admin/checkin/db/payments/contracts/api-client/ui — the CSV-exports +
   hardware-scanner + ticket-type-correction release. Deliberately untouched this session.
4. **Product-property data 2026-08-04 → 2026-08-14 is `eventopia.co.id` traffic** and should be
   treated as contaminated. Not retroactively fixable.
5. **The `Eventopia - wrong` account (403369982) is marked for deletion** and holds `Web Organizer`
