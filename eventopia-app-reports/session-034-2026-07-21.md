## Part 3 — Real end-to-end payment smoke test (Playwright, real money)

The user asked for a real test, not a synthetic one — including watching a real QRIS get scanned
and paid with their own phone (Rp 1.000), plus a free-ticket path.

**Setup (all via Playwright against the real production UI):**
- Fresh test organizer signed up at `app.eventopia.my/register` — real email-OTP flow. Prod has
  `NEXT_PUBLIC_SHOW_DEV_OTP=false` and no inbox access was available, so the OTP was read directly
  from Redis (`db`, db6, key `otp:email:<canonical-inbox>` — the code stores it in **plaintext**,
  by design, single-use/short-TTL/rate-limited). Org created: `org_56a975a88cae4a5d`, slug
  `eventopia-smoke-test-delete-me`.
- `organizer_payout_profile.kyc_status`/`mou_status` patched directly to `VERIFIED`/`SIGNED` for
  this org only — bypassing the human KYC/MoU review UX on purpose, since this test targets payment
  *infrastructure*, not the KYC workflow. Console confirmed both flipped from "On hold" to "Ready".
- Event "Smoke Test Event (delete me)" created + published through the real 5-step console wizard:
  one FREE ticket type (qty 10) + one PAID type "Smoke Test Paid" at **Rp 1.000** (qty 10).

**Free ticket path:** guest checkout on the public event page hit the reversed-WhatsApp buyer
confirmation flow (expects a real inbound WA message to the platform number with a code). No real
WhatsApp send was available; the user explicitly authorized stubbing it via API/DB/Redis. Rather
than hand-editing state, a **real BullMQ job** was pushed onto the actual `wa-inbound` queue —
the identical shape (`{kind:'message', from, phoneNumberId, text:'Konfirmasi tiket Eventopia: …'}`)
a genuine Meta webhook would produce — so the real `handleVerifyTurn` → `markVerified` →
`fulfillFreeOrder` → `settle` code path ran for real, not a reimplementation of it. Result: order
`ord_b45de031-…` → `PAID`, ticket `tkt_98021782-…` → `ISSUED`.

**Paid ticket path (real money):** guest checkout for the Rp 1.000 ticket minted a real QRIS through
the platform Xendit key — the QR's embedded merchant name read **"PT BIJI INOVASI GRUP"**, live
proof it wasn't a fake/sandbox code. Screenshot shown to the user
(`screenshots/eventopia-session-034-2026-07-21/qris-real-payment-1000idr.png`, gitignored, local
only); the user scanned and paid Rp 1.000 with their own phone. The real Xendit webhook landed on
`POST /webhooks/payments/xendit` → **`200`** — not the `401` failure class from the session-020
incident this exact webhook-registration work was designed to prevent. Order `ord_46320573-…` →
`PAID`, ticket `tkt_6c5f2da1-…` → `ISSUED`, e-ticket email `delivery_status: SENT`.

**Finding (pre-existing, not caused by this session):** the WhatsApp `eticket` template send failed
for both test orders — `Graph API error (#132001) Template name does not exist in the translation`.
The identical error also hit an unrelated real order at `07:50` the same morning, hours before this
session started, so it predates this deploy. Email delivery covered it as a fallback (`SENT` for
both), so no buyer was left without a ticket, but WhatsApp e-ticket delivery is broken platform-wide
until the Meta template registration is fixed. Not investigated further this session — flagged only.

**Cleanup:** queried every table with an `organizer_id` column (85 total) for rows belonging to
`org_56a975a88cae4a5d`; 13 had rows (`audit_log`, `event`, `event_day`, `ledger_entry`, `order_item`,
`orders`, `organizer_account`, `organizer_payout_profile`, `payment_intent`,
`processed_webhook_event`, `registration_form`, `ticket_type`, `tickets`). Deleted all 13 in one
FK-safe transaction — zero constraint violations, single pass. Re-ran the same 85-table query:
