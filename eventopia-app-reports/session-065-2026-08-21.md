## Cleanup — verified, not just trusted

Hit the same `organizer_account.id` vs. JWT `organizerId` id-form mismatch session-064 documented
(`org_75e031d28934467c` in the token vs. the real `oacc_ad71bfe7-…` primary key) — looked it up by
`slug`/`display_name` before deleting, per that precedent. Similarly the account rows: JWT `sub` is
`usr_acc_…` but the real `account.id` is `acc_…` (same prefix, `usr_` stripped) — looked up by the
stripped id before deleting.

Deleted in FK-safe order, single transaction with explicit `COMMIT`:
`staff_membership` (1) → `event_day` (1) → `event` (1) → `organizer_account` (1, by its real
`oacc_` id) → `account` (2, owner + crew). Re-queried all five by exact ID afterward — **zero
residue** confirmed, not just trusted from `DELETE n` output.

Redis: enumerated every key touching either created account before deleting anything. Deleted
`org:meta:`, `org:slug:`, the owner's `membership:acc:<id>` home key (no `:org:` suffix — older
per-account schema), the crew identity's `membership:acc:<id>:org:<test-org-id>` key (created by
this session's invite/accept), and both accounts' `sess:user:<id>` session keys — 6 keys total.
**Left in place, deliberately:** the crew identity's `membership:acc:<id>:org:org_demo` key —
`org_demo` is the platform's pre-existing shared demo tenant a bare `intent: attendee` signup lands
on by default (same pattern session-064 found and correctly left alone), confirmed by
pattern-matching before any delete. Re-scanned all patterns after deletion — zero unintended
residue.
