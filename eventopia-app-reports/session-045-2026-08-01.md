### What shipped (19 commits, 2 bundled features)

1. **Crew check-in sign-in redesign** (`docs/launch/crew-checkin-login-deploy.md`) — replaces

   admitting scans offline — durable in IndexedDB, never uploaded. New at-receipt partner gate
   blocks un-invited numbers before they get a working link. Redis grant self-heal from the
   durable `staff_membership` row (never resurrects `REVOKED`).

   to just flip status to `REVOKED` with no list filter, so the row stayed visible. Now a real
   `DELETE … RETURNING` + Redis grant clear + `role.removed` audit entry, replacing
   `role.revoked`. **Irreversible by design** — a code rollback cannot restore deleted rows.

### Smoke test — fully automated, no real WhatsApp needed

The crew sign-in challenge is a "reversed OTP": a real inbound WhatsApp message is what marks it
verified (`markVerified`, called from the wa-inbound worker's `handleVerifyTurn`). Rather than
hand-crafting Redis state (bypasses the new partner-gate logic entirely) or a fake Meta webhook
payload (shape/signature risk against real infra), stubbed the **one actually-unavoidable step**
— the inbound HTTP delivery — by calling `handleVerifyTurn()` directly against real prod
Redis+DB, exactly as the real worker does (`@eventopia/api/auth-wa-verify-worker`, same imports,
same `createWorkerWaVerifyService`/`createWorkerPartnerInviteCheck` wiring as
`apps/workers/src/index.ts:355-362`). One gotcha: the script's env must be the **full** prod
`.env` (`bun --env-file=`), not a hand-picked subset — a partial env silently fell back to the
insecure dev PII key on first attempt, caught before trusting the result.

Created one disposable organizer (`org_44498367a70241db`, via real email-OTP signup + Redis-read
code, proven recipe) and one disposable test event. All steps below hit the real production
API/DB/Redis — nothing mocked except the WhatsApp HTTP delivery itself:

1. **Crew removal, full recipe from the deploy note (curl + psql):** invited a disposable number,
   confirmed invite link `200`, `DELETE`d it, confirmed roster excludes it (`{"staff":[]}`),
   invite link now `404`, DB row count `0`, and a `role.removed` audit entry written with the
   correct pre-removal snapshot.
2. **Crew sign-in, invited number:** started a `wa-verify/start` challenge (`intent:staff`, no
   slug — matches the new no-slug client), ran the stub as that invited number →
   `handleVerifyTurn` returned the scanner-link reply (partner gate passed) → polled `status` →
   `verified` → `POST /v1/auth/staff/assignments` correctly listed our test org/event → `POST
   /v1/auth/wa-verify/complete` with the picked `organizerId` minted a session correctly scoped
   (`eventScopes: {evt_...: ["staff_scanner"]}`) → `POST /v1/auth/refresh` (the actual bug this
   deploy fixes) returned a fresh token. Full chain works end-to-end.
3. **Crew sign-in, un-invited number:** fresh challenge, ran the stub as a phone invited to
   nothing → got the "belum terdaftar sebagai panitia" rejection reply, challenge status flipped
   to `rejected` via the real poll endpoint. Confirms the new at-receipt gate (one of the 19
   commits) actually discriminates rather than failing open.
4. **Cross-feature interaction:** re-ran the sign-in stub as the crew member deleted in step 1 —
   correctly rejected. Confirms removal really does cut off check-in access, not just console
   visibility (the exact case commit `3316c6a9` pinned a test for).
5. **UI:** Playwright on `checkin.eventopia.my` — new one-tap sign-in renders (no slug/phone
   fields), 0 real console errors (1 flagged error was an unrelated third-party Cloudflare
   Insights beacon timeout). Screenshot:
   `screenshots/eventopia-session-045-2026-08-01/checkin-new-signin.png`.
6. Core surfaces: `app.` 200, `checkin.` 200, `www.` 301 (expected), `api.` 400 on a no-param
   probe (expected).
