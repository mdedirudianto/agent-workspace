# Session 4 — OpenVPN "peer certificate verification failure" (expired server cert) + renewal

**Date:** 2026-10-08
**Server:** `root@dev` (`154.26.130.96`)
**OS:** Ubuntu 22.04.5 LTS
**Goal:** Find out why the Mac OpenVPN client could no longer connect to the dev OpenVPN server ("peer certificate verification failure"), and fix it.

---

## Symptom

Mac client (`dedi.ovpn`) fails the TLS handshake with `peer certificate verification failure`. Server process healthy: `openvpn@server` up since 2026-04-17, UDP `1194` listening, NTP-synced, `Initialization Sequence Completed`.

Server journal on each attempt (from the Mac's public IP):

```
OpenSSL: error:0A000415:SSL routines::sslv3 alert certificate expired
TLS Error: TLS handshake failed
```

The *alert* is sent by the client: it rejects the server's cert as expired. The `tls-crypt` layer was fine (control-channel wrapping initialised). The recurring `tls-crypt unwrap error: packet too short` lines are unrelated internet scanners on UDP 1194.

---

## Root cause

**The server certificate expired on 2026-09-26 22:38 UTC.** It was issued 2024-06-23 with the Easy-RSA 3.1.2 default lifetime of **825 days**.

| Item | Before | Note |
|------|--------|------|
| Server cert `server_cZHsTk8HdkgmvRYt` | notAfter **2026-09-26** (expired) | root cause |
| Client cert `dev` | notAfter **2026-09-26** (expired) | same 825-day default; embedded in `/root/dev.ovpn` |
| Client cert `dedi` | notAfter 2036-03-07 | issued 2026-03-10 with 3650 days; unaffected |
| CA (`cn_UeTT3zeC0ru3Fmmq`) | notAfter 2034-06-21 | fine |
| CRL | nextUpdate 2034-06-21, 0 revoked | fine |

Not the cause (checked): cert/key mismatch (pubkeys matched), server config, OpenVPN/OpenSSL upgrade (no apt activity), clock skew, `tls-crypt` key.

---

## Research

Easy-RSA 3.1.2 (installed) uses "renew v3" (introduced 3.1.1): re-signs the **cert only, keeping the existing private key**; the old cert moves to `pki/renewed/` and can later be revoked with `revoke-renewed`. Because the CA and the cert CN stay the same, the client's `verify-x509-name server_cZHsTk8HdkgmvRYt name` still matches and **client profiles need no change** for a server-cert renewal. (Easy-RSA 3.2.0 changed/removed `renew`, so this procedure is version-specific.)

Sources: [OpenVPN forum — Easy How-To for expired client/server certs](https://forums.openvpn.net/viewtopic.php?p=121197), [OpenVPN forum — server certificate expired, step by step](https://forums.openvpn.net/viewtopic.php?p=120785), [Easy-RSA PR #547](https://github.com/OpenVPN/easy-rsa/pull/547), [AWS Client VPN renew guide](https://docs.aws.amazon.com/vpn/latest/clientvpn-admin/mutual-renew.html).

## Notes / lessons

- **Easy-RSA defaults bite twice:** certs default to 825 days, the **CRL to 180 days**. When regenerating a CRL always set `EASYRSA_CRL_DAYS`. A lapsed CRL is a full outage that looks like a client-side TLS error.
- The first cut of the monitor script silently skipped client certs (over-escaped tab in a quoted heredoc, then `read` collapsing the empty revocation-date column); caught because the output lacked `client:` entries, fixed by parsing `index.txt` with `awk -F'\t'`. The pre-fix negative test also left one synthetic `EXPIRING` `user.crit` line in the journal at 21:54:51 WIB (not a real alert).
- No alerting existed for this: `dev` has no Netdata, and fluent-bit only ships PM2 logs. Uptime Kuma (`monitor`) is cluster-internal at `10.0.0.3:3001`, unreachable from `dev` (public `status.biji.uk` is).
