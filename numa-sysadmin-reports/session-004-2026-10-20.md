# Session 4 — PM2 empty after reboot: restore apps + enable PM2 startup unit

**Date:** 2026-10-20
**Server:** `root@numa` (`46.250.239.44` / `10.0.0.7` — Contabo VPS)
**OS:** Ubuntu 24.04.4 LTS
**Clock:** Asia/Jakarta (WIB); `pm2.log` is also WIB

---

## Symptom

`pm2 list` on numa was empty. Expected: `numa-home`, `ytgrab-api`, `bgutil-pot`.

## Findings

| Check | Result |
|-------|--------|
| Uptime / `last reboot` | Booted **Oct 19 19:13 WIB**; previous boot `6.8.0-124` (Jun 3) ended in a clean **poweroff at 18:52:59** (journal `systemd-poweroff`). Powered off, then started ~20 min later; the cause is not in the guest logs |
| PM2 startup unit | **None.** No `pm2-root.service` in unit files or `/etc/systemd/system`, so nothing ran `pm2 resurrect` after boot. Earlier boots (Apr 7, Jun 3) predate the current PM2 apps; the dump was only ever relied on in a live daemon |
| `~/.pm2/pm2.log` | `pm2 has been killed by signal, dumping process list before exit` at 18:51:27 (shutdown), then a **new daemon** at 09:25 today, started by the first `pm2 list` of this session |
| `dump.pm2` | Intact (written 18:51 on shutdown): `numa-home`, `ytgrab-api`, `bgutil-pot` |
| Prerequisites | `start.sh`, `ytgrab-api/dist/index.js`, `.env`, `bgutil-pot/server/build/main.js` all present; ports 7009/4416 free; Node v24.14.1; disk 34%, RAM 7.1 GiB free |
| Other services | `cron`, `fluent-bit`, `fail2ban`, `ufw`, `ssh` all active; canary crontab intact |
| Public impact | **None visible.** `youtubegrab.com` stayed up (`gitSha 71dcc62`): `db` (LB weight 1) served all `/api` traffic for ~14 h while numa (weight 2) was down. `db`'s PM2 apps were online at 14 h uptime. The numa canaries (cron survived the reboot) would have run against a dead API from 19:13 until now, so expect Kuma #46/#50–52 DOWN/gap noise for that window; not checked in Kuma |

## Actions Taken

| # | Action | Result |
|---|--------|--------|
| 1 | `pm2 resurrect` | 3 apps restored. `ytgrab-api` boot lines: `rate limiter {"mode":"enforce"}`, `resolved-url cache {"ttlMs":3600000,"node":"numa/v4"}`, `proxy pool refreshed` (100 datacenter + 10 residential), `api listening` on `10.0.0.7:7009` (~4 s). `bgutil-pot` on `*:4416` |
| 2 | Verify | `http://10.0.0.7:7009/api/v1/health` → ok, `gitSha 71dcc62`, db + redis ok. Public `/api/v1/health` and site → 200. After 30 s: 160 request lines on numa (147×200, 8×204, 3×206, 2×422); tier canaries logged UP (direct / datacenter / residential) |
| 3 | `pm2 startup systemd -u root --hp /root` | Created and enabled `/etc/systemd/system/pm2-root.service` (`Type=forking`, `ExecStart=pm2 resurrect`, `PIDFile=/root/.pm2/pm2.pid`) |
| 4 | `pm2 save` | `dump.pm2` rewritten with the same 3 apps |

State after: `pm2-root` is **enabled** and shows `inactive` — expected, because the running daemon was started by hand rather than by the unit. It takes over at the next boot.
