# Session 7 — Multi-domain flapping investigation (api.youtubegrab.com / api.qute.my / qute.my / wa.foucher.co)

**Date:** 2026-09-22
**Server:** `root@proxy` (`46.250.234.153`, internal `10.0.0.2`)
**OS:** Ubuntu 24.04.3 LTS
**Trigger:** Fleet Telegram alerts — `api.youtubegrab.com`, `api.qute.my`, `qute.my`, `wa.foucher.co` all `🔴 Down (timeout of 48000ms exceeded)` within minutes of each other, recovering on their own shortly after.

---

## Summary

Investigated a ~15-minute window (20:45–21:00 WIB) where several unrelated domains proxied through `proxy` — different backend apps, different upstream hosts — went down and recovered together. Found **no fault on `proxy` or its backend (`app`)**: nginx logged zero requests for these domains during the window, no restart/reload happened, system health (load, disk, memory) was nominal throughout, and fail2ban didn't ban anything relevant. All affected domains are Cloudflare-proxied, and the errors seen (`522`, `525`, `526`, plus Kuma's client-side timeout) are Cloudflare's own edge-to-origin connectivity codes. This points to a **transient network-path issue between Cloudflare's edge and the origin**, not an application or server fault — and it self-recovered without any intervention. This is the **second occurrence in two days** (a similar broader flap hit ~10 unrelated domains on 2026-09-21, 16:20–17:16 WIB). No config change was made this session; findings and a monitoring recommendation are recorded here for the next occurrence.

---

## Investigation

**Timeline** (from `uptime-kuma` container logs on `monitor`, WIB):

| Time | Event |
|---|---|
| 20:45–20:59 | `foucher.co` (500), `admin.foucher.co` (525/526), `wa.foucher.co`, `qute.my`, `api.qute.my` (522), `api.youtubegrab.com`, `youtubegrab.com` (ECONNRESET) all flap down/pending/failing, overlapping and repeating every ~60s retry |
| ~21:00 | All recovered; nothing since |

**Confirmed Cloudflare-proxied:** `dig` on all three domains resolves to CF anycast ranges (`104.21.x.x` / `172.67.x.x`).

**Ruled out on `proxy`:**
- `grep "2026/09/22 20:5" /var/log/nginx/error.log` → zero matches — the requests never reached nginx.
- `systemctl status nginx` → running continuously since `2026-09-21 22:04:07 WIB`, no restart during the window.
- `journalctl` 20:44–21:00 WIB → only routine port-scan `[UFW BLOCK]` noise (background, unrelated) and normal cron; no OOM, no disk pressure, no service restarts.
- `df -h /` → 77G free / 20% used — not a disk issue.
- `fail2ban-client status` / `/var/log/fail2ban.log` around the window → only SSH-jail bans of unrelated scanner IPs, `nginx-http-auth` jail untouched. `fail2ban.service` itself last restarted `06:45:53 WIB` (unrelated, hours before the incident).
- Netdata `web_log_1m_*` alarms (successful/bad_requests/internal_errors) — silent during this window, in contrast to yesterday's similar flap where they fired repeatedly. Consistent with traffic never arriving at nginx to log, rather than nginx erroring on it.

**Ruled out on `app`** (upstream for the ytgrab API):
- `uptime` → load 1.20–1.55 throughout, normal.
- `journalctl` 20:44–21:01 WIB → no entries at all (no crashes, no OOM, no restarts).

**Error signatures observed** (from Kuma): `522` (Cloudflare could not open a TCP connection to the origin within its timeout), `525`/`526` (SSL handshake/cert), `timeout of 48000ms exceeded` (Kuma's own client-side timeout), `ECONNRESET`. These are Cloudflare edge-side codes, not application error pages — `522`/`525`/`526` are rendered by Cloudflare itself when it can't complete a connection to the origin, so by definition the origin's nginx/app never saw those requests to log or error on, which matches the empty nginx error log.

**Not the first occurrence:** `telegram-alerts` ledger shows a similar, broader flap on **2026-09-21, 16:20–17:16 WIB** hitting `vault.biji.uk`, `team.wagrab.com`, `api.quranchat.me`, `app.teamy.my`, `blog.wagrab.com`, `qute.my`, `api.qute.my`, `api.youtubegrab.com`, `wa.foucher.co`, GlitchTip, and others — also self-recovering with no server-side trace. Two occurrences in two days makes this a pattern worth watching, not a one-off blip.

---

## Actions Taken

None — no config change on `proxy` or `app`. This was an analysis-only session; no fault was found on infrastructure we control, and the incident had already self-resolved before investigation started.

---

## Recommendation (not yet implemented)

- Add a Kuma monitor that hits `proxy`'s origin IP directly (bypassing Cloudflare — e.g. request with the real `Host:` header against `46.250.234.153`) alongside the existing public/CF-routed monitors for at least one of these domains. Next time this flaps, that will immediately distinguish "Cloudflare can't reach us" (origin monitor stays green) from "we're actually down" (both go red) — right now both scenarios look identical from Kuma's public-URL checks alone.
- If a third occurrence happens, check Cloudflare's dashboard Analytics for the `youtubegrab.com` / `qute.my` / `foucher.co` zones at the exact timestamps — that's the only place edge-to-origin connection failures are actually logged; nothing on our side captures it.
- Worth a quick check of Contabo's status history for this VPS if the pattern continues — `proxy` and `numa` are both Contabo KVMs.
