### WhatsApp Mac media cache — deep dive

User pushed back with a phone screenshot showing WhatsApp's own "Manage Storage" reporting only **432.6MB** used, against the **17GB** found on disk in `~/Library/Group Containers/group.net.whatsapp.WhatsApp.shared/Message/Media` (168,726 files). Investigated root cause:

- **Root cause: WhatsApp for Mac has no media-cache pruning at all.** iOS actively expires viewed Status/Story media (~24h) and offers a storage manager; the Mac (Catalyst) client has neither — every photo/video/PDF/Story ever viewed since 2024-10-10 just accumulates indefinitely. Reinstalling the app would **not** fix this (the Group Container is separate from the app bundle and isn't touched by a plain reinstall, and even a fresh install has the same lack of pruning).
- **Breakdown by content type:** mp4 8.7GB (2,531 files, mostly Status videos), pdf 4.4GB (1,725 files — 1,654 of them from a single business/broadcast contact `210007090057347@lid`), jpg 3GB (22,439 files), thumbnails only 171MB despite 141,440 `.thumb` files.
- **Breakdown by origin:** ~9GB in `*.status`-suffixed folders (viewed Stories — inherently ephemeral, already expired on WhatsApp's servers, zero data-loss risk to delete) vs. ~7.9GB in regular chat/group media folders (real chat attachments, of which 4.2GB is the one PDF-broadcast contact).

User confirmed they had already reviewed the contact and downloaded anything they wanted to keep before approving the wipe.

## Open Items

1. **du vs. df accounting gap** — categories summed via `du` total roughly 63GB (18+18+7.2+1.35+2+17), but the actual `df`/`diskutil` delta was ~43GB. Consistent with the APFS purgeable/snapshot accounting overhead flagged as unreliable in S51-53; no local TM snapshots were found holding blocks (`tmutil listlocalsnapshots` showed only OS-update snapshots), so the gap is most likely block-sharing/compression overlap in `du`'s reporting rather than genuinely un-reclaimed space. Worth treating `du`-per-category estimates as directionally correct but not additive going forward.
2. **Docker, iOS Simulator, and Android AVD are now fully gone** — next time any of grobiz's local dev/QA work needs them, expect: Docker Desktop reinitializing a fresh VM (reseed the stack from compose files), Xcode redownloading the iOS 26.3.1 runtime before `GroBiz-QA-iPhone17` can be recreated, and Android Studio redownloading the `android-36` system image for `grobiz-qa-36`.
3. **pnpm/npm/Chrome cache regrowth automation** — carried forward again from S52/S53 (now 7 consecutive sessions flagging this as recurring manual toil); still not implemented.
4. **WhatsApp media cache has no built-in pruning** — this will silently regrow the same way over time since the Mac client doesn't expire anything. No fix available beyond periodic manual `rm -rf` on `Message/Media` (safe to repeat; confirmed it's pure re-fetchable cache, not the message database).
