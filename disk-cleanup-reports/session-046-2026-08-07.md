# Session 46 — Root-Caused the Docker.raw Climb: 160 Abandoned ERPNext Tenant DBs

**Date:** 2026-08-07

**Disk before:** 90% used — 21GB free
**Disk after:** 72% used — 58GB free
**Recovered:** ~37GB (Phase 1: ~37GB bulk cleanup · Phase 2: ~157MB uninstalled-app leftovers)

---

## Context

One day after S45 (28.2GB free), free space was back down to 21GB. User asked for an analysis-and-recommend pass. The survey found that the Docker.raw growth flagged as unexplained across S43/S44/S45 had a concrete cause that `docker system df` had been actively hiding, and that a single Next.js dev cache had ballooned to 5.2GB overnight.

Presented tiered recommendations via AskUserQuestion; user approved all three tiers (excluding miaw-call node_modules) plus codex, ComfyUI, and the Docker installer dir, and chose to nuke the MariaDB volume outright rather than drop tenant DBs selectively.

---

## Findings

### Root cause: `docker system df` was under-reporting by 16GB

Three prior sessions recorded "Docker.raw is 21GB but only ~1GB reclaimable" and concluded prune structurally couldn't help. That reading was correct but incomplete — the reclaimable figure only counts *dangling* resources. The weight was in **active local volumes: 17.78GB**, which `docker system df` reports as 0% reclaimable because a (stopped) container still referenced them.

Measuring from inside the VM (`docker run --privileged -v /:/host alpine du -sh /host/var/lib/docker/volumes/*`) showed:

| Volume | Size |
|---|---|
| **`grobiz_mariadb-data`** | **16.1GB** |
| `grobiz_erpnext-apps` | 585.8M |
| `grobiz_erpnext-sites` | 138.3M |
| `grobiz_redis-data` | 54.9M |
| 4 anonymous volumes | 21.9M each |

Inside `grobiz_mariadb-data`: **160 `_<hash>` site databases at ~95.5MB each (~15GB)** — per-tenant ERPNext sites accumulated from grobiz multi-tenant provisioning runs. Oldest **Jun 17**, newest **Aug 3**. The whole `grobiz-*` stack had been stopped for 25 hours. Actual schema/engine files (`ibdata1` 332M, `ib_logfile0` 96M, `mysql` 329M) were a rounding error by comparison.

**Lesson for future sessions:** when Docker.raw is large, measure volumes from inside the VM rather than trusting the `RECLAIMABLE` column.

### Docker.raw compacted itself

**`Docker.raw` fell 21GB → 6.7GB with no manual intervention.** Docker Desktop's automatic TRIM reclaimed the space into the sparse file within seconds of the volume removal. S45's next-session note anticipated needing Docker Desktop's destructive "Clean/Purge data" or a lowered disk cap — **neither was necessary.** The correct lever was always removing the data inside the VM; compaction follows on its own.

## Phase 2 — Uninstalled-App Leftovers Audit

User asked for a follow-up sweep of caches/leftovers belonging to apps no longer installed, **excluding Chrome, Claude, and WhatsApp**.

**Method:** built an inventory of 121 installed `.app` bundles (`/Applications`, `~/Applications`, `/System/Applications`) plus 8 Homebrew casks, then cross-referenced it against `Application Support`, `Caches`, `Containers`, `Group Containers`, `Preferences`, `Logs`, `HTTPStorages`, `WebKit`, and home dotfiles.

A first pass matching on **bundle ID** was near-useless — most Library folders are named by human-readable app name (`Zed`, `Cursor`, `obsidian`), not reverse-DNS, so it produced only false positives. The pass that worked was **name matching + directory mtime**, with staleness as the primary signal.

Remaining launch agents verified legitimate: `watchman`, `redis`, `mongodb-community` are all live Homebrew formulae; CCleaner / Google / Zoom are installed apps.

### SIP blocked the Container directory husks

`rm -rf` on `~/Library/Containers/*` returned `Operation not permitted` — **including under `sudo`** — because `containermanagerd` metadata is SIP-protected and the shell lacks Full Disk Access.

**The sudo pass did reclaim the contents** (WPS Office went 17MB → 40KB), leaving only empty directory shells of 32–40KB each:
`com.kingsoft.wpsoffice.mac.global` (+`.recentfiles`), `net.pixiv.vroid.macosx`, `com.canva.canvaeditor`, `org.blenderfoundation.blender.thumbnailer`, `com.1password.1password-launcher`, `com.1password.browser-support`, `2BUA8C4S2C.com.1password.browser-helper`.

Removing the husks requires granting Terminal Full Disk Access in System Settings → Privacy & Security. ~250KB total — not worth it for space, only for tidiness.
