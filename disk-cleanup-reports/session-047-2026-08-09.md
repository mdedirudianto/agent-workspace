# Session 47 — Disk Hit Zero: Unity Installer Staging and Chrome Code-Sign Clones in TMPDIR

**Date:** 2026-08-09

**Disk before:** 100% used — 1.1GB free
**Disk after:** 77% used — 48GB free
**Recovered:** ~47GB (Emergency: ~25GB · Tier 1: ~5GB · Unity: ~8GB · Tier 2: ~7GB)

---

## Context

Two days after S46 closed at 58GB free, the disk was at **1.1GB free — 100% capacity**. Mid-survey the volume hit true zero and tool output began failing with `ENOSPC`, so the session split into an emergency phase (act first, survey later) and a normal tiered phase.

The cause was not any of the tracked repeat offenders. **~37GB had accumulated in `$TMPDIR` (`/private/var/folders/99/…`)**, a location no prior session had surveyed — every previous session had scanned `~/` and `~/Library` but never the per-user temp directory, which is on the same volume.

---

## Findings

### The 194GB / 70GB discrepancy that led there

`du -sh /Users/dedi/*` totalled ~70GB against 194GB used. Two gaps explained it: the glob skips dotfiles (~18GB), and **44GB sat in `/private/var`**, of which **40GB was `/private/var/folders/99/qwjpxb7523d_8tmnlyj15bhh0000gn`** — the user's `$TMPDIR` and `X` (code-sign clone) directories.

**Lesson for future sessions:** start the survey with `df` vs. `du /Users/dedi` and chase the *difference*. `~/` is not the disk.

### New offender #1 — Unity Editor installer staging (19GB)

| Item | Size | Detail |
|---|---|---|
| `$TMPDIR/unity-editor-pkg-{0Edh0I,c6zjWE,haMf6Z,hvxwzF}` | **4 × ~4.8GB = 19GB** | Each held `Unity.pkg.tmp/Payload` — a 5.06GB uncompressed Unity Editor installer payload |

All four dirs stamped Aug 9 03:35; the `Payload` files dated Jul 22. Unity Hub was **not running**, and the editor had already installed successfully to `/Applications/Unity/Hub` on Aug 8 12:34. These were staging dirs from four install attempts that Unity Hub never cleaned up — the single largest one-shot leak this workspace has recorded.

### New offender #2 — Chrome code-sign clones (18GB reported, 3GB real)

`$TMPDIR/../X/com.google.Chrome.code_sign_clone/` held **13 clone directories of 1.4GB each**, 12 of them orphans from repeated Chrome relaunches between Aug 8 22:19 and Aug 9 00:48. macOS creates one of these each time Chrome relaunches while running; they are normally reaped.

**`du` reported 18GB but deleting 12 of them freed only 3GB** — they are APFS copy-on-write clones sharing blocks with `Google Chrome.app`. Only the diverged blocks are real.

**Lesson:** for anything named `*clone*` on APFS, `du` is an upper bound, not a measurement. Trust the `df` delta.

The newest clone (`s12Kkp`, 14:03) was kept — it belongs to the running Chrome, which was unaffected throughout.

### Timing hazard: a live build was running

A mid-session process check found **GradleDaemon 9.0.0 (pid 19987) and a Kotlin compile daemon actively reading `~/.gradle/caches/modules-2/`**, with the `grobiz_a36` emulator up headless — the `fix-mobile-receipt-back` worktree had a commit from 13:58, one minute before the session started.

Deleting `~/.gradle/caches` at that moment would have broken a running build. The Gradle items were **held**, the safe Tier 1 items ran first, and the deletions were executed only after the daemon dropped to 0.0% CPU and the emulator exited.

**Lesson:** `pgrep -fl "gradle|xcodebuild|qemu|emulator|metro"` before removing any build artifact. Prior sessions checked whether *apps* were running, never whether a *build* was.

### Docker: restart failure, then a dead-end reclaim

Docker's daemon was down at survey time. `open -a Docker` left it half-started — `com.docker.backend` running, but no Electron UI, no VM, and no socket. Its log showed a shutdown at 13:51, **the same minute the disk hit zero**: Docker had been killed by the full disk and came back wedged.

Fix: `osascript quit` → `sudo kill -9` the surviving backend PIDs → relaunch. **Daemon up in 20s.**

The reclaim itself yielded nothing:

| | Total | Reclaimable |
|---|---|---|
| Images | 7 / 3.188GB | 29.43MB (0%) |
| Containers | 10 / 36.66MB | 122.9kB (0%) |
| Local volumes | 14 / 1.9GB | 3.7kB (0%) |

`docker image prune -f` → **0B**. `Docker.raw` stayed at 6.6GB, unchanged from S46.

The reason is that **the grobiz ERPNext stack has been re-provisioned** since S46 (`grobiz_mariadb-data` exists again) and auto-started with the daemon. The 6.6GB is live data, not garbage. Reclaiming it now would mean destroying a working stack — declined.

> **Watch item:** S46 root-caused Docker.raw's climb to 160 orphaned ERPNext tenant DBs in `grobiz_mariadb-data`. That volume is back and the stack is running. Without a teardown step in the provisioning flow, the 16GB leak will rebuild.
