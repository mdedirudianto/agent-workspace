# Session 7 — Private-network outage: `app` isolated from the 10.0.0.0/22 fabric, every app-backed site 502 (~1 h 30 min)

**Date:** 2026-10-23
**Server:** `devops@app` / `root@app` (154.26.129.104 / 10.0.0.5), with `proxy`, `db`, `monitor`, `backup`, `erp` as read-only vantage points
**OS:** Ubuntu 24.04.4 (app), QEMU/virtio guest

**Summary:** Every site that `proxy` forwards to `app` returned 502 from 05:50 WIB, while `proxy` itself and the static sites (`sijari.uk`, `meetgrab.us`) stayed up. nginx logged `connect() failed (113: No route to host)` for `10.0.0.5`. All five other private hosts reached each other and none could reach `app`; `app` could reach none of them (ARP `FAILED`/`INCOMPLETE` for `.1 .2 .3 .4 .6`). `app` itself was healthy: 48 PM2 entries online, services listening on `10.0.0.5`. A packet capture on `app`'s `eth1` showed its ARP requests going out with no replies, and `proxy`'s requests for `10.0.0.5` never arriving. Capture on `proxy` and `db` showed `app`'s requests never arriving there either, so the switch port was dead in both directions. Cause: `eth1` lost carrier at 05:51:37 WIB (10 s) and never carried traffic again; netplan, sysctls and ufw were unchanged, so the fault sits on the provider's virtual switch. Same signature as the `db` outage of 2026-10-22 ([grobiz session-070](../grobiz-app-reports/session-070-2026-10-23.md), finding 2). A firewall check, an `eth1` down/up and a guest reboot did **not** help. The user then did a shutdown and start from the provider panel (~07:20 WIB) and the private network came back immediately. All 48 PM2 entries resurrected on their own, 502s stopped at 07:25 WIB, and every site checked answered.

## Incidents

- **Outage:** the above. Impact: all sites proxied to `app` (`10.0.0.5`), ~1 h 30 min. Static sites on `proxy` were unaffected. Follow-ups below.
- **Alerting:** the user noticed at 06:53, about an hour after the start. Whether Kuma/Telegram alerted for the 05:50 start was **not checked** (the local `telegram-alerts/ledger.jsonl` stops at 2026-09-22; the authoritative one is on `monitor`). See follow-up.
- **Secrets:** none printed. A public GlitchTip client DSN key appeared once in a trimmed access-log line; it is public by design (embedded in browser JS), not a secret.
- **Prod writes by tests:** none. Smoke checks were GET only.
- **Our own scripting slips (no effect):** an unquoted shell variable and an `arping` that is not installed on `proxy` caused two failed command runs before the capture worked.

## State after

- `app` up since 2026-10-23 07:20:43 WIB (02:20:43 CEST), kernel unchanged, PM2 48/48 online. `pm2-devops` resurrects everything by itself: load peaked at 41 about 4 min after boot and fell to ~5 by 07:28.
- Private fabric: all 7 hosts ok. Latency on pairs involving `app` and `monitor` was still elevated at 07:28 (finding 8).
- Docs updated: `docs/fleet/profiles/servers/app.md` (v3, failure signature and boot-time notes) and `docs/fleet/open-decisions.md` (R16).
