# Session 4 — grobiz-sites.sh backed up only 1 of 11 tenant sites per run (stdin-eating ssh bug)

**Date:** 2026-08-03
**Server:** `root@backup` (public `194.233.81.93`, internal `10.0.0.4`)
**OS:** Ubuntu 22.04.5 LTS
**Trigger:** Building a Telegram-alert ledger tool (see `telegram-alerts/`) surfaced a recurring weekly `[verify] FAILED grobiz-site:59aba5d4.gro.biz.id — no db archive` alert, unaddressed since 2026-07-14.

---

## Summary

`jobs/grobiz-sites.sh` enumerates tenant ERPNext sites on `erp` and loops over them to back each one up. The loop has run since the job was introduced (session-006 in `grobiz-app-reports`, 2026-06-07) but **has never backed up more than one site per run** — a classic bash pitfall where an `ssh` call inside a `while read ... done <<< "$var"` loop shares the loop's stdin, so the first `ssh` invocation drains the rest of the site list and the loop silently exits after one iteration. `erp` now has **11 real tenant sites**; only whichever one sorted alphabetically first at any given time was ever actually backed up. Fixed with a one-line stdin redirect and verified all 11 sites back up in a single run.

---

## Root Cause

```bash
while IFS= read -r SITE; do
    ...
    ssh $SSH_OPTS root@"$REMOTE_HOST" \
        "sudo -u frappe bash -lc \"cd $BENCH_DIR && bench --site $SITE backup --with-files\"" >> "$LOG_FILE" 2>&1
    ...
done <<< "$SITES"
```

`ssh` without `-n` or a redirected stdin inherits the calling shell's stdin — here, the `<<< "$SITES"` here-string feeding the loop. On the first iteration, `ssh` reads (and discards) whatever remains of `$SITES` from stdin before running its remote command. The next `read -r SITE` then hits EOF and the loop ends after exactly one site, every run.

Confirmed against `backup.log` history: the single site processed per run tracked `ls -1`'s alphabetical order among currently-existing tenant sites, shifting each time a new, alphabetically-earlier site was provisioned on `erp`:

| Site (first char order) | Backed up exclusively | Until |
|---|---|---|
| `59aba5d4` | since job creation (2026-06-07) | 2026-06-18 |
| `55b00350` | 2026-06-18 | 2026-07-26 |
| `322b1717` | 2026-07-26 | 2026-07-27 |
| `05110a77` | 2026-07-27 | this fix (2026-08-03) |

Each switch lines up with a new site being provisioned that sorted earlier than the incumbent (`3... < 5...`, `0... < 3...`). `erp` currently has 11 real tenant sites (`ls /home/frappe/frappe-bench/sites/ | grep gro.biz.id`, excluding `erp.gro.biz.id` and `pool-*`); this job backed up at most 1 of them on any given run since it existed — the other 9–10 had **zero** bench backup coverage the entire time, silently.

The weekly `verify.sh` only checks whatever the most recent `grobiz-sites` run happened to produce, so it only ever flagged the one site that had *just* fallen out of rotation (`59aba5d4`, since 2026-07-14) rather than the much larger gap.

## Notes

- The fix only touches the direct `ssh` call for `bench backup`. The `rsync -a -e "ssh $SSH_OPTS" ...` call in the same loop was not affected — `rsync` manages its own SSH transport pipe rather than sharing the parent shell's stdin, which is also why the bug never manifested as an rsync failure.
- This is the same class of bug documented in [Session 3](session-003-2026-06-20.md) (Tier 2 silently missing 8 DBs) — a job that "usually looks green" (no error, no non-zero exit) while quietly covering far less than it should. Worth a quick skim of the other per-site/per-DB loop jobs (`tier2-pg.sh` is already auto-discovery and fine; nothing else in `/opt/backup/jobs/` currently loops with an `ssh` call inside a `while read <<<` construct, checked via `grep -l 'while.*read' jobs/*.sh`).
- Next scheduled run that exercises the fixed path: the regular 6-hourly cron (`0 0,6,12,18` WIB) via `backup-grobiz.sh`. The manual run above already populated fresh backups for all 11 sites today.
- Discovered via the new [telegram-alerts/](../telegram-alerts/) ledger tool, not a scheduled sweep — worth periodically running `pull.sh` and reading the tail rather than waiting for a copy-pasted Telegram message to prompt investigation.
