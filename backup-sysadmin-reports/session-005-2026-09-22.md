# Session 5 — grobiz verify false positives: 16 "no db archive" FAILs were orphaned dirs, not lost backups

**Date:** 2026-09-22
**Server:** `root@backup` (public `194.233.81.93`, internal `10.0.0.4`)
**OS:** Ubuntu 22.04.5 LTS
**Trigger:** Fleet Telegram alert — `Backup verify FAILED: grobiz-site:05110a77.gro.biz.id grobiz-site:2caaaf0a.gro.biz.id ...` (16 sites), 2026-09-22 21:02 WIB.

---

## Summary

The alert looked like a mass backup failure across 16 grobiz tenants, but **no tenant data was ever missing or corrupt** — every one of the 16 flagged names had a healthy, current, verified-OK backup sitting right next to it under a different (correct) directory name. The FAILs were **orphaned local snapshot directories** left over from a site-naming change on `erp` back in August, whose last stale file finally aged out of GFS retention today, leaving 15 previously-populated dirs empty plus one long-dead tenant dir (`05110a77`, gone since before [session-004](session-004-2026-08-03.md)) — and `verify.sh` scans every local directory unconditionally, so it flagged all 16 the moment they went empty. Removed the 16 stale directories and patched `rotate.sh` to self-clean empty grobiz site dirs going forward, so this class of false positive can't reaccumulate.

---

## Root Cause

`jobs/grobiz-sites.sh` dynamically enumerates tenant sites from `erp` (`ls sites/ | grep '\.gro\.biz\.id$'`) each run and creates a local mirror directory per site under `$BACKUP_ROOT/bench/grobiz/<site>/`. [Session 4](session-004-2026-08-03.md) (2026-08-03) confirmed the 11 tenant sites at the time were named bare `<hash>.gro.biz.id`. Sometime before **2026-08-23**, grobiz's per-tenant ERPNext sites on `erp` were renamed to include the `.erp.` segment (`<hash>.erp.gro.biz.id` — same restructuring documented in [erp-sysadmin session-003](../erp-sysadmin-reports/session-003-2026-09-22.md)'s domain layout). `grobiz-sites.sh` picked up the new names automatically (it's live-enumerated, not hardcoded) and has been backing up all 37 current tenants correctly under `.erp.` names ever since — but it never deletes the *old* local directories for names that stopped appearing in the live list. Those old bare-hash dirs kept their last pre-rename backup file (dated `20260823...`) sitting untouched.

`verify.sh`'s `verify_grobiz()` loops over **every directory** under `$BACKUP_ROOT/bench/grobiz/*/` unconditionally — it has no notion of which site names are still live on `erp`. As long as a stale dir still had its one old file, it passed (stale but present). Today, `rotate.sh`'s GFS intraday/daily/weekly retention (30-day / 726h ceiling) finally expired that last `20260823` file in each of 15 dirs in the same run — confirmed via `[rotate] grobiz pruned .../<hash>.gro.biz.id/20260823_...-database.sql.gz (age 726h)` log lines for all 15 — leaving them empty. `05110a77.gro.biz.id` was already empty/stale going back to session-004 (that tenant no longer exists on `erp` at all). `verify.sh` flagged all 16 as `FAIL - no db archive` in the same run, which read as a mass failure.

Meanwhile the real, live backups (`<hash>.erp.gro.biz.id`, matching current `erp` site names) all verified `OK - gzip intact` in the exact same run — confirmed by cross-referencing `erp:/home/frappe/frappe-bench/sites/` (37 real tenant sites, all named `.erp.gro.biz.id`) against `backup.log`.

## Notes

- This is a **verify-script blind spot**, not a data-loss incident — worth remembering the next time a `grobiz-site:... no db archive` alert fires shortly after any tenant-site rename/decommission on `erp`: check whether the flagged name has a sibling `.erp.gro.biz.id` (or whatever the current naming is) directory that verified OK before assuming data is actually missing.
- The fix is self-cleaning going forward: any time a tenant site is renamed or removed on `erp` again, its old local dir will empty out naturally over the 30-day GFS window and `rotate.sh` will now `rmdir` it in the same run instead of leaving it for `verify.sh` to flag.
