## 5. Observations

- ⛔ **The result page crashes when the Audio tab opens on ~24% of videos (pre-existing, not a regression).**
  - `/process` lists yt-dlp format IDs like `140-drc` (DRC audio). The web picker defaults to the highest-bitrate audio, which is often the `-drc` twin.
  - It builds the download URL during render. `api-client`'s `getDownloadUrl` throws `TypeError: itag must be a single integer or two comma-separated integers`, and the page falls to "Something went wrong".
  - Reproduced on production at 1280 and 390 px (`jVGJwKsiWT0`).
  - **Size**, from the `videos` rows seen in the last 7 days (10,467):
    - **2,491 (23.8%) crash on opening Audio**;
    - 2,825 (27.0%) have a pickable row that crashes;
    - 67 have no muxed formats, so Audio is their first tab and the page can crash on load.
  - The server never sees it: the throw happens before any request, so no API log or `download_events` row shows it. GlitchTip should have it; not checked (no `monitor` access this session).
  - The code dates from the picker's first version (2026-05-19), so rolling back doesn't help.
  - This is repo FOLLOW_UPS **B2-4** (report C8), which recorded only the 400 side. It's now 🔴 there, with a web-only hotfix option: drop formats that fail the itag rule from the picker, and never throw from render.
  - **Stopped here per "stop on any issue"**; the fix needs the user's go-ahead (web deploy ~6 min).
- **A repeat served by a residential entry still pays datacenter first.** Reuse runs inside the tier walk, at the entry's own tier. Datacenter is bot-challenged for many videos, so such a repeat spends ~8–10 s of fresh datacenter attempts, then reuses residential (~1 s). That's why residential reused rows sit at 10–14 s while datacenter reused rows are ~2 s. It's in repo FOLLOW_UPS "Batch 3 in production", with a fix direction: remember briefly that datacenter failed for this video + format.
- **Concurrent misses seen:** a download manager opened four segments of one format before the first response, and each resolved fresh (8.8–21.9 s). Then later segments reused (1.2 / 2.1 s). This was the expected, unbuilt single-flight item.
- **The restarts cut some in-flight visitor downloads again**, as in session-040. That is the known drain-at-nginx item (repo FOLLOW_UPS B3-6).
  - A merged `UC4dEPqmEcE` 1080p failed at 09:32:51 with 51.8 MB sent, 2 s before db's restart.
  - Four `muxed` rows of two videos, started 09:23–09:30, are left `ok` / 0 bytes / `completed_at` NULL. They were download-manager segments that resume.
- The local `ssh` running the detached build returned only when the build ended. The `&` covered the whole `cd && date && nohup …` list, so the backgrounded subshell held the channel. The build itself was fully detached (`nohup`, stdio to files). Next time, background only the `nohup` command.
