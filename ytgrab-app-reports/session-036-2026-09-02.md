## 2. Root cause of the transcript failures

YouTube's **subtitle endpoint rate limits well before the player does**, so a burst of caption requests from one exit IP trips a 429 while metadata through the same binary keeps working. That asymmetry is exactly why transcripts looked *intermittently* broken (0% one day, 50% the next) rather than plainly rate limited.

**And our code made it terminal.** `attemptDirect` in `extractors/ytdlp.ts` documented its policy as:

> Only a bot challenge falls through to the proxy tiers. Everything else … is not something another exit IP fixes.

A 429 is the clearest possible case of *"another exit IP fixes this"* — and it was not on the list. It arrived as a bare `ExtractorError`, died on the direct tier, and the request failed outright **with a healthy proxy pool sitting unused**.

The download path had already reached the opposite conclusion: an upstream 429 there parks the direct tier (`markDirectChallenged("upstream 429")`). Extraction was simply inconsistent with it.

## 3. api 1.15.1 — what shipped

Commit `c4bbdc1`, deployed to `numa` (04:50 WIB). New `RateLimitedError` + `isRateLimited` matcher, classified at all three yt-dlp entry points (metadata, captions, stream-URL resolve).

| Property | Behaviour |
|---|---|
| Direct tier | 429 now falls through instead of terminating; parks direct as `"rate limited (429)"` |
| Proxy loop | Treated as **soft**, `countTowardHealth: false` |
| Progressive-client chain | **Excluded** — a 429 must not advance the chain |
| Genuinely terminal errors | Unchanged (private/region-locked video still fails fast, one attempt) |

Two deliberate choices worth recording:

- **A separate error type from `BotChallengeError`,** though they share a retry policy. They are different facts, and reporting a 429 as a challenge would send the next investigation at the PO Token provider, which has nothing to do with it.
- **Excluded from the client chain.** A 429 means this exit has already been told it is asking too often; trying two more clients from the *same* IP is the one response guaranteed to make it worse, and it would spend two more POT mints doing so. Changing exit fixes a rate limit; changing client does not.

**A bug I introduced and caught before shipping:** my first cut left `isChallenge = err instanceof BotChallengeError`, which put `RateLimitedError` in the **hard** branch — charging a YouTube-side rate limit to *proxy health* and disabling a working pool for something it had no part in. That is precisely what the surrounding comment warns against. Fixed to a `youtubeSide` predicate covering both.

**Tests:** 329 passing in `apps/api` (up from 324) — five new cases covering fallthrough, direct parking, the soft/no-health classification, terminal errors still being terminal, and the chain-abort guard.

### Verified live

The tier walk does exactly what it should:

```

datacenter × 3   (soft, health untouched)
residential × 3  (soft, health untouched)
```

**But it still ends in 502 for the videos I tested**, because all six exits were rate limited at once. Which brings me to the honest caveat.

## 4. The honest caveat: I was measuring my own load

The 429s I kept reproducing were **self-inflicted**. Fifteen sequential caption requests, then repeated retries, from one host — that is precisely the burst pattern that trips the limit. Production caption volume is ~20–33/day.

The same videos that 502'd through the API succeeded moments later when run by hand, **both direct and proxied**. So the limit is transient and burst-driven, not a property of those videos.

The `BotChallengeError`s appearing alongside are the same story from the other end: `run-ytdlp.ts` documents that load starves the single-threaded POT minter, and I was the load.

**So the fix is correct in principle and verified mechanically, but its benefit under real traffic is unproven** — and it carries a real cost I should name: a 429 that *does* affect every exit now costs ~40 s and six yt-dlp spawns before failing, where it used to fail instantly. Under a genuine broad limit that is worse, not better. Worth revisiting with a cap (one alternate exit rather than the full walk) if organic traffic shows it. **Do not read my burst tests as evidence either way; watch organic transcript volume.**

## 9. C4 completed — api 1.16.0 / web 1.15.3 (`0b7b1d9`)

Session-035 shipped C4 partial. It is now done.

Every probe carries `playerClient` and a `clientAttempts[]` list — each configured client in order with `ok` and a trimmed reason — through `ProxyProbeSchema` in `packages/contracts` and into the admin proxy-doctor panel, which flags **"first choice failing"** when a later client had to carry the resolve.

**This is the gap that let the September regression run for a week.** The per-tier canaries measure *tiers*; nothing measured *clients*. `web_safari` went 20/20 → 0/14 while every canary reported the tiers healthy — and it was right to. A probe saying "datacenter is fine" while the first-choice client is dead is telling the truth and still missing the outage.

The probe walks the chain but **deliberately ignores the demotion breaker**: one that inherited the breaker's state would report a client dead because it was already *believed* dead, and since the breaker only clears on expiry that belief would be self-confirming for as long as the canary kept running. Both invariants are pinned **at the source level** rather than with mocks so they survive refactors — `recordClientOutcome` joins the existing read-only mutator blocklist, and a new guard asserts the prober never calls `isClientDemoted`.

**Verification:** 333 api tests; workspace lint/typecheck/build/test all green on Node 24 (17/17 tasks). Public LB `0b7b1d9` on 4/4 probes with distinct uptimes, public download a valid MP4, and `scripts/smoke-web-assets.mjs` reports **22 referenced assets + image optimizer all served correctly** — the check session-033's outage existed for.

## 10. "Muxed formats are unavailable" — user-reported, root-caused, fixed (api 1.17.0)

User reported the web UI showing:

> Muxed (combined audio/video) formats are unavailable. Try audio-only or video-only downloads.

### The cause: metadata and resolve were asking different clients

`playability.missingMuxed` is set in `process-video.ts` when `bucketFormats` produces an empty `muxed` bucket. That bucket comes from the **metadata** extraction — and metadata had no client override. It used yt-dlp's default.

Since late August 2026 that default returns **no progressive formats at all**. Measured on production IDs:

| | default client | `mweb` |
|---|---|---|
| jM7Eou4bV-Q | **NONE** | `['18']` |
| 8gcxP6XfAHI | **NONE** | `['18']` |

**7 of 8 sampled videos had no muxed format on the default client.** So the format list had no muxed entry, `missingMuxed` went true, and every client — web, extension, mobile — showed the warning.

**Meanwhile the download path worked fine.** `YTDLP_PROGRESSIVE_PLAYER_CLIENT` gave the *resolve* step a POT-bearing client, and I had downloaded both those exact videos end-to-end earlier in this very session. **The API was refusing to offer a format it could cook.**

It also explains an anomaly noted back in session-034 and left unexplained: `muxed` volume fell from ~900/day to ~100/day after 08-24. That was not users losing interest — it was the UI hiding the option.

### The fix

New `YTDLP_METADATA_PLAYER_CLIENTS` (default `default,mweb`), passed as `player_client` on the metadata invocation so several clients' format lists merge in **one** yt-dlp call.

**A list, not a swap**, and that distinction has teeth: `mweb` alone cannot see DASH at all (SABR), so replacing the default would have traded every 1080p option for a 360p one. Together they yield strictly more:

| | default | default,mweb |
|---|---|---|
| muxed | 0 | **1** |
| audio | 10 | **14** |
| video | 18 | **19** |

**Cost:** ~2.2 s per *uncached* extraction — one extra player fetch inside the same process, deliberately not a second spawn, because every spawn taxes the single-threaded POT minter. Metadata is Redis-cached (30 min TTL), so it is paid once per video per TTL. `""` reverts without a deploy.

Left alone deliberately: `sharedUrlCacheUsableFor` still distrusts the shared URL cache for progressive itags. Its docblock reasons from "metadata runs on the default client", which is now only half true, but the guard errs safe and relaxing it needs its own evidence.

### Deploy + the cache detail that mattered

`ff29a1b`, both API nodes, `YTDLP_METADATA_PLAYER_CLIENTS=default,mweb` appended to both `.env`.

**The fix did not appear at first**, and the reason is worth recording: metadata is cached for 30 minutes, so already-processed videos kept serving the pre-fix answer. Verified on *uncached* IDs first (`kJQP7kiw5Fk`, `9bZkp7q19f0` → `muxed=['18']`), then dropped the stale keys.

⚠️ **That Redis is shared — 30,081 keys, most belonging to other apps.** So: a scoped `--scan --pattern "video:meta:*"` delete of exactly **14 keys**, never a `FLUSHDB`. 30,067 keys left untouched.
