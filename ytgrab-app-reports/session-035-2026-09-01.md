### 1.3 `bgutil-pot` heap cap (≈23:20) — and a correction

Session-034 recorded this as *"recommended 2026-08-02, never applied."* **That was half wrong and worth stating precisely.**

The pm2 **saved dump** on both nodes already had it:

```
node_args: ['--max-old-space-size=1536']
max_memory_restart: 1258291200      # 1200 MB
```

But the **running processes did not**:

```
$ tr '\0' ' ' < /proc/$(pm2 pid bgutil-pot)/cmdline
node /root/bgutil-pot/server/build/main.js       # no --max-old-space-size
```

So the fix was configured months ago and the live process never picked it up — which is exactly consistent with the OOM traces (`Mark-Compact 1995.4 (2054.8) → …` then `FATAL ERROR: Reached heap limit`, i.e. the **default ~2 GB** ceiling, not 1536 MB) and the 11 / 8 restarts. A saved pm2 config is not evidence that the running process has it; `/proc/<pid>/cmdline` is.

Recreating the app with `--node-args` **still** did not put the flag on the cmdline, so I used `NODE_OPTIONS`, which node honours unambiguously and which is verifiable in the child's environment:

```bash
pm2 delete bgutil-pot
NODE_OPTIONS="--max-old-space-size=1536" pm2 start /root/bgutil-pot/server/build/main.js \
  --name bgutil-pot --max-memory-restart 1200M --cwd /root -- --port 4416
pm2 save
```

Verified on both: `NODE_OPTIONS=--max-old-space-size=1536` present in `/proc/<pid>/environ`, `max_memory_restart` 1200 MB live, `/ping` healthy, tokens still minting, downloads still `206`.

Belt and braces on purpose: pm2 restarts the process at 1200 MB RSS **and** V8 now caps the old space at 1536 MB, so neither path reaches the 2 GB wall that was crashing it.

## 3. What is in the repo but not in production

Three commits on `main`, `apps/api` **1.15.0**:

| SHA | Commit |
|---|---|
| `306b338` | `docs(api): analyse the September progressive-client regression` |
| `07cef99` | `feat(api): try a chain of progressive player clients, and demote dead ones` |
| `f461c14` | `chore(release): apps/api 1.15.0 — progressive client chain` |

**What it does.** `YTDLP_PROGRESSIVE_PLAYER_CLIENT` becomes a comma-separated priority list (default `mweb,web_safari,android`); a single value still parses as a one-element chain, so no `.env` migration is required. The chain is bounded by a circuit breaker in a new `extractors/client-health.ts`, modelled on the direct-tier breaker in `proxies/pool.ts`: `YTDLP_CLIENT_DEMOTE_STREAK` (5) consecutive failures park a client for `YTDLP_CLIENT_DEMOTE_MS` (30 min), success resets the streak, the park expires on its own.

**Why the breaker is the load-bearing part, not the chain.** Every attempt spawns yt-dlp; every spawn asks the single-threaded bgutil POT provider for a token; starve it and yt-dlp proceeds *without* one, which is what produces "Sign in to confirm you're not a bot". A naive chain would have traded a resolver bug for a bot-challenge bug. Demotion keeps the steady-state cost at **one spawn per download even when the first choice is dead**.

New observability, which is the half that was actually missing: `progressive client fell back` `{itag, from, to}`, `progressive client chain exhausted`, `progressive client demoted`, and a `resolverDegraded` flag on both media-403 log lines so *"we had no servable URL"* is finally distinguishable from *"googlevideo refused a good one"*.

**Tests:** 324 passing in `apps/api` (up from 309), including a new `client-health.test.ts`. Workspace `lint`, `typecheck` and `build` all clean.

⚠️ **`pnpm -w test` fails on 20 pre-existing `apps/web` tests** (4 files: `home-shell.test.tsx`, `format-picker.test.tsx` and two others). **Confirmed pre-existing** by stashing all of this session's work and re-running on a clean tree — identical 20 failures. Not caused by this work and not fixed here, but it means the workspace suite is currently red and someone should own that separately.
