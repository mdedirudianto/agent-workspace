# Session 28 — LB weight rebalance for `IP_LOCK_FAILED`: checked, not recommended

**Date:** 2026-08-05
**Servers:** `root@proxy` (46.250.234.153), `root@numa` (10.0.0.7), `root@db` (10.0.0.1) — read-only investigation, **no changes made**
**Trigger:** user proposal — equalize the `ytgrab_api` nginx upstream weight between `numa` and `db` to help with the 87 `IP_LOCK_FAILED` events flagged in session-026/027
**Result:** 🔍 Checked live. **Recommendation: don't equalize the weights** — the mechanism doesn't match the evidence, and it trades a plausible small benefit for a real, measured risk on `db`.

---

## Summary

Session-026/027 found 87 `IP_LOCK_FAILED ranged fetch returned 403` events in `~/ytgrab-canary.log` on `numa` since 2026-08-02, flagged by the dev agent's handoff doc (`CANARY_REDEPLOY_HANDOFF.md` item 4) as a real, uninvestigated issue. The user proposed equalizing the `proxy` nginx upstream weight for `ytgrab_api` (currently `numa` weight=2 / `db` weight=1) as a possible fix, reasoning that spreading load more evenly might reduce whatever is causing the 403s.

Checked the actual mechanism before recommending anything:

- **The 87 events come from the tier canary, which runs only on `numa` and never touches the LB.** `~/ytgrab-download-canary.sh --tiers` invokes `pnpm --filter @ytgrab/api proxy:canary -- --tier <tier>` directly on `numa` — a standalone `tsx` script, not an HTTP request through nginx. It resolves and fetches through one proxy within a single process invocation, on a fixed 5-minute cron cadence. Reweighting public traffic between `numa`/`db` has no path to changing this at all.
- **`gradeFetch`'s `IP_LOCK_FAILED` verdict is any status ≥400 on the ranged fetch step** (confirmed in `apps/api/src/proxies/doctor.ts:222`, and already flagged in the dev's handoff doc) — it's a bucket, not a diagnosis. A genuine exit-IP mismatch, a 429, and an untokened-URL 403 all land in the same label. Nothing about that classification is sensitive to which of the two API nodes issued the request.
- **`db` is the more loaded host already, and for a structural reason.** Live check: `db` load average **1.54** vs `numa` **0.04**. `db` isn't just the API secondary (`nice -n 10`, weight=1 by design) — it's also the Postgres host for `ytgrab_prod`, serving DB queries for **both** API nodes, plus running its own `bgutil-pot` and API instance. The existing 2:1 weight split already under-serves `db` relative to `numa`'s idle headroom; pushing more download/proxy traffic onto it (a 1:1 split would raise its share from ~33% to 50%) risks new contention on the one host that's also the shared database, for a fix that doesn't address the actual reported symptom.
- **The one plausible (unconfirmed) link is token contention, not load balance.** `numa`'s heavier share means its local `bgutil-pot` (PO-token minter, one per node) sees more download-tier proxy churn than `db`'s. The tier-canary always forces the `datacenter` tier specifically, which bypasses the `PROXY_METADATA_KIND_ORDER=direct,...` fix from session-025/`apps/api` 1.13.0 (that fix only reorders metadata, not the canary's forced single-tier probe or download traffic). So there's a believable path from "`numa` runs busier" → "its `bgutil-pot` is busier" → "the canary's own resolve calls contend for a token" → "untokened URL → 403 mislabeled `IP_LOCK_FAILED`" — but this is a **token-contention** story, not an LB-weight story, and the fix for it (if confirmed) would be tuning `numa`-local concurrency, not reshuffling the public traffic split.

## Recommendation

**Don't equalize the weights** to address `IP_LOCK_FAILED`. It doesn't reach the actual failure path (a canary that never touches the LB, and a production failure mode that isn't node-specific), and it would shift more load onto `db`, which is already the busier host in practice and carries a role (shared Postgres) the weighting was almost certainly set to protect.

**Better next step (cheap, no production change):** do the data-gathering the dev agent's handoff doc already asked for — correlate the 87 failure timestamps against `numa`'s `bgutil-pot` logs:

```sh
grep 'POT minter expired' ~/.pm2/logs/bgutil-pot-out.log   # on numa
```

If the timestamps cluster with minter-expiry events, the real fix is tuning `numa`-local concurrency (e.g. `YTDLP_MAX_CONCURRENCY`) or `bgutil-pot` capacity — not the LB. If they don't correlate, the mechanism is still open and the exit-IP logging suggestion in the handoff doc (`check_tier` logging `exitIp` alongside the verdict) is the next cheapest lever.
