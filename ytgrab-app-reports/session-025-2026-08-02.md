## Summary

Shipped `fix/download-stability-pot-contention` (`docs/POT_CONTENTION_ANALYSIS.md`): the standing ~15–18% `bot_challenge` rate on `videos:process` was never YouTube blocking our proxy IPs (42/42 hand-run extractions across 42 distinct datacenter proxies passed) — it was **contention on `bgutil-pot`**, the shared PO-token provider. yt-dlp forwards `--proxy` to it on every extraction; a rotating proxy invalidates its cached minter almost every call, and under load (23.6% challenge rate above 30 extractions/hr) it blows past its own 20s timeout, so yt-dlp proceeds tokenless — which YouTube answers with a bot challenge. Fix: metadata now goes through the **direct (no-proxy)** tier first (`PROXY_METADATA_KIND_ORDER=direct,datacenter,residential`), so one minter serves its full 12h TTL instead of being re-minted per rotating proxy; a new `YTDLP_MAX_CONCURRENCY` gate (4) bounds all yt-dlp spawns so they queue instead of stampeding the provider. Also fixed along the way: **captions had been 100% broken for 10+ days** (0 ok / 1,523 failed — a stale bot-challenge-string regex plus no proxy pool/retry on the caption path), and merge-queue failures were mislabeled (both "queue full" and "resolve failed" wrote the literal string `"queue full"`, corrupting the number `FFMPEG_MAX_CONCURRENCY` would be sized from).

Two operational fixes shipped ahead of the code deploy on both API nodes: capped `bgutil-pot`'s previously-unbounded heap (OOM-crashed 5 times) and upgraded yt-dlp `2026.06.09` → `2026.7.4` (8 weeks stale). `FFMPEG_MAX_CONCURRENCY` was raised 4 → 12 in the same restart as the code deploy (user decision: raise now rather than wait a day to re-measure the newly-separated `queue full`/`resolve failed` split — box is idle at 0.02 load either way).

**Docs correction carried forward:** `docs/DEPLOYMENT.md` still describes `numa` as "the only API node" (flagged stale already in session-022). `db` is confirmed still an active LB secondary running its own `ytgrab-api` + `bgutil-pot`, so every operator step in this release was applied to **both** nodes, not just `numa`.

Also stood up 3 new per-tier Uptime-Kuma push canaries (direct/datacenter/residential), closing the "aggregate canary hides a single dead tier" gap that let residential fail silently for 3 days in July behind a healthy datacenter tier. While wiring this up, discovered and fixed a real bug: the existing product-check canary (monitor **#46**) has been reporting **false DOWN on every run since 2026-06-24** (5+ weeks) — the script hardcoded `API=http://127.0.0.1:7009`, which broke the moment the API moved off loopback binding onto `numa`'s private IP in session-018's migration. Every twice-daily push and the between-push "no heartbeat" timeout has been a false alarm the whole time.
