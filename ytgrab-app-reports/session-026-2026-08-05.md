# Session 26 — Root-caused per-tier Kuma canary noise: broken `urlenc()` silently drops non-ASCII pushes

**Date:** 2026-08-05
**Servers:** `root@numa` (10.0.0.7), `root@monitor` (10.0.0.3) — investigation only, **no changes made** (handoff to dev agent per user)
**Trigger:** user reported "so many ytgrab notifications, each 5 minutes, and like half are errors" in the Telegram alert chat
**Result:** 🔍 Root cause found and confirmed live. Two distinct problems bundled together, both handed off for a code/config fix — nothing changed on `numa` or `monitor` this session.

---

## Summary

The 3 per-tier Kuma push canaries stood up in session-025 (`ytgrab Direct/Datacenter/Residential Tier Canary`, ids 50/51/52, `*/5 * * * *` cron on `numa` running `~/ytgrab-download-canary.sh --tiers`) are generating far more Telegram noise than the "known noise" note in `telegram-alerts/README.md` assumed. Pulled the ledger fresh (`telegram-alerts/pull.sh`) and found, since 2026-08-02: **682 down events** for these 3 monitors, of which **624 are `"No heartbeat in the time window"`** — Kuma's own internal watchdog firing, not a real reported failure.

Traced this to a real bug, not cron jitter:

**`urlenc()` in `~/ytgrab-download-canary.sh` (on `numa`) only escapes space/`;`/`&` — it does not percent-encode non-ASCII bytes.** The residential tier's failure detail string from `pnpm proxy:canary` is `"QUOTA_EXHAUSTED proxy returned 402 — plan out of bandwidth"` (note the em-dash, `—`, a multi-byte UTF-8 character). When that raw byte sequence lands unescaped in the push URL's query string, Kuma's push endpoint (`http://10.0.0.3:3001/api/push/<token>`) returns **HTTP 400 Bad Request**. `push()` in the script never checks curl's exit status or response (`curl -s ... >/dev/null`), so this failure is completely silent — the script logs `"DOWN residential QUOTA_EXHAUSTED..."` to its own local log as if the push succeeded, but Kuma never receives it. Kuma's watchdog then reports the generic `"No heartbeat in the time window"` every single cycle instead of the real message — this is the bulk of the noise the user is seeing.

**Confirmed live** (see Verification): replayed the exact request numa's cron sends, by hand — the version with the em-dash gets `400 Bad Request`; a plain-ASCII test message with the identical token succeeds and lands in Kuma's `heartbeat` table.

**Consequence — a real outage has been invisible for 3 days.** `~/ytgrab-canary.log` on `numa` shows the residential proxy tier has returned `QUOTA_EXHAUSTED proxy returned 402 — plan out of bandwidth` on **every single check since 2026-08-02 13:47** (868 occurrences as of this session) — a real, ongoing outage. None of it ever reached Telegram/Kuma, because of the bug above. Monitor #52 (`ytgrab Residential Tier Canary`) has received exactly **one** real heartbeat since it was created (a `"No heartbeat"` self-report from Kuma on 2026-08-02); every other row in its history is also `"No heartbeat in the time window"`. This is the same class of failure session-025 found and fixed for monitor #46 (silently false for 5+ weeks) — the fix meant to close that gap has its own version of the same gap.

The session-025 open-follow-up note — *"Residential tier canary (#52) will alert Telegram until the Webshare residential plan resets — reporting real QUOTA_EXHAUSTED state, not a bug"* — is **incorrect** and should be treated as superseded by this session: #52 has not alerted at all: it's been in a `"No heartbeat"` false-noise loop instead.

A second, independent contributor: all 3 tier-canary monitors have **`maxretries=0`** in Kuma (`interval=300`, `retry_interval=60`), so a single late/missed heartbeat — cron jitter, a slow `pnpm` cold start — is immediately treated as DOWN and notified, then flips back UP on the next successful push seconds later. That's 2 Telegram messages for a non-event, compounding on top of bug #1.

Separately, a **real, non-noise issue**: Direct/Datacenter tiers hit `IP_LOCK_FAILED ranged fetch returned 403` **87 times** in `~/ytgrab-canary.log` since 2026-08-02 — a genuine recurring proxy IP-lock failure, worth investigating with the Webshare pool independent of the alerting bugs above.

## Findings

| # | Finding | Evidence |
|---|---|---|
| 1 | `urlenc()` in `ytgrab-download-canary.sh` doesn't percent-encode non-ASCII bytes | `urlenc() { printf '%s' "$1" \| sed 's/ /%20/g; s/;/%3B/g; s/&/%26/g' \| cut -c1-180; }` — only 3 characters handled |
| 2 | Residential quota-exhausted message contains an em-dash, breaking the push | Manual replay: `msg` with `—` → Kuma responds `HTTP 400 Bad Request`; same request with `msg=test` (ASCII) → `HTTP 200 {"ok":true}`, row inserted into `heartbeat` table |
| 3 | `push()` never checks curl's result | `curl -s -m 15 "$1?..." >/dev/null` — no `$?` check, no response validation; failure is invisible to the script and to the operator |
| 4 | Monitor #52 (residential) has received exactly 1 real heartbeat ever | `SELECT msg, COUNT(*) FROM heartbeat WHERE monitor_id=52 GROUP BY msg` → 502× `"No heartbeat in the time window"` (2026-08-02 → now) + 1× `"test"` (this session's manual probe). Zero real `QUOTA_EXHAUSTED` rows despite 868 local log entries reporting exactly that |
| 5 | Residential tier has been down every single check for 3 days, invisibly | `grep -c QUOTA_EXHAUSTED ~/ytgrab-canary.log` → 868, first at `2026-08-02T13:47:20Z`, still ongoing as of this session |
| 6 | `maxretries=0` on all 3 tier monitors — no tolerance for a single late heartbeat | `SELECT id,name,interval,maxretries,retry_interval,resend_interval FROM monitor WHERE name LIKE '%ytgrab%'` → ids 50/51/52 all `interval=300, maxretries=0, retry_interval=60` |
| 7 | Direct/Datacenter genuinely fail `IP_LOCK_FAILED` (403) periodically — not alerting noise, a real proxy issue | `grep -c IP_LOCK_FAILED ~/ytgrab-canary.log` → 87 since 2026-08-02; also present in the Kuma ledger as real down/up pairs (53 in `telegram-alerts/ledger.jsonl`) |
| 8 | Ledger volume breakdown confirms the split | Of 682 down events since 2026-08-02 for the 3 tier monitors: 624 `"No heartbeat in the time window"` (bug), 53 `IP_LOCK_FAILED` (real), 5 `SLOW ... budget exceeded` (real, marginal) |

## Recommended fix (for the dev agent — not applied this session)

1. **Fix `urlenc()`** in `ytgrab-download-canary.sh` to properly percent-encode arbitrary UTF-8 bytes — e.g. swap the `sed`-based approach for `curl -G --data-urlencode` (let curl encode the query string itself) or a `python3 -c 'import urllib.parse,sys; print(urllib.parse.quote(sys.argv[1]))'` helper. This is in **both** the deployed copy (`/root/ytgrab-download-canary.sh` on `numa`) and the repo's versioned copy (`infra/canary/ytgrab-download-canary.sh`, per session-025's note about the same file needing a separate fix) — fix upstream in the repo so a future `install -m 755` doesn't reintroduce it, then redeploy to `numa`.
2. **Make `push()` fail loudly** — check curl's HTTP status (`curl -s -o /dev/null -w '%{http_code}'`) and log a clear `WARN push failed (HTTP $code) for $label` line when it isn't 200, instead of assuming success.
3. **Raise `maxretries` to 1 (or 2)** on Kuma monitors 50/51/52 (`ytgrab Direct/Datacenter/Residential Tier Canary`) so a single missed/late heartbeat doesn't immediately page — direct SQL against the embedded MariaDB, same access pattern as session-025 used to create these monitors (`docker exec uptime-kuma mariadb -u root -S /app/data/run/mariadb.sock kuma`).
4. **Not a monitoring fix, a real infra action:** the Webshare residential proxy plan needs its bandwidth quota topped up / reset — it's been fully spent since 2026-08-02 13:47 and every residential-tier request has failed since.
5. **Worth a look, real issue:** the 87 `IP_LOCK_FAILED` (403) events on Direct/Datacenter — may indicate a specific proxy IP getting rate-locked repeatedly; check against Webshare pool rotation/cooldown logic.
