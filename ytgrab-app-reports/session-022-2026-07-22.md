## Trigger

Production had been stuck on `9abf4aa` (v1.7.0) since session-020 (2026-06-28) while a July download outage was live — `pm2 logs` was a wall of `no healthy residential proxy`. A dev-agent handoff reported every fix for the outage (`docs/PROXY_FAILURE_ANALYSIS.md` F1–F5, F7, F9, F10) merged to `main` and unshipped, plus a new off-by-default direct (no-proxy) download tier (F6, downloads only). User asked to: redeploy the fix, check `docs/DEPLOYMENT.md` for the latest runbook, enable the direct tier now (accepting it can be disabled with a one-word env change later), and ship `apps/web` too for the new admin monitoring panels — even though Google OAuth env isn't configured on `app` yet.

## Notes / follow-ups

- **Direct tier is live but young.** Per `docs/DEPLOYMENT.md` §5 this wants a 30–60 min watch on `/admin/proxies` for the **Direct** series and `usedGiB` flattening before calling it settled. Rollback is deleting `direct,` from `PROXY_DOWNLOAD_KIND_ORDER` + `pm2 restart` on either node independently — no redeploy.
- **`db`'s blocked egress to `proxy.webshare.io`** needs its own investigation (likely a firewall/UFW rule scoped tighter than `numa`'s). Not urgent — downloads aren't affected, only `db`'s ability to self-heal its proxy list from Webshare's API — but worth fixing so `db` isn't silently degraded relative to `numa`.
- **`docs/DEPLOYMENT.md` §1 should be corrected** to list `db` as an active secondary API node, and drop the "v24 under nvm" claim for `app` (nvm was never actually there for the `devops` user).
- **Node 24 is now the *system default* on `db` and `app`**, installed via NodeSource (matching how `numa` already had it) — no nvm on either. On `app` (shared box, ~30 unrelated PM2 apps), this was a fleet-wide default-version change: existing processes kept running on their already-loaded v22 binary at the time, but the `apt install` itself triggered an immediate `needrestart`-driven bounce of **every** app on the box (not the originally-expected "whenever each app next restarts on its own"). Nothing broke this time, but future sessions doing `apt-get install`/`upgrade` involving `nodejs` on `app` should expect the same forced fleet restart via `needrestart`.
- **`apt.vector.dev` repo has a broken/expired GPG key on `app`** — unrelated to ytgrab, not fixed (out of scope), worked around by scoping `apt-get update` to just the NodeSource list. Flagging in case it blocks a future `apt-get update` on that box.
- **Web ships Phase 4a–4d** (web/mobile sign-in, cross-device history sync, `/account`) as an unavoidable side effect of fast-forwarding to `main`. Google sign-in visibly absent (button hidden, not broken) until `GOOGLE_CLIENT*` env is sourced for `apps/web/.env` on `app` — still an open item.
- **Rollback (API):** `git reset --hard 9abf4aa` on numa/db, restore `ytgrab-api-dist-9abf4aa`, `pm2 restart`. **Roll-forward only past migration 0010** — an older build's `ON CONFLICT (day, kind)` upsert fails outright once the PK includes `op`; a rolled-back API keeps serving downloads but stops recording proxy stats.
- **Rollback (web):** `git reset --hard 4259341` on app, rebuild, re-copy standalone static assets, restart.
- Canary still on `numa` (`/root/ytgrab-download-canary.sh`, twice-daily cron) — unchanged, kept reporting through the deploy window.
