# Session 43: thumbnails hung after the `app` reboot (Next image-cache startup scan); cache pruned, capped at 256 MiB (web 1.18.1, `fc9f7a1`)

**Date:** 2026-10-23 (morning)
**Servers:**
- `devops@app`: write (image-cache prune, pull, detached web build, restart); read (PM2, logs, `/proc`)
- `root@proxy`: read (nginx error log)
- numa and db: not touched (the API was not involved and not redeployed)

**Trigger:** the user reported that on `youtubegrab.com` the thumbnails never loaded (endless loading) and asked whether the redirect or the numa/db API was at fault. It followed this morning's private-network outage on `app` ([app-sysadmin session-007](../app-sysadmin-reports/session-007-2026-10-23.md): `eth1` lost carrier 05:51 WIB, fixed by a provider hard stop/start; boot 07:20 WIB).

**Result:**
- **Root cause:** Next.js 15.5.18 builds a disk-LRU index of its image cache at boot by reading every cache entry serially, and every `/_next/image` request awaits it. The cache had **53,915 entries / 1.5 GB** (default cap = 50% of free disk, so unbounded). After the reboot the page cache was cold, so the scan ran about **17 minutes** and every thumbnail request hung. It cleared by itself at ~07:40 WIB.
- **Fix, step 1:** pruned cache entries older than 7 days: 53,915 → **13,899** entries, 1.5 GB → 414 MB, no restart.
- **Fix, step 2:** `images.maximumDiskCacheSize: 256 MiB` in `apps/web/next.config.ts`, shipped as `fc9f7a1` (web 1.18.1). `origin/main` went `5ac47ef` → `fc9f7a1` (the user's 5 pending local commits plus this one); `app` went `71dcc62` → `fc9f7a1`. The API (`71dcc62`) was **not** redeployed.
- Cold-start check after the deploy: `Ready in 2.1s` (previous starts 30–90 s) with an empty cache.
- The numa/db API and the redirects were **not** involved: thumbnails go web → `/_next/image` → `i.ytimg.com`.

## 5. Incidents

1. **Thumbnail outage (cause above).** Window at least 07:21–07:40 WIB, plus whatever the 05:51–07:20 network outage covered. Self-resolved; permanent fix is the cap.
2. **Deploy asset gap ≈ 10 min (07:52–08:03 WIB).** `next build` deletes `.next/standalone` at start, so the running server had no client JS/CSS until the restart. I estimated 2–4 minutes in the plan; the real build took 10 min 46 s (the trace phase alone took ~5 min on 6 vCPU). The user had accepted a gap, but not one this long. Visitor impact was not measured (no per-request check of chunk 400s).
3. **A hung SSH call while starting the build.** I backgrounded a whole `cd && rm && date && nohup …` list, so `date`'s output stayed on the SSH pipe and the call hit the 120 s tool timeout. The build itself was unaffected (output redirected to its log, still progressing). I verified it on a fresh connection and later killed the two stale local `ssh` client processes (PIDs 71935/71936). Lesson: redirect everything of the backgrounded command, not just the build.
4. No secrets were printed and no production data was written. The cache prune is the only deletion, and it removed derived cache only.
