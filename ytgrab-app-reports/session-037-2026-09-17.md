# Session 37: HK scraper, datacenter proxy mass-disable, error-rate reality check (read-only)

**Date:** 2026-09-17
**Servers:** `root@numa` (read), `root@db` (read, incl. `ytgrab_prod`), `root@proxy` (read), `devops@app` (read)
**Trigger:** user report from the admin panel: (1) very high load yesterday, mostly HK; (2) errors high vs completed downloads "since the last update"; (3) 245 of 250 datacenter proxies disabled; (4) "All proxies" table has no pagination.
**Result:** **Investigation only, nothing changed on any host.** Full report with evidence and the fix plan is in the repo: `ytgrab/docs/PROD_ANALYSIS_2026-09-17_SCRAPER_PROXY_ERRORS.md`. It awaits user approval before any ops step or code change.

## 1. Findings

| # | Report | Reality | Sev |
|---|---|---|---|
| 1 | HK load spike | **Bulk scraper since 2026-09-16 19:51 WIB, still active.** `/videos:process` comes through a rotating residential-proxy network (~4,300 IPs/day, 1 request/IP, mostly US/NL/IN). The bytes are pulled by **~55–65 HK hosts**. Every HK-downloaded video (5,288/5,288) was processed first. Stale UA `Chrome/128.0.0.0` on 96% of API calls, spoofed referer, a random `cid` per request. **382 GB to HK by 09:30 today** (93% of downloads). Webshare datacenter usage **+422 GB on 09-16**. | 🔴 |
| 2 | Errors > completed | **Mostly metric definition plus slow downloads, not a 1.17.0 regression.** The admin "errors" count includes `aborted`, and **70% of aborted rows have an `ok` for the same client+video within 10 min**. Chart ≈ 42% errors; estimated real non-success ≈ 23%. Root driver: download **TTFB p50 19 s / p90 37 s**. Every attempt and every Range request re-runs yt-dlp (no per-proxy URL cache), and ~69% of datacenter resolves are bot-challenged first. Abort share was already 30–55% in August. | 🟠 |
| 3 | 245 DC proxies disabled | **Caused by #1 via a classification bug.** 208 were disabled in the 09-16 20:00 hour. Scraper load filled the 4-slot yt-dlp gate, and `ConcurrencyGateTimeoutError` (a local 20 s queue wait) **is counted as a proxy fault** in `pooled-download.ts` (`thrownErrorIsProxyFault` only excludes `BotChallengeError`). Client aborts and 429s count too. 5 strikes → disabled for 24 h. Webshare still lists 250 working proxies. They auto-return ~20:00–21:00 WIB today and will re-disable if the scraper is still active. | 🔴 |
| 4 | No pagination | Confirmed. `ProxyTable` renders all **627 rows** (367 archived) client-side and the default view includes archived. | 🟡 |

## 2. Irregularities found

| Item | Evidence |
|---|---|
| **Kuma #46 product canary has never passed** | `numa:/root/ytgrab-canary.log`: DOWN twice daily since **2026-06-25, zero UP ever**. The script uses `API=http://127.0.0.1:7009`, but the API binds `10.0.0.7`. The deployed script is byte-identical to repo `infra/canary/ytgrab-download-canary.sh`, so **session-025's fix never reached the repo** and was overwritten 08-17. The alert is noise. |
| `/process` advertises format IDs `/download` rejects | Format IDs like `140-drc`, `251-0`, `399-sr` → download validator `^\d+(,\d+)?$` → **400**, not recorded in `download_events`. 2,582 hits today from the scraper, and 22/week from real users. |
| Datacenter plan changed this morning | `proxy_plan_usage.plan_id` `14206476` → `14323402` at ~09:10 WIB, replacements 96 → 250. **Needs user confirmation.** |
| No API rate limiting at all | The design docs describe it; it's a Phase 5 unchecked item. |
| Origin open to non-CF traffic | `proxy` UFW 443 allows anywhere, so `cf-connecting-ip` and `cf-ipcountry` are spoofable if someone bypasses CF. |
| Second API consumer | One SG IP, 320–650 `/process` calls/day since ≥ 09-03, no UA/referer. One IR IP 100–250 downloads/day. |
| `process_events` FK violation fails user requests | 28/week `process_events_video_id_videos_id_fk`, plus ~6/week ZodError `formats … null`. |
| `db` Python 3.10 | yt-dlp deprecation banner fills the start of stored `error_detail` (2,000 chars) and hides the real `ERROR:`. The next yt-dlp release that drops 3.10 would break `db`. |
| Logs not rotated | `numa` `ytgrab-api-out.log` 264 MB, no pm2-logrotate. `proxy` nginx logrotate `size 200M` overrides `daily`, so `error.log` 95 MB is unrotated since Feb. |
| Weekly API restart | Both nodes SIGINT at 06:47 WIB on Sundays (09-06, 09-13). Not in root crontab, source unidentified. It resets in-memory pool, park and client-health state. |

## 3. Recommended actions (pending approval)

**Ops, today:**
- O1: CF WAF block on the `Chrome/128.0.0.0` UA for `/api/v1/videos*`.
- O2: CF rate limit plus an HK ASN review. A per-IP limit alone is weak: legit p99 is 32 downloads/IP/h, HK median 13/h.
- O3: reset the 245 disabled DC proxies **after** blocking.
- O4: confirm the Webshare plan change and add a bandwidth alert.
- Then O6: CF-only origin for the vhost. O7: fix canary #46 in the repo and redeploy. O8: Python ≥ 3.11 venv on `db`. O9: log rotation.

**Code (per repo workflow, each needs plan → cross-check → approval):**
- C1: exclude gate timeout, client abort and 429 from proxy health.
- C2: mass-disable breaker.
- C3: Redis rate limiter plus a per-IP concurrency and byte budget.
- C4: signed process→download token (contract change).
- C5: per-proxy URL cache plus a sticky proxy for Range requests (TTFB).
- C6: admin error metrics split and dedup.
- C7: proxies table pagination, hide archived.
- C8: format-ID mismatch.
- C9: 48 h `direct`-first A/B on `db` only, after the scraper is blocked.
