# Session 29 — Tier-canary interval widened 5min→15min: eliminates residual "No heartbeat" flapping

**Date:** 2026-08-06
**Servers:** `root@monitor` (10.0.0.3), `root@numa` (10.0.0.7)
**Trigger:** user reported still seeing `[ytgrab Datacenter Tier Canary] [🔴 Down] No heartbeat in the time window` Telegram alerts, and asked whether the 5-minute check cadence was necessary
**Result:** ✅ Fixed and verified live — false Down alerts on the Direct/Datacenter tier canaries stopped after widening the Kuma monitor interval and matching numa's cron

---

## Summary

Session-027 fixed the em-dash URL-encoding bug (residential tier's `QUOTA_EXHAUSTED` message silently failing to push) and raised `maxretries` 0→1 on the 3 tier-canary Kuma monitors (50/51/52). That closed most of the noise from session-026, but the user was still seeing `"No heartbeat in the time window"` Down alerts specifically on the Direct/Datacenter tiers.

Pulled a fresh ledger and confirmed this is a *different*, still-open issue: in the ~36 hours since the session-027 fix, 17 more false Down/Up flap pairs occurred (9 on Direct, 8 on Datacenter) — the canary script itself reported `UP ... OK 131072 bytes` reliably on every cycle throughout. Queried Kuma's `heartbeat` table directly and found the cause: **the tier-canary interval (300s) exactly matches numa's cron cadence (`*/5 * * * *`), leaving zero slack.** Kuma's internal push-monitor watchdog fires partway through each 5-minute window (observed ~3–3.5 min in) and occasionally catches the real heartbeat as "not yet arrived," flagging Down; the real heartbeat then lands ~100s later and flips it back Up. `maxretries=1` reduced but didn't eliminate this, since the tight interval gave the watchdog no margin to absorb normal cron/script timing variance.

The residential tier (52) was unaffected by this — it's been genuinely, continuously down (Webshare quota exhausted since 2026-08-02) and Kuma only alerts on state transitions, so it hasn't been re-notifying.

**Fix applied:** widened both the Kuma monitor interval and numa's cron to 15 minutes, giving 3x the slack. Verified live over 2 full cycles post-change: the watchdog's transient pending-state check still fires right at each boundary, but now resolves silently (`important=0`, flips to Up within seconds) instead of escalating to a real Down alert.
