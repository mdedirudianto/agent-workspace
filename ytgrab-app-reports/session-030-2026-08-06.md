# Session 30 — Kuma `maxretries` was masking real failure messages; added exit-IP logging for `IP_LOCK_FAILED`

**Date:** 2026-08-06
**Servers:** `root@monitor` (10.0.0.3), `root@numa` (10.0.0.7)
**Trigger:** user still seeing `[ytgrab Datacenter Tier Canary] [🔴 Down] No heartbeat in the time window` after session-029's interval widening
**Result:** ✅ Root-caused (not a repeat of the timing-jitter bug — a real `IP_LOCK_FAILED` event was being mislabeled) and fixed; added diagnostic logging so the underlying `IP_LOCK_FAILED` issue can finally be traced to a specific proxy

---

## Summary

Session-029 widened the Kuma tier-canary interval 5min→15min to fix false Down/Up flaps caused by timing-jitter racing the watchdog, verified clean over 2 cycles, and called it fixed. The user reported it was still happening. A fresh ledger pull showed a new flap at 13:15–13:30 UTC and disproved the "still a timing race" hypothesis: `numa`'s canary log showed a **genuine** failure at that exact time —

```
2026-08-06T13:15:28Z DOWN datacenter IP_LOCK_FAILED ranged fetch returned 403
```

— but Kuma's `heartbeat` table recorded it as `status=2 (pending) → status=0/important=1 "No heartbeat in the time window"`, discarding the real message entirely.

**Root cause: `maxretries=1` (set in session-027 to add jitter tolerance) is actively wrong for a push-type monitor.** On a DOWN push, Kuma doesn't alert immediately — it goes PENDING and waits `retry_interval` for a *follow-up* heartbeat to confirm the failure. But this canary only pushes once per cron cycle (now 15 min); no follow-up is coming within `retry_interval` (180s), so the wait always times out and Kuma's own watchdog fires the alert using its generic message instead of the real one the script sent. Session-026's original data confirms this is new behavior: at the old `maxretries=0` setting, genuine `IP_LOCK_FAILED` events showed their real message in the ledger (53 of them, called out separately from the "No heartbeat" bucket). `maxretries=1` silently started masking them after session-027.

Session-029's interval widening was real and correct (it fixed actual timing-jitter races — 0 such races since), but it doesn't help this class of failure at all, since `maxretries` was never providing genuine tolerance for a push monitor in the first place — it just delayed and re-labeled the same alert.

**Fixed:** reverted `maxretries` 1→0 on monitors 50/51/52. Alert volume for genuine failures is unchanged (they should alert — it's real signal), but the message will now correctly say `IP_LOCK_FAILED ranged fetch returned 403` instead of the misleading `No heartbeat in the time window`.

Separately, attempted to root-cause the underlying `IP_LOCK_FAILED` issue itself (111 events since 2026-08-02, open since session-026, previously deferred in session-028 pending a `bgutil-pot` log correlation). That correlation turned out to be a dead end — the `bgutil-pot-out.log` has no timestamps at all (pm2 isn't configured with `time: true`) and logs "POT minter expired" roughly every 80 seconds continuously (4,278 times over ~4 days), far too frequent to distinguish anything even if timestamps existed. Instead found a more direct gap: `doctor.ts`'s `probeProxy()` already returns `exitIp` and proxy `id` on every probe (including failures), but `check_tier()` in the canary script discards everything except `ok`/`verdict`/`detail` before logging — so there was no way to tell, historically, which specific proxy IP was responsible for any `IP_LOCK_FAILED` event. Patched the deployed script to log `exitIp`/`proxy` alongside every UP/DOWN line, so the next occurrence is actually traceable.

## Findings

| # | Finding | Evidence |
|---|---|---|
| 1 | The 13:15 alert was a real `IP_LOCK_FAILED` failure, not a timing race | `numa` log: `13:15:28Z DOWN datacenter IP_LOCK_FAILED ranged fetch returned 403` |
| 2 | Kuma recorded it as pending-then-generic-timeout instead of the real message | `heartbeat` table: `51 \| 13:15:28 \| status=2 \| "datacenter: IP_LOCK_FAILED..."` → `51 \| 13:15:31 \| status=0/important=1 \| "No heartbeat in the time window"` |
| 3 | `maxretries>0` can't provide real tolerance for a push-type monitor — there's no re-poll, only a wait | Push monitors receive state from an external script on its own schedule; Kuma's retry can only wait for a follow-up push, which won't arrive before the next cron cycle |
| 4 | Before session-027 raised `maxretries` to 1, real `IP_LOCK_FAILED` events showed correctly in the ledger | Session-026 finding #8: "53 `IP_LOCK_FAILED` (real)" tracked distinctly from the "No heartbeat" bucket at `maxretries=0` |
| 5 | `bgutil-pot-out.log` has no timestamps and fires too frequently to correlate | `wc -l` → 94,850 lines / 4-day uptime; `grep -c "POT minter expired"` → 4,278 (~1 every 80s); no per-line timestamp, pm2 not configured with `time: true` |
| 6 | The canary probe already captures `exitIp`/proxy `id` on every result, including failures — but the script discards them before logging | Live `pnpm proxy:canary --tier datacenter --json` → `{"exitIp":"103.101.88.212","id":"datacenter:103.101.88.212:5936",...}`; `check_tier()`'s python parse only extracted `ok`/`verdict`/`detail` |
| 7 | `IP_LOCK_FAILED` is specifically an IP-stickiness failure between two stages of one proxy connection | `doctor.ts` comment: "googlevideo rejects (403) unless the byte fetch egresses from the resolving IP" — points at datacenter/direct tier proxies not holding a stable exit IP across two sequential requests |
