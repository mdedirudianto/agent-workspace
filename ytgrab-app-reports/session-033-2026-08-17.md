## Summary

The repo work (14 commits, branch `fix/download-403-media-fetch`, merged `--no-ff` as `572beb9`) is written up in the product repo: [`docs/DOWNLOAD_403_ANALYSIS.md`](https://github.com/biji-dev/ytgrab/blob/main/docs/DOWNLOAD_403_ANALYSIS.md) for the investigation, [`docs/DEPLOY_MEDIA_403_FIX.md`](https://github.com/biji-dev/ytgrab/blob/main/docs/DEPLOY_MEDIA_403_FIX.md) for the release-specific runbook, [`docs/FOLLOW_UPS_MEDIA_403.md`](https://github.com/biji-dev/ytgrab/blob/main/docs/FOLLOW_UPS_MEDIA_403.md) for what was deliberately left. This session is the deploy.

**What the release does:** googlevideo answers the media byte-fetch with 403 based on YouTube's per-request `fexp` experiment bucket, not on our exit IP. Our code was reading that 403 as "this tier is broken", which parked the free ~2 MB/s `direct` tier ~11.5 h/day and pushed every download onto metered 42–93 KB/s proxies at ~20 GB/day. The release stops charging a 403 to tier health, resolves progressive formats with a POT-bearing player client, records merged failures, logs the `fexp` bucket on every 403, and renames the `IP_LOCK_FAILED` verdict.

### The mechanism, confirmed live

Every one of the 18 diagnostic-carrying 403s is a **pot-less `ANDROID_VR`** URL, and **17 of 18 sit in the enforcing bucket `51946838`**:

```
tier=direct status=403 url={"hasPot":false,
  "fexp":"51565116,51946838,52089683","client":"ANDROID_VR","itag":"18",
  "host":"rr5---sn-ojnpo5-5f.googlevideo.com"}
```

**Zero `WEB`/`pot=yes` URLs were refused.** That is the clearest possible confirmation that the POT-bearing client defeats this failure mode, and it took ~20 minutes of production traffic to establish — the field was added for exactly this.

## 4. Findings

| # | Finding |
|---|---|
| F1 | **`api.youtubegrab.com` 301s to apex** — the API is served under the apex path, not the subdomain. Matches monitor #34's "UP via 301" note; worth knowing before writing a health check against the subdomain. |
| F2 | **The API binds the private IP, not localhost.** `ss` shows `10.0.0.7:7009`, so `curl localhost:7009` returns nothing. Cost ~10 minutes chasing a non-existent startup failure — use the bound address. |
| F3 | **Manual canary runs silently do not alert.** `KUMA_PUSH_DIRECT/DATACENTER/RESIDENTIAL` are set as **env lines at the top of root's crontab**, not in the script. Running `./ytgrab-download-canary.sh --tiers` by hand prints `no push URL configured … nothing will be alerted`. Alerting via cron is intact — but this reads exactly like broken alerting, and "fixing" it would be a mistake. |
| F4 | **Graceful shutdown works properly** — `SIGINT → server drained → redis closed → db pool closed`, and an in-flight 1,759 s merge completed before the drain. |
| F5 | Webpack **cache** packs under `.next/cache/webpack/` retain the old `IP_LOCK_FAILED` string after rebuild. Not served, not runtime — build cache only. |

## 5. Corrections to earlier sessions

**The "111+ `IP_LOCK_FAILED` (403) events" follow-up (sessions 026/028/030/032) is answered, and its framing was wrong.** It was tracked as "a real, recurring proxy IP-lock issue". It is not an IP-lock and not proxy-side: the same 403 reproduces at the same rate on the server's own IP, on datacenter proxies, on residential proxies, and from an unrelated home residential connection. It tracks YouTube's per-request `fexp` experiment bucket. The verdict has been renamed `MEDIA_FETCH_403` precisely because the old name asserted a disproven cause and sent three investigations at the proxy pool.

**Session-032's lead was correct and mattered more than it looked.** It observed that every datacenter probe reports the same proxy `103.101.88.212:5936`, i.e. the canary re-tests one IP instead of sampling the pool. Confirmed still true this session. That defect is *why* the tier canaries show all three tiers failing in near-lockstep (~44–53% today) while the production aggregate shows a clear, stable ordering:

| Day | datacenter | residential | direct |
|---|---|---|---|
| Aug 17 | **37.9%** | 45.7% | **57.5%** |
| Aug 16 | 45.2% | 50.2% | 67.9% |
| Aug 15 | 50.1% | 51.7% | 70.5% |

I initially trusted the canary over the aggregate and told the user the tiers were equivalent. **That was wrong** — the ~1,000-attempts/day aggregate is the better evidence, and it says `direct` is consistently the worst tier by ~20 pp. Stronger still: datacenter is only tried *after* direct has already failed, so it works the harder residue and still succeeds 62% of the time.

## 6. The residual, and it is now fully explained

Post-deploy failure is materially better (11.8% in the first hour vs 28.9%) but not zero. The remaining muxed failures are **videos where `web_safari` cannot serve itag 18 at all**:

```
Bpy7zxj0Z2w    web_safari OK    c=E pot=
Mc6voRYTu1c    web_safari FAIL  Requested format is not available
```

For `Mc6voRYTu1c` the override has no URL to give, so the code's designed fallback drops to yt-dlp's default client — producing a pot-less `ANDROID_VR` URL, which the enforcing bucket then refuses ~50% of the time. That fallback is deliberate: without it the video would fail *every* time instead of half the time. Ruled out along the way: stale Redis URLs (403s are spread across the whole window, not clustered after restart), format mis-bucketing (all sampled videos classify itag 18 as `muxed`), and load sensitivity (`web_safari` resolved 6/6 sequential **and** 6/6 concurrent).

**So the honest position: for a subset of videos there is currently no client that yields a servable progressive URL.** That is the next real problem, and it is YouTube-side.

## 9. Incident: the web deploy shipped without client assets (same session, 23:07–00:45 WIB)

**Caused by this session's Step 3.** User reported the site erroring in-browser and the admin magic link never arriving:

```
GET /_next/image?url=%2Flogo.png&w=96&q=75   400 (Bad Request)
2908-c9aceb2bff4a2b51.js:1     Uncaught SyntaxError: Unexpected token '<'
main-app-93b364d817dec3cd.js:1 Uncaught SyntaxError: Unexpected token '<'
layout-829ff55cf74fd395.js:1   Uncaught SyntaxError: Unexpected token '<'
```

### Root cause — one fact, three symptoms

`apps/web` is a Next **standalone** build. `next build` regenerates
`.next/standalone/` from scratch and deliberately does **not** place
`.next/static` or `public` inside it — copying them is a manual post-build step,
documented in the repo at `docs/DEPLOYMENT.md:254-257`. **I ran build + restart
and skipped it**, and because the build wipes the directory, the copy made by a
previous deploy was destroyed. On `app` afterwards:

```
.next/standalone/apps/web/.next/static  → ABSENT
.next/standalone/apps/web/public        → ABSENT
```

| Symptom | Mechanism |
|---|---|
| `Unexpected token '<'` | Chunk missing → falls through the `[...notFound]` catch-all → **307 → HTML**, which the browser parses as JavaScript |
| `/_next/image` 400 | `public/logo.png` absent, so the optimizer has no source |
| **No magic-link email** | Same cause. JS never loads → React never hydrates → the login form cannot submit. Confirmed: newest `verifications` row was **19:27 WIB, pre-deploy**; the 23:07 attempt created none |

**Ruled out:** the Resend key (send-only restricted key — its 401 on `/domains` is expected, not invalid) and authorization (`dedi@biji.uk` exists, `role=admin`, verified). Both were red herrings.

### Why it survived my post-deploy checks

Every check I ran passed. `curl https://youtubegrab.com/` returned **200** with server-rendered HTML; both API nodes were healthy; `pm2` was green. The site *rendered* and was *entirely non-interactive*. **A status-code check cannot detect this, because the wrong answer is a 200.** I verified the API directly and the page's HTTP status, and never fetched a chunk the HTML referenced to confirm it was actually JavaScript.

**Cloudflare hid half of it:** `webpack-*.js` (hash unchanged across builds) served from a 6.5-day-old cache `HIT` while new hashes `BYPASS`ed to origin and failed — so the site was intermittently broken depending on which chunks a visitor needed, and would have degraded further as cache entries expired.

Galling detail: I had documented this exact failure mode in the repo's own `FOLLOW_UPS_MEDIA_403.md` §9 hours earlier — "after a partial deploy… a missing chunk turns into a syntax error rather than an honest 404" — and then walked into it.

### Remediation

| # | Action |
|---|---|
| 1 | Copied `.next/static` + `public` into the standalone tree, `pm2 restart ytgrab-web`. All 22 referenced assets → 200 `application/javascript`; `/_next/image` → 200 `image/png` |
| 2 | **No Cloudflare purge needed** — verified rather than assumed: HTML is `cf-cache-status: DYNAMIC` (not cached), and cached chunks are content-hashed and therefore immutable |
| 3 | Triggered a real magic link for `dedi@biji.uk` → `{"status":true}`, new `verifications` row, no send error logged |
| 4 | Browser-verified: **0 console errors**, video processes, format picker and CTA render, admin login form live |

### Prevention shipped (`apps/web` 1.15.2, `63080ae`)

Documentation had already failed once here, so the mechanics changed instead:

- **The copy is now part of the build.** `apps/web` `postbuild` → `scripts/copy-standalone-assets.mjs`, which **fails loudly** on a missing source rather than shipping a broken tree. Cache-safe (turbo's `build` outputs already include `.next/**`). Verified end-to-end on `app`: a plain `pnpm --filter @ytgrab/web... build` now produces a complete tree.
- **A missing framework asset 404s** instead of redirecting — `/_next/*` now calls `notFound()` in the catch-all, so the fault names itself.
- **`scripts/smoke-web-assets.mjs <base>`** resolves every asset the served HTML references and asserts the **content-type**, cache-busted so it measures the origin not a CDN edge. Verified both directions: **exit 1** against a simulated outage, **exit 0** against production.
- Also fixed `apps/web`'s `start` script, which ran `next start` — impossible against a standalone build.

### Lesson for future deploys

**Add `node scripts/smoke-web-assets.mjs https://youtubegrab.com` to every web deploy.** "HTTP 200 and it renders" is not evidence that a web deploy worked.
