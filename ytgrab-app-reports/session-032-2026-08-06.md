# Session 32 — Root-caused the "No heartbeat" alerts properly: Kuma's deadline is anchored to the last heartbeat, not the clock

**Date:** 2026-08-06
**Servers:** `root@monitor` (10.0.0.3), `root@numa` (10.0.0.7) — read-only on numa
**Trigger:** user reported `[ytgrab Datacenter Tier Canary] [🔴 Down] No heartbeat in the time window` for the **third** time, after session-029 and session-030 both claimed to have fixed it
**Result:** ✅ Actual mechanism identified and fixed (`interval` 900s→1200s); verified over 4 cycles with 0 false alerts and a 40x margin against observed variance. **Both prior fixes were wrong about the cause** — corrected below.

---

## Summary

Third report of the same alert. The previous two sessions each identified a real problem and fixed it, but neither was the thing actually generating these alerts.

**The real mechanism:** Uptime Kuma anchors a push monitor's deadline to **the last heartbeat it received**, not to a wall-clock schedule. The canary pushes at `cron_time + script_runtime`, and script runtime varies per cycle. Working through it:

```
deadline = previous_arrival + interval
         = previous_cron + previous_runtime + interval

arrival  = current_cron + current_runtime
         = previous_cron + cron_period + current_runtime
```

With `interval == cron_period` (both 900s after session-029), the common terms cancel and it reduces to:

> **the heartbeat is late whenever this cycle's runtime exceeds the previous cycle's.**

That is not jitter — it is a ratchet that trips roughly every other cycle, regardless of how large the interval is, as long as it equals the cron period.

The 14:30 alert, exactly:

| | time | note |
|---|---|---|
| Previous datacenter heartbeat | 14:15:30 | script took 30s |
| Kuma's deadline | 14:30:30 | = 14:15:30 + 900s |
| **Watchdog fired** | **14:30:31** | 🔴 Telegram: "No heartbeat in the time window" |
| Real heartbeat arrived | 14:30:43 | script took 43s — **13s late** |

Datacenter runtimes over the preceding 5 cycles: 32s, 29s, 31s, 30s, **43s**. Nothing was wrong with the canary or the proxy — the script simply ran 13 seconds slower than the cycle before it.

**The fix:** make Kuma's `interval` meaningfully *larger* than the cron period, so runtime variance can't consume the deadline. `interval` 900s → **1200s** (20 min) with cron unchanged at `*/15` gives **300s of slack**. `maxretries` stays at `0` (session-030's change, which is correct — see below).

## Corrections to sessions 029 and 030

Both prior sessions declared this fixed. Recording precisely what each got right and wrong, since the follow-up notes in the README were misleading.

| Session | What it did | Verdict |
|---|---|---|
| **029** | Widened cron `*/5`→`*/15` **and** Kuma `interval` 300s→900s | ❌ **Did not address the cause.** Scaling both together kept them equal, so slack stayed at exactly 0 seconds. The absolute numbers changed; the quantity that mattered did not. Its "0 false alerts over 2 cycles" verification was luck — at ~50% per-cycle odds, two clean cycles is a 1-in-4 coin flip. |
| **030** | Reverted `maxretries` 1→0 | ⚠️ **Correct fix, wrong stated reason, and it made the noise worse in the short term.** The message-masking analysis was right and is now proven (see Verification: the 15:30 real failure alerted with its true message). But `maxretries=1` had been *accidentally absorbing* the ratchet — a late heartbeat went PENDING and resolved silently when the real push landed seconds later. Removing that cushion is why alerts reappeared immediately after session-030. |

The honest summary: session-029 fixed nothing and mis-verified; session-030 fixed a real and separate defect while removing the accidental mitigation for this one. Only the combination of session-030's `maxretries=0` **and** this session's interval slack produces correct behavior.

## Verification

Watched **4 full cycles** (15:00, 15:15, 15:30, 15:45 UTC) rather than the 2 that produced session-029's false positive.

| Check | Result |
|---|---|
| False alerts (`important=1` + `No heartbeat`) across 4 cycles | **0** |

| Largest cycle-over-cycle runtime increase | **+7s** (25s→32s) against **300s** of slack — ~2% of budget, a ~40x margin |
| Real failure handling (15:30 cycle) | 🔴 `datacenter: IP_LOCK_FAILED ranged fetch returned 403` (`important=1`) — real cause, correctly alerted |
| Recovery handling (15:45 cycle) | ✅ `datacenter: OK 131072 bytes` (`important=1`) |
| Residual `No heartbeat` rows | Present only for monitors *already* in a down state (52 residential, 51 during its real outage) — all `important=0`, no notification fired |

The margin argument matters more than the cycle count here: 4 clean cycles alone would be ~94% confidence given ~50% prior odds, but the +7s-against-300s measurement shows the failure mode is now ~40x away from triggering, which is the stronger evidence.

## Notes / follow-ups

- **The `IP_LOCK_FAILED` root cause has a new lead (from session-030/031's exit-IP logging, paying off immediately).** The datacenter canary re-probes the *same* proxy (`103.101.88.212:5936`) every cycle rather than sampling the ~100-proxy pool. The likely reason: the canary selects with `observeOnly` (deliberate — so a monitor can't skew the pool it watches, per the script's own header) which doesn't bump `used_count`, so the deterministic LRU round-robin never advances. **This is an inference from the log pattern plus the script's comments, not verified against the selector code** — confirm via `/admin/proxies` or `apps/api/src/proxies/pool.ts` before acting. If it holds, the recurring `IP_LOCK_FAILED` is one flagged IP intermittently 403ing, not a tier-wide fault, and pool recycling would address it.
- **Webshare residential quota still exhausted** (unchanged since 2026-08-02, now 5 days) — still a billing action outside SSH scope.
- **Lesson for future monitoring config:** for any Kuma **push** monitor, `interval` must exceed the producer's schedule period by more than the producer's runtime variance. Setting them equal guarantees roughly half of all cycles alert falsely. Monitor #46 (`ytgrab Download Canary`, `interval=43200` vs. twice-daily cron = 43200s period) has **the same zero-slack configuration** and is a latent instance of this bug — it has not been noticed because its runtime variance is tiny relative to a 12-hour window, but it is the same defect. Worth widening to ~46800s (13h) opportunistically.
