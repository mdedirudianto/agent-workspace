## Root Cause

## Ledger Bug Found (`telegram-alerts/pull.sh`)

Netdata 2.x status codes are **3 = WARNING, 4 = CRITICAL** (confirmed by distinct `new_status` on all 5 hosts; 2 never appears). `pull.sh` mapped 3 → CRITICAL and only selected `IN (2,3)`, so:

- every netdata row labelled `CRITICAL` before today is really a **WARNING**;
- real CRITICALs (status 4, e.g. 279 `web_log_1m_successful`, 4 `internal_errors` on proxy) were **never pulled**.

Fixed going forward (2→WARNING legacy, 3→WARNING, 4→CRITICAL; SQL now `IN (2,3,4)`); README documents the caveat and the "ledger ≠ what reached Telegram" point. **Backfilled for the last 72h only** (256 rows, `"backfill":true`, Actions 7) — resetting the checkpoints would have duplicated ~11k rows, so older missing CRITICALs stay missing.

### Deliberate deviation from the first proposal

The first recommendation was a fleet-wide `DEFAULT_RECIPIENT_TELEGRAM="…|critical"`. Not applied: `alarm-notify.sh` supports the modifier (verified `filter_recipient_by_criticality`), but it would also mute genuine resource warnings — e.g. `app` `ram_available` (WARNING) — and 3 of the 4 proposed "drop" alarms were already `silent`. Targeted per-alarm silencing gives the same noise cut with no loss of disk/RAM/swap/load visibility. The `|critical` option remains available if still too noisy.
