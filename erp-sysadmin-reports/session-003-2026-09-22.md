# Session 3 — Enable Server Scripts (bench-wide)

**Date:** 2026-09-22
**Server:** `root@erp` (`217.15.166.117` public, `10.0.0.6` internal)
**OS:** Ubuntu 24.04.4 LTS
**Goal:** Unblock "Server Scripts feature is not available on this site" seen when trying to add a Server Script in the ERPNext desk, and decide the enablement scope for the grobiz multi-tenant instance.

---

## Background

Frappe (v16.9.0, bench 5.29.1) gates the whole Server Script doctype behind a single
config key, `server_script_enabled`, checked in `frappe/utils/safe_exec.py`:

```python
def is_safe_exec_enabled() -> bool:
    return bool(frappe.get_common_site_config(cached=True).get(SAFE_EXEC_CONFIG_KEY))
```

This reads **`common_site_config.json` only** — never a per-site `site_config.json` —
so the flag is bench-wide by construction. There is no way to enable it for one
tenant site and not another on the same bench; it was absent (disabled) everywhere.

**Security check before enabling:** the `Server Script` doctype's own permission is
gated on a separate role, **`Script Manager`** — not `System Manager`. Every grobiz
tenant "owner" is granted `System Manager` on their own site
(`apps/api/src/core/erpnext/roles.ts` in the grobiz repo), which raised the question
of whether enabling this would hand code-execution to merchants. Queried the role
tables directly:

- Base site (`erp.gro.biz.id`): only `Administrator` and the ops `admin@gro.biz.id`
  account hold `Script Manager`.
- Sample tenant site (`04cb57c2.erp.gro.biz.id`): **only `Administrator`** holds it —
  the merchant owner user does not, and `roles.ts` never assigns `Script Manager` to
  `owner`/`manager`/`kasir`.

So enabling the feature bench-wide does **not** expose scripting to any tenant/merchant
— only whoever holds the per-tenant `Administrator` login (rotated/revealed from the
admin dashboard) or the ops `admin@gro.biz.id` account (currently only provisioned on
the base site) can use it. Confirmed with the user this matches intent: server-side
scripting is meant to stay an internal/ops capability, rarely if ever touched by
tenants.

## Actions Taken

| # | Action | Detail | Result |
|---|--------|--------|--------|
| 1 | **Enabled `server_script_enabled` globally** | `sudo -u frappe bench set-config -g server_script_enabled 1` — writes into `sites/common_site_config.json` (bench-wide, applies to all current + future sites automatically since `bench new-site` inherits the same file). | Done |
| 2 | **Restarted bench** | `sudo -u frappe bench restart` (supervisor groups `frappe-bench-web` + `frappe-bench-workers`). Config is otherwise cached in-process for up to 60s per worker; restart makes it take effect immediately. Single shared bench serving all 41 sites (`dns_multitenant`) — restart is necessarily all-sites-at-once, ~10s blip. | All processes back to RUNNING with fresh PIDs |
| 3 | **Verified** | `bench --site erp.gro.biz.id console` → `server_script.enabled()` returns `True`. Spot-checked a tenant site (`04cb57c2.erp.gro.biz.id`) → also `True`. | Confirmed on base + tenant |
| 4 | **Documented for grobiz dev agent** | Added a section to `~/Projects/grobiz/docs/guides/erpnext-access.md` explaining the capability, who can actually use it, and a guardrail against ever adding `Script Manager` to `ERPNEXT_ROLE_MAP`. | Done |

---

## Config Change

`sites/common_site_config.json` — added:

```json
"server_script_enabled": 1
```

**Rollback:** `sudo -u frappe bench set-config -g server_script_enabled 0` then
`sudo -u frappe bench restart`.

---

## Notes

- This is a standing platform capability now, not a one-off tweak — new tenant sites
  provisioned going forward inherit it automatically via `common_site_config.json`,
  no change needed in the grobiz provisioning code.
- Scripting access is effectively restricted to whoever can log in as `Administrator`
  on a given site (ops-controlled, per-tenant password from the admin dashboard) — see
  `docs/guides/erpnext-access.md` in the grobiz repo for how that login works.
