avilia is the affiliate operating system that Hoteru reports booking events to. pnpm/Turborepo
monorepo with 2 deployable apps: `backend` (Fastify 5 + Prisma 6, 22 models) and `portal`
(Vite + React 19 SPA). First production deploy — it previously existed only as a staging
instance on `dev` (`*.dev.avilia.id`, `deploy@154.26.130.96`), which is untouched and still running.

**No Redis.** Unlike hoteru, nothing in the codebase uses Redis — Postgres is the only datastore.

### TLS deviation from plan: HTTP-01, not DNS-01

The plan called for a DNS-01 wildcard (as hoteru uses), but no Cloudflare API token exists for the
`avilia.id` zone and the user added the `app`/`api` records manually. Verified that Cloudflare
passes plain HTTP through to the origin (no forced HTTPS redirect), so **HTTP-01 webroot works and
renews**. Consequence: **no wildcard** — a new subdomain needs the cert re-issued with the extra
`-d`. If the zone ever enables "Always Use HTTPS", renewal breaks; DNS-01 would then be required.

## Findings

- **`SECRET_ENCRYPTION_KEY` is load-bearing.** It AES-256-GCM-encrypts every hotel's webhook
  secret in `ServiceSecret`. If it is lost, all stored service secrets become undecryptable and
  every hotel must be re-provisioned. It exists **only** in `apps/backend/.env` on `app` — back it
  up to Vaultwarden.
- **`config.ts` has no production boot guard.** Missing `JWT_SECRET`/`SECRET_ENCRYPTION_KEY`
  silently fall back to the dev values committed in `.env.example` — a footgun for any future
  instance. Verified at runtime here that the real values loaded; a fail-fast guard belongs upstream.
- **Repo deploy docs describe infrastructure that isn't ours** (`docs/operations/deployment.md`,
  `docs/agents/deploying-to-prod.md`): single VPS, `/home/deploy`, `127.0.0.1:4030`, local
  Postgres, `certbot --nginx`. `ecosystem.config.cjs` binds `127.0.0.1:3001`. All adapted to the
  cluster and **not used as written** — same recurring trap hoteru's repo has.
- Route `POST …/affiliate-sync` validates the body **before** auth, so an unauthenticated request
  with no body returns 400 rather than the documented 401 (401 with a valid body). Cosmetic.
- No `trustProxy` in the Fastify setup, so request logs show the proxy IP (`10.0.0.2`) as the
  client. `@fastify/rate-limit` is registered with `global: false` and no route opts it in, so
  nothing is rate-limited today — but if a limiter is ever added, it would key on the proxy IP and
  throttle all users together.

## Hoteru ↔ Avilia integration — analysed, deliberately NOT wired

Direction is **one-way: Hoteru → Avilia**. Avilia never calls Hoteru's API (its reconciliation
polling is inert — no `pollingEndpoint` set, and Hoteru exposes none). The only reverse link is the
promo URL (`https://<hotel site>/r/<slug>`) that the portal shows affiliates.

To wire one hotel later:
1. In Avilia (as `avilia_admin`): `POST /api/provisioning/services` with `serviceId` `svc_bwalk` /
   `svc_technopark` (these IDs are what the portal's promo-link map expects). The response returns
   the webhook secret **once**.
2. In that hotel's hoteru `apps/backend/.env`, then `pm2 restart <hotel>-api`:
   `AVILIA_ENABLED=true`, `AVILIA_SERVICE_ID`, `AVILIA_SERVICE_SECRET`, and
   `AVILIA_EVENTS_URL=http://10.0.0.5:3140/api/service-events/events` — the **private** URL, since
   both apps live on `app`; it avoids the Cloudflare hairpin (whose WAF/bot rules can block
   server-to-server POSTs) and the payload is HMAC-signed regardless.
3. Candidates: the **Bwalk** and **Technopark** tenants. Central `~/hoteru` (shared demo, 3 hotels
   on one process) must stay disabled — one `service_id` would conflate hotels.

**Blockers to fix in the Avilia codebase before wiring:**

- ❗ **Promo links point at staging.** `packages/utils/src/promo-links.ts` hard-codes
  `bwalk.dev.hoteru.uk` / `technopark.dev.hoteru.uk` (confirmed present in the built bundle).
  Production affiliates would be handed **staging** links. Needs `bwalk.hoteru.co.id` /
  `technoparkmalang.hoteru.co.id`, ideally config-driven.
- ❗ **Every synced affiliate gets the hard-coded password `aff123`**
  (`provisioning.service.ts:647`, `db/ledger-repository.ts:107`) — login with it returned 200 in
  the contract test. Needs a real credential flow before onboarding real affiliates.
- ⚠️ **Avilia ignores the hotel's commission rate.** Hoteru sent 8% (`defaultRateBps` 800) but the
  ledger recorded **10%**: `syncPartnerAffiliate` only creates a rate for the demo offer
  `offer_room_weekend_001`, so real `roomTypeId` offers fall back to the 1000bps JIT default. The
  shadow ledger will diverge from hoteru's own commission numbers.
- ⚠️ **Hoteru swallows webhook rejections.** With a wrong secret, Avilia returned 401 and hoteru's
  `emit()` logged nothing (it never inspects the response status). A misconfigured hotel looks
  exactly like "no bookings yet" — after wiring, confirm via Avilia's dead-letter queue / nginx logs.
- ⚠️ **Existing affiliates never sync.** `syncAffiliate` fires only on affiliate *creation*, so
  Bwalk's BW01–BW100 and Technopark's existing affiliates won't exist in Avilia until their first
  attributed booking auto-creates them with a placeholder email (`<slug>@<hotel>.aff.local`).
  A one-time backfill through the same endpoint (Bearer auth) would seed them with real emails.
